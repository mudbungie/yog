## Origin
Same investigation as bl-bd9d (conversation <agent-id>). This is the second, independent contributing defect: even once the real cause (role toolset gap) is fixed for `message`, this class of confusion will recur for any future tool/role mismatch, because an agent has no reliable way to introspect what it can actually call.

## Evidence
The agent's branch worktree (agents/<agent-id>) contains, per `git ls-tree`:

    descriptions/skills/{bash,dispatch,load_skill,message,read_file}.md
    descriptions/tools/{bash,dispatch,load_skill,message,read_file}.json

i.e. the FULL 5-tool pool's schemas and skill blurbs are committed to every branch, per lernie ARCH.md §3.3 "Descriptions-always population": "the harness copies, from the data-root pools, every available tool's JSON schema ... and every available skill's SKILL.md frontmatter ... into descriptions/**" — unconditionally, not filtered by the branch's own role's `tools:` grant.

But the actual wire `tools:` array sent to the model (steps/.../006/request.json) contained only `["bash","read_file","load_skill"]` — message and dispatch were both present as on-disk descriptors but not actually callable.

The agent has no copy of `providers.yaml` (the actual source of truth for its grant) in its own worktree — that file lives only on the `config/default` branch, which the agent's branch forked from but does not carry forward as a readable file (confirmed: `providers.yaml` does not appear in `git ls-tree -r agents/<agent-id>`). So when the user asked "why can you not [send a message]? do you not have the message skill/tool?" (messages/005-user.md), the agent's ONLY avenue for investigation was `bash`-exploring `descriptions/`, where it found what looks like full documentation for a `message` tool (schema + skill body) with no visible signal that this particular role was never granted it. This is what produced the multi-turn confusion in messages/006 through 018: the agent initially concluded (messages/010) "this environment seems to support messaging" before eventually landing on the correct but confusing conclusion "I still can't invoke a message tool directly ... only bash, read_file, and load_skill are actually exposed to me as callable tools here" (messages/018).

Per ARCH.md §3.3 itself, this may even be a spec-compliance gap, not just a UX one: "a tool's skill composes as the description field of that tool's tools: entry ... selected by the role's tools: list; a standalone skill's — one no tool claims — has no such home and composes as a path-framed head text block" — implying a tool-claimed skill (message, dispatch) should NOT be independently visible as text/schema when its tool isn't in the role's tools: list. The `descriptions/**` snapshot the model can `bash`-inspect directly contradicts that "two wire homes" rule by making the tool-claimed descriptor visible on disk regardless of role selection — it's simply a different mechanism (raw directory snapshot for provenance/reproducibility) that happens to be reachable by `bash` and misleads exactly as if it were composed into context.

## Layer at fault
lernie's context-assembly / Descriptions-always design (ARCH.md §3.3), pinned crate `lernie = "=0.0.2"`. Not the model, not yog.

## Suggested fix direction
Pick one, non-exclusive:
1. Give every agent a cheap, role-scoped ground truth it CAN read from its own worktree — e.g. commit a filtered/derived `descriptions/tools/` (or a manifest) containing only the role's actually-granted tools, so bash exploration and the wire tools: array agree.
2. Alternatively (or additionally), have the harness commit the resolved role's `tools:` list itself (a small derived file, e.g. `role.json` or similar) into the agent's own worktree at dispatch time, so an agent asked "why can't you do X" can answer from its own branch instead of guessing from an incomplete/misleading descriptions/ snapshot.
3. Document, in the message/dispatch SKILL.md bodies themselves, the caveat that presence of a schema in descriptions/ does not imply the tool is callable — the ground truth is the wire tools: array only, cross-checked at the model's own next call attempt.

Whichever direction, the goal is dissolving the edge case rather than patching around it: today the agent has strictly more filesystem visibility than it has actual capability, and no signal that distinguishes the two.
