Round 1, lane comparator. Driven against an isolated engine (yog 0.0.38, main tip; own XDG roots; wire on 127.0.0.1 with a lane port), worker role on `claude-session-direct` / `claude-sonnet-4-6`.

Gesture and reply:

    yog gesture --ws W --agent A "/revoke"
    {"kind":"floored","ok":true,"standing":true}

Then, with the floor standing:

    yog gesture --ws W --agent A "/message Run the bash command `echo ADJUDICATED` now."
    {"exit":0,"kind":"outcome","ok":true,"stderr":"","stdout":""}

25 s later the conversation is `quiescent`, `refused:false`, nothing held, and
the transcript tail reads:

    model | [{"id":"toolu_…","input":"{\"command\":\"echo ADJUDICATED\"}","kind":"tool-use","name":"bash"}]
    tool-result | None
    model | [{"kind":"text","text":"The command ran successfully and output:\n\n```\nADJUDICATED\n```"}]

Repeated once with `echo SECOND` — same result. `/attention` shows no held
call; `/agent` never entered a held state.

Expected, from `yog gesture --help /revoke` verbatim:

  "Stops letting the selected conversation act on its own: from its next tool
  call, everything but a read waits for you — the same park a held call already
  makes, applied to all of them. … It covers the conversation and everything
  below it, including children it has not spawned yet."

`bash` is not a read, so the call should have parked and waited for `/answer`.
It did not.

Severity p2: the gesture answers ok and reports the floor standing, so an
operator has positive confirmation of a guarantee that is not in force. That is
worse than a refusal — the whole point of /revoke is the moment you no longer
trust the conversation, and it is exactly then that the acknowledgement is
false. Not p1 only because a workaround exists (`/stop`), and because the
adjudication path itself demonstrably works elsewhere in the suite.

Where to look: the boundary writes the floor (kind `floored`), but the control
that classifies a call is litany`s; the defect may be that the floor mark is
written somewhere the control never reads, or that it is read at a step
boundary the already-running loop had passed. Note the neighbouring open ball
bl-72bd, which is the same family one layer out (a routed shell on a foot is
classified by name and passes the destructive floor).

DRIVEN against a scratch engine (own XDG roots, lane port 7753) with a real
step, worker on claude-session-direct / claude-sonnet-4-6. The premise does not
hold: the floor DOES bind at the next tool call.

Reproduced the ball exactly. /revoke -> {"kind":"floored","ok":true,
"standing":true}; then a message asking for `echo ADJUDICATED`; 25 s later the
transcript carries the tool_use, a tool_result of exit 0, and the model's
summary. Nothing held.

Then, with the SAME floor still standing and nothing else changed, one more
message asking for `mkdir -p /tmp/<probe>`:

    /attention -> "held": {"reason": "bash {\"command\":\"mkdir -p
    /tmp/<probe>\"} classified open-world (`mkdir` reaches /tmp/<probe>,
    outside the writable root)", "tool": "bash", "tool_use": "toolu_..."},
    "says": "came to rest - your turn; parked a tool invocation for your
    answer", "signals": ["stopped","held"]

and the directory does not exist. So the mechanism is sound end to end: the
gesture's row, the fold, the classifier and the park.

What actually happened is that `echo` classifies as a READ. The effect
vocabulary classifies invocations, never tool names (VISION 4.11 item 1) --
which is the whole reason `bash` cannot carry one class -- and the floor raises
every class ABOVE read, which is what /revoke's help already promised
("everything but a read waits for you"). echo, ls and cat are reads whatever
tool runs them.

The real defect is legibility, and that is what this ball fixes: an operator
reads "a read" as a kind of TOOL. The help now says a read is what the call
does, that bash running ls/cat/echo still runs, and that the same bash writing
outside its worktree, reaching the network or touching credentials parks. Both
directions are regressions now -- one unit beat over the fold, one end-to-end
through the seeded shim.

Note for the neighbouring bl-72bd: `find <path> -delete` was ALSO classified a
read before that ball, so its drive had two holes, not one.
