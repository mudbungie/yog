Follow-up to bl-71ee (delivered as commit 824ef59). That fix cured the atomic-rename .tmp leak (coalesces_atomic_rename_to_destination now GREEN on macos-14, CI run 29622456319) but REGRESSED fs_watcher::tests::detects_removal_under_summary on macos-14 (232 passed, 1 failed). Linux stayed green; the whole rename family is green on both.

FALSE PREMISE. bl-71ee's diagnosis asserted "a genuine deletion still carries a Remove event." CI disproves it. bl-71ee reframed classify to key on EventKind::Remove: `Remove(_) => Removed; _ if exists => Touched; _ => None`, over `latest[path]` (the LAST coalesced event). On macOS FSEvents, `fs::remove_file` on a file created before the watch armed yields a per-path coalesced event whose flags include CREATED|REMOVED; notify's translate_flags emits multiple events and the LAST one for the vanished path is NOT the Remove. So classify saw a non-Remove kind on an absent path and returned None -> the removal was dropped -> `.expect("event")` panicked at tests.rs:144. (Same class of bug bl-71ee fixed for the rename source — keying on the LAST event — but in the opposite direction.)

CORRECT DISCRIMINATOR. Absence alone can't separate the two vanished-path cases; the distinguishing history is HOW the path left: an atomic-rename source received a rename (Modify(Name(_))) event (Linux From, macOS Any) and the destination survives; a genuine deletion received NO rename event. And existence is ground truth for the current state. So classify on (renamed?, exists?), aggregating `renamed` across ALL of the path's events in the tick (macOS appends a trailing Modify(Data) after the Name, so last-event keying misses it):

    // in coalesce: track per-path `renamed` = saw any Modify(Name(_)), OR-folded
    fn classify(renamed: bool, path: &Path) -> Option<ChangeKind> {
        if path.exists() {
            Some(ChangeKind::Touched)          // present now: Touched, whatever the history
        } else if renamed {
            None                               // gone via rename: the .tmp source, dropped
        } else {
            Some(ChangeKind::Removed)          // gone, not renamed: a genuine deletion
        }
    }

This dissolves BOTH special cases (the Remove arm AND the rename-departure branch) into one existence+renamed decision, and does not depend on whether macOS emits a Remove for a delete — only on the established facts that a rename source always carries a Name event and a delete never does.
