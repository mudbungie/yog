Seen at least four times on 2026-08-14 (the bl-8626, bl-1ce0, bl-4841 and bl-b4b5-adjacent gates): the GitHub Actions leg runs the whole suite green and then tarpaulin reports being signaled mid-run, exiting non-zero. The gate stores that as a FAIL verdict keyed by tree, so a re-run answers 'fail — chain stops' from cache without rebuilding, and the close pays the local gate. Every affected close was green locally at 100% coverage, so the verdict is always a false negative. Likely class: runner memory/OOM or the runner's process supervision signaling tarpaulin (it is the longest, heaviest step). First moves: capture the runner's dmesg/oom evidence in the workflow on tarpaulin failure; consider retry-once-on-signal in scripts/speculate-gate (retry ONLY the signaled class, never a real test failure); check whether a stored FAIL of this class should be evictable so a clean re-run is not blocked by cache. Verify against the tree; this body drifts.

---

Upstream ask (balls), recorded rather than filed — the one half of this defect yog cannot close. `speculate_run::build` returns `status.success()` and its caller writes `Verdict { pass }` from that unconditionally, so a gate command has exactly TWO answers and an infrastructure death has to borrow one of them: exit 0 vouches for an unproven tree, anything else stores a FAIL that stops the candidate chain forever without rebuilding. What is missing is a third — a reserved exit code meaning "no verdict, record nothing" — which would leave the (tree, gate) key absent, and absence is a miss and therefore a rebuild. yog already spells that 75 (EX_TEMPFAIL) at the gate and the speculate workflow honors it, because the workflow decides for itself whether to record; the local driver cannot, because the verdict is written after the gate has exited. Until upstream reserves a code, scripts/speculate-gate rebuilds once when a run comes home with no verdict at all, and two consecutive infrastructure deaths still store a FAIL.
