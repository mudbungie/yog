The advertised direct namespaces do not receive the composed world.

Literal help:

`Run balls' own verb surface in this process, against the world's store and landing.`

`Run lernie's own verb surface in this process, against the nested world.`

The architecture says: `yog reads the ambient environment once, computes its data-root anchor, and composes one world Env — the ambient snapshot plus a fixed override set — used both to derive every substrate path yog reads and to spawn every child.`

With synthetic ambient roots, direct `yog bl prime` and `yog bl create` write beneath `/home/u/ambient-state/balls`; the exported world path `/home/u/data/yog/world/state/balls` remains absent, and `/board` cannot see the task. Direct `yog lernie prime` similarly writes beneath ambient `LERNIE_HOME`, not `/home/u/data/yog/world/lernie`.

`yog exec bl ...` and `yog exec lernie ...` use the promised nested world and are the workaround.

Cause: argv dispatch reaches the linked crates before world composition. The current integration tests encode the ambient behavior even though help and DESIGN require the nested behavior. Closed bl-ea39 only injected the world into spawned children; it does not cover in-process multiplex arms.

Acceptance: every non-discovery bare `yog bl` and `yog lernie` operation reaches the same nested state as `yog exec`; conflicting ambient substrate state remains untouched; explicit mark inheritance and already-composed re-entry remain intact; help and version probes remain world-free and write nothing. One command spelling must not silently operate on a different task and agent universe.
