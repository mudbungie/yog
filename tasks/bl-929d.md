Operator design ruling 2026-08-03, verbatim: 'I think the user input should be overhauled to be the inbox. You type, you're typing into the inbox. Other items that are coming in: you see them land in the inbox above your text input. There is a horizontal rule that goes up to see more items pile in, or the user types enough to push it up (anything but the user input gets a fold arrow, ofc), and then when the prompt goes out, it snaps back down, making it clear that the input was pushed "over the line" into the prompt. Also, since that's a commit boundary, that line, such as it is, should persist, these lines (faint, gray, with a commit id on the right side) should persist through the entire chat.'

Decomposed:
1. The composer IS the inbox view. Typing composes an inbox item; other arriving items (agent messages, deposits) visibly land in the same surface, above the text input.
2. A horizontal rule is the fold line between 'already chat' and 'pending inbox'. It rises as items pile in or as the user's typing grows. Every pending item EXCEPT the user's own input gets a fold arrow.
3. On send, the rule snaps back down: everything above it was pushed 'over the line' into the prompt. The gesture makes the commit visible.
4. Send is a commit boundary, so the line persists: faint gray rules with the commit id on the right side, one per boundary, through the entire chat history.

This is a DESIGN ball (bl-50f3 pattern): the deliverable is the DESIGN amendment recording the contract, plus the implementation balls it files. Design constraints to honor and check against:
- Derivation discipline: the persistent boundary rules must derive from the commit spine the transcript already reads (the step/dispatch commits) — no stored UI fact; the commit id shown is the real commit. Relate to bl-98da (V1 Historian: the step spine is a commit spine) without merging scopes.
- Single source: 'the inbox' is lernie's inbox (deposits, flushed on scan). Decide precisely what the composer-as-inbox claims: is the typed draft literally an inbox deposit (a lernie fact) or a yog-side draft that joins the same visual queue? Whichever, one home for each fact; no second inbox representation that can drift.
- Builds on bl-c038 (composer docked in the conversation pane, commit 85e569d) and the per-target drafts model. The in-flight strip's seat (DESIGN pins it between chat tail and the composer's seat) must be re-ruled or preserved explicitly.
- UI/backend isolation: the frame renders snapshots; item arrival must not add frame-time work.
- Boundary discipline: if new gestures result, they land as variants first (control boundary, bl-8aab).
