Operator report 2026-08-21: a sent message shows as a visible DUPLICATE in the
inbox-composer queue for ~1s — the faded echo row and the solid real-deposit
row for the same message coexist. Wanted: one row, in place — faded before the
deposit hits disk, solid after, never two.

## Verified mechanism (2026-08-21)

The duplicate is structural, two uncorrelated clocks:

- `src/app/echo/seat.rs:52-59` `echoed_pending()` appends the echo to the
  fresh inbox answer UNCONDITIONALLY — no dedup. Same in the snapshot fold:
  `src/app/echo.rs:249` `agent.pending.push(echo.deposit())` (the ✉n badge
  double-counts too).
- For a follow-up message the deposit file already exists BEFORE the echo is
  minted: the §8.2 message verb is piped and run to completion
  (`src/actions/verbs.rs:82-98`), and the echo is minted only on the wire
  receipt (`src/shell/acting.rs:219-222`, §9.8 ruling 3;
  `src/app/focus.rs:101-109`).
- The REAL row arrives fast: `Query::Inbox` re-reads `inbox/<agent>/` fresh at
  answer time (`src/boundary/answer.rs:151`), refreshed on the asker's 500ms
  `ASK_PERIOD` (`src/wire/asker.rs:50`).
- The ECHO retires slow: `Echo::landed` (`src/app/echo.rs:126-130`) fires only
  when a whole-workspace derivation bumps the `messages/` NNN counter past the
  mint-time baseline — behind BRIDGE_POLL 50ms (`src/watch/mod.rs:54`) +
  DEBOUNCE 100ms (`src/app/dirty.rs:31`) + WORKER_POLL 25ms
  (`src/app/derive/worker.rs:31`) + the full re-derivation pass (DESIGN:98-102
  concedes a real workspace's pass cannot finish inside 2s), and the deposit
  only reaches `messages/` at the driver's next step boundary anyway.
- So from the first fresh inbox answer until derivation catches up, the queue
  holds two rows with the same body: one solid (`tone_of`,
  `src/composer/mod.rs:113-124`: real file → Plain) and one faded (echo →
  Weak). The fold line also sits one row too high for the duration
  (`src/composer/mod.rs:29-35`).

## The promise being broken

DESIGN §7.2 (~2597-2611) already rules the wanted behavior: "A pending echo is
*visibly* pending … brightens to full strength the instant the derivation
carries it. Brightening is that same row at full strength, not a repaint into
different hues." Appending a second row and later deleting the first violates
that. §11 (~5700-5710) words the queue echo as standing in for "a message
whose deposit has not been flushed" — once the inbox file exists and paints,
the echo stands in for something the seat already shows.

## The change

For the QUEUE seat (and the fold's `pending` push): the echo must yield to the
real deposit the moment the seat can show it — never two rows for one message.

Design guidance (implementer decides the exact key, then amends §7.2 to record
it — see constraints):
- §7.2 (~2579-2589) forbids text matching and conflated proxies
  (`last_action_unix`, `tip_oid`) for the LANDED predicate. The queue needs a
  second, narrower reconciliation: "the deposit I stand for is now in the
  inbox answer." A count high-water over the inbox listing, baselined at the
  moment the act is queued (enter time — before the verb runs and writes the
  file; receipt time is too late, the file already exists), is the same
  count-not-text philosophy applied to the inbox seat. Carrying the baseline
  on `Owes::Message` (`src/shell/acting.rs:113-131`) is one shape.
- Retiring the echo's QUEUE seat is separate from retiring the echo itself:
  the §3.4 focus-claim/landed predicate (`adopt_started`,
  `src/app/focus.rs:126-138`) stays on the messages/ counter per §7.2's
  "landing and the claim are one event".
- The ✉n badge and fold-line height follow automatically once the fold stops
  double-pushing.
