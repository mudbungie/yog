Measured on main (f20db947, bl-e6c9's landing) and in a claim worktree: 5 runs
per side of `cargo test --lib git_env::write_exec::tests::a_child` gave 1
failure on each. It is not lane-specific — every `bl close` in this repo runs
the whole suite twice (hook + coverage), so it will redden gates at random.

    thread '...a_child_that_cannot_write_is_reported_with_the_path'
    panicked at src/git_env/write_exec.rs:117:9: Broken pipe (os error 32)

The beat asserts the error names the path and says "sh exited"; what it got
was the raw EPIPE. The child is `sh -c 'cat > "$1" && chmod 755 "$1"'` with a
path whose parent directory does not exist, so `cat` fails and closes the read
end IMMEDIATELY. Whether the parent's `write_all` of the body lands before
that close is a scheduler race: win it and the child's status and stderr come
back as designed, lose it and the write's own error is returned instead.

The fix is not a timing one. A broken pipe on the way in means the child is
gone, so the honest answer is to stop treating the write's error as the
outcome: wait for the child regardless and report its status and captured
stderr, falling back to the write error only if the child exited cleanly. That
makes the two orderings one answer instead of two.

Filed from lane Y9; not touched there because `write_exec` is bl-e6c9's own
landing from tonight.
