DESIGN §7.2/§7.3, found by the §11-rule sweep (bl-7dca).

`Cadence` (`src/app/cadence.rs`) reads three bases out of `cadence.yaml` and
derives every period from them — `wound_grace`, `late_pass`, the
stale-snapshot threshold, the I4 poll floor. §7.2 says outright that each
derived period *"follows the tuning"* so no reader has to know the arithmetic.

**No reply carries any of them.** Grep `src/boundary/` for `Cadence`: nothing.
The bases are reachable only as raw text through `Query::ReadConfig`
(`ConfigFile::Cadence`), so a seat that wants a derived period must re-implement
`Cadence`'s arithmetic against a YAML file it also has to parse — two
implementations of one derivation, which is the drift this document exists to
prevent.

It bites hardest on **`wound_grace`** (bl-90bf, bl-18e8). The tree already
rules the gate is the seat's (`src/fixture.rs`: *"`wound_grace` is the seat's,
not the server's. The window left with bl-7942 and `WoundGrace` has had no
consumer in this crate since; what yog serves is the wound itself"*), and
`src/wire.rs` states why the server must still be able to say the number:
*"the §7.3 wound grace is the sum of every leg a fact crosses before a seat can
see it, and the last of those legs is the ask. A server that did not name the
period could not state the grace, and would raise the alarm the grace exists to
prevent."* Both are right and together they are the defect: the server computes
the number, the seat needs the number, and nothing hands it over. So today
either every seat hard-codes a window (which a `cadence.yaml` edit silently
falsifies) or every seat flashes a red no-response banner on healthy sends —
the exact alarm bl-90bf closed.

`src/app/grace.rs` / `crate::app::WoundGrace` is 100%-covered code with no
consumer, in the same class as bl-7cc8's residue.

Candidate shapes, not a foregone answer: a `cadence` object on the
`Query::Workspaces` answer beside `derived_at_unix` and the growth note (the
read every seat already makes at `ASK_PERIOD`, and where the staleness line
already rides); or a `Query::Cadence` of its own; or the wound carrying its own
"believe me after" stamp so the seat needs no period at all — which is the only
shape that also removes the arithmetic from the seat.

Whichever lands, amend DESIGN §7.2 (the periods paragraph) and §7.3 (the
bl-90bf row) to name the carrier, and decide `WoundGrace`'s fate with it.

---

**Arm taken: (a)'s destination, reached by making the engine apply the grace. (b) was never licensed.**

**Step (a), verified against the tree: NO, the engine did not apply it.** `boundary::answer::inspector::transcript` folds `steps_view::latest_wound` with no clock and no age; `steps_view::build`'s only gate was `wound::driven(state)`, and that `state` comes off the *published snapshot* (`state_of(snap, ..)`) while the disk half is read fresh at the ask. So the bl-90bf TOCTOU survived the seat's departure intact — the false wound window was still the full `wound_grace` (~17.6 s on the default cadence) after every send.

**Step (b) was NOT licensed, because its precondition is false.** It reads "*Only if the seat genuinely must wait a period on its own*". The seat does not have to: a stateless per-ask server can judge the window itself, given an anchor that is a fact about the world rather than about an observer's first sight. That anchor already existed — the step's own `request.json` mtime, which litany writes immediately before it invokes the model and which §5.1 #28 already reads as `call_start_unix`. So `steps_view::build` takes the caller's clock and the live cadence's window and states a no-response wound only once the step has outlived it. The wound crosses **already-judged**, `src/app/grace.rs`/`WoundGrace` is deleted, no `Query::Cadence` was added, and no reply gained a field.

Also, a "believe me after" stamp anchored on anything the *server re-derives* does not work: `derived_at_unix` advances every full sweep (15 s) while the grace is 17.6 s, so the stamp stays permanently ahead of now and the wound never paints. The anchor has to be the step's own start, and once it is the step's own start the server can just make the comparison.

**Two premises of the ball are dead.** "**No reply carries any of them**" is only true of `wound_grace`. `late_pass` is consumed by the derivation worker's own drift row and no seat wants it; `stale_after` is consumed at the boundary (`answer::chrome::workspaces`) and its verdict already crosses as the `stale` label. Neither was ever a carrier defect. And `wound_grace` itself was *already* applied server-side on the other surface that uses it — `opslog::launch::stillborn(&trees, entry, now, grace)` in `app::derive::fetch::refresh_ops` judges a dead launch before the ops row crosses. This change makes the wound do what the ops row already did, which is why it is one rule in one place rather than a new mechanism.

**What the change costs.** bl-90bf's "only the banner is graced, not the Steps-tab row" clause is reversed: a server has one answer, and which surface paints it is a view (§8.5 — views never cross), so a wound that is not yet believable is a false definite in a table cell exactly as in a banner (§10). Recorded in DESIGN §7.3's row.

**One latent defect found and fixed on the way:** `fixture::lay` wrote `request.json` and never stamped it, so every laid conversation read as a call that started at the instant of the lay. That already falsified §5.1 #28's `call_start_unix` for fixture worlds, and under this change it would have made the `wound` state answer no wound at all for the whole of the grace. The request's mtime is now stamped from the recipe's offsets beside the response's.

Amended: DESIGN §7.2 (the periods paragraph — every derived period is spent on this side), §7.3 (the bl-90bf row), the sweep ledger row, and the §12 rows for `app/cadence.rs`, `steps_view`, and `fixture` (the `app/grace.rs` row is gone). `src/wire.rs`'s `ASK_PERIOD` sentence STAYS and is stronger: the server must know the seat's poll period to compute the window it now waits out.
