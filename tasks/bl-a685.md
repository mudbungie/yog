## Symptom

The first conversation on a fresh server is granted eight tools, none of which
this world can run, and it spends a whole turn discovering that one refusal at
a time.

Driven live on a scratch world — one workspace, one goal ("add one line to a
README"), no enrolled foot:

```
model  → read_file            → Exit code: 1 … no tool of that name is loaded …
model  → clients              → (none is registered here)
model  → bash                 → Exit code: 1 … no tool of that name is loaded …
model  → clients              → (none is registered here)
model  → bash                 → Exit code: 1 …
model  → apply_patch          → Exit code: 1 …
model  → "the tools are not loaded … This appears to be a configuration issue"
```

Five refused calls, seven round trips, ~92k tokens, and a conversation that
ends having done nothing. The workspace's own config says the tools are there:

```yaml
roles:
  worker:
    tools: [apply_patch, bash, cd, dispatch, load_skill, message, multi_tool, read_file]
```

and so does the world — `<world>/litany/tools/` holds all eight descriptions
and `<world>/litany/skills/` all eight skill files. Every one of them is
unrunnable, because since the four-component split (bl-37fd) **tools follow the
client** (REMOTE §5) and this server has no foot enrolled.

## This is not the refusal's fault

The per-call refusal is genuinely good — it names the tool, says no machine
advertises it, points at the `clients` tool and names the remedy (enrol a
thrall with `subject_cwd` on that entry). The model even followed it and found
the empty client list. The defect is upstream of the refusal: **the grant is a
promise the world cannot keep, and nothing says so before the goal is fired.**

## There is already a rung for exactly this shape

`start::gate` (DESIGN §8.1) exists because of this operator ruling, quoted in
its own header:

> *"On a wall holding no usable provider credential, typing a goal and hitting
> Enter will work zero percent of the time — the conversation is born,
> immediately dies on no-models, and the operator learns it from a dead row (or
> from nothing at all). The pane is inviting the one act that cannot succeed
> while hiding the one act that must come first."*

Word for word the same situation, one input over: a wall with no reachable tool
cannot do work, the operator learns it from a dead conversation, and the act
that must come first (`/enroll <name> foot`) is not offered. The gate is a pure
read of a table the frame already holds; the client roster `/clients` answers
is the same kind of table.

## Repro

    # fresh world, one workspace, no /enroll, a signed-in provider row
    /prepare dir <repo>  →  /prompt "edit a file"
    # every tool call refuses; the conversation ends having done nothing

## Two halves, and the second is the smaller one

- **The warning.** A start whose role grants tools into a workspace with no
  advertising client is the credential gate's shape, and its remedy sentence is
  one line (`/enroll <name> foot`, then run thrall there).
- **The grant.** The shipped `roles.worker.tools` list is litany's install seed,
  held in step with litany's own tool pool by a test upstream. On a yog world it
  now names eight tools no local executor will ever serve. Whether the seed
  should still name them — the grant is what makes a *routed* tool of that name
  callable once a foot advertises it — is the ruling this ball wants; if it
  should, then the pool's presence is not the problem and only the warning is.
