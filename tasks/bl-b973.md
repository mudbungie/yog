Deploy the post-severance containerized yog server to the deployment box, crossing the wire-v1 line and the engine fence in one maintenance window (operator ruling: publish and cut over together so latest misaligns only for a moment). **LANDED 2026-08-30, as a container.**

**The serving path is the image, and the unit runs it.** `make image` built `yog:<version>` from the tip (`d43a228a`) under the pinned toolchain; `image-scan` passed both directions. The image travelled by `save | ssh … load` and nothing was pushed to any registry (DESIGN §10.1: a push is not undoable, and there is no push target to forget to guard). On the box it is retagged `yog:<version>-<short-commit>` and the unit names *that* — an immutable tag, never a moving `latest`, so the deployment can say what it is running.

The unit was rewritten in place. Its `ExecStart` had been `yog serve`, a verb that stopped naming anything at bl-7942, so it was stale whichever path this took. It is now a `docker run` unit and implements the README's mount contract exactly: **one mount** — the box's real data root at `/state/yog`, the image's `XDG_DATA_HOME=/state` supplying XDG's extra level — plus a mounted work dir for §8.1's bare-rung cwd. Host networking, because the listener binds what `wire/address` names and a bridge namespace does not hold that address. `--user`, because the mount is the operator's own files and must stay so. A git identity by environment, because the image ships none and yog's substrate commits. `ExecStop=docker stop -t 30`, because DESIGN §8.5's grace is only spent if SIGTERM reaches PID 1 *inside* the container. `Restart=always` with a ~100 s retry window, which is the only ordering a user unit can have against a system-level container daemon.

**The world scrap kept nothing, because there was nothing to keep.** The ruling protects every wall's `brazen/` — and this box held **no walls at all**: no walls directory under the world, and no brazen config, credentials or cache anywhere on it. The provider registrations the keep-list exists for were never there, so the migration half of the ruling was vacuous and is recorded here rather than assumed. Deleted: the pre-fence engine home (the `lernie`-era harness root, the fence's `LITANY_HOME` rename), the nested state root, the tool shims, and both named workspaces. No retired dir existed. `wire/` was not touched.

**The registry was read off and re-seated, and that is the one subtlety.** REMOTE §4.1's registrations are files under the *state* root the scrap deletes, while the certificates they scope are the material the ruling keeps — so a plain scrap would have kept every seat's identity and silently de-scoped it. The four `(client, workspace)` pairs were enumerated before the delete and re-created after: one empty file each, which is the whole of a registration. One client's advertised-tool document was deliberately **not** restored — an advertisement is the tool host's own to write on its next connect, and restoring it would have published a claim no live host had made.

**Insurance first.** A zstd tarball of the entire pre-fence data root sits at `~/yog-prefence-<box>-<date>.tar.zst` on the box, sha256 recorded in the drive report. It is never to be deleted.

**Verified over the real wire, from a second box, on the kept trust root and the kept client leaf.** A `workspaces` query answered `ok` with an empty row set — correct, the workspaces were scrapped — and a workspace-named query answered in band with `unknown workspace`, which is the engine answering rather than the channel failing. Both were re-run after `systemctl restart` and after the container was destroyed out from under the unit, which the unit recovered from on its own.

**The hourly reconciler is disabled, deliberately.** It reconciles a *cargo-installed binary* against the registry and reads quiescence off the unit's own cgroup; against a container unit both facts are wrong, and its restart arm would fight the container. The old binary is left installed and is not running — the only `yog` process on the box is the container's.

**A foot leaf was minted for the dev box's thrall** on the deployment box's own CA (`WIRE_FOOT=1`, so `OU=foot` — advertise and execute only), carried by hand over the ssh channel as REMOTE §1.4 requires, placed as a §8.2 entry on that box, registered, and its private key destroyed on the server. Installing the thrall itself is another ball's.

**Follow-up, filed (bl-c6e2):** the repo's `scripts/deploy/` path still seats a binary unit, so `make deploy HOST=…` would overwrite this container unit. The previous unit is kept beside it with a `.prefence-bak` suffix. **Not tested:** a reboot.
