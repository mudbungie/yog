## Clock design questions (moved here from retracted lernie bl-36a2)

1. **Where cadence lives.** Per-role cadences (demo: shepherd 1m, sensor 2m) — in the workspace's governing config commit (lernie stores, yog reads and derives its timers), or in yog's own config? The config-commit answer keeps one authoritative home for fleet control facts; yog derives, never stores a second copy.
2. **Cost discipline.** Fleet README: *"Each watcher cycle costs at least one model call, and revives the coordinator"* — ≥2 calls per cycle minimum. Make idle cycles cheap or skippable rather than reproducing cron's unconditional fire.
3. **Liveness while yog is closed.** The cron gap's sting was silence (*"a fleet whose cron is not installed is a fleet whose watchers never wake, and nothing in the harness notices"*). yog-as-clock inherits a variant: the fleet ticks only while yog runs. Accept as the operating model (fleet lives with the operator's session), or surface it loudly (e.g. 'watchers N cycles overdue' on bring-up)?
4. **Rendering.** Per-watcher last-wake/next-wake on the operator surface — now native yog state, no cross-harness derivation needed.
