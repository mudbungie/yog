Follow-on from the operator ruling on bl-dd1d (2026-08-13): `balls/tasks` is
scrubbed and published rather than moved to a private remote. A one-time scrub
is a treadmill without a standing guard — the task log grows every day, and
nothing scans it.

`scripts/leak-scan.sh` (bl-167d) scans the yog worktree's INDEX. The task store
is a different repo entirely (`$XDG_STATE_HOME/balls/clones/<enc>/tasks`),
written by `bl`, never touched by yog's pre-commit hook. Ball bodies are
exactly the prose that leaks: transcript quotes, other people's names, machine
state, provider auth state, operator home paths.

Two pieces:

1. **A gate on store commits.** Run the same rule table (`scripts/leak-rules.sh`)
   over `tasks/` and refuse the commit that trips it. Where it hangs is a design
   question, not a given — a balls plugin on the `close.pre`/`update` schedule,
   or a CI check on the published ref. Pick the one that cannot be bypassed by
   the agent writing the ball, and say why.
2. **A stated rule in AGENTS.md** for what may never enter a ball body: other
   people's names and addresses, verbatim transcript prose, live machine state
   (pids, load, paths under a real `$HOME`), provider auth state, conversation
   ids. The maintainer's own `mudbungie` identity is explicitly permitted —
   that ruling is recorded on bl-dd1d.

Do not couple this to bl-dd1d's one-time scrub: that ball is a migration, this
one is a recurring gate, and the migration should not wait on it.

---

## Where it hangs, and why there

**The store gate is a balls plugin at `<op>.post`** (`scripts/yog-leak-gate`),
prepended ahead of `bl-tracker` on every op the landing runs the tracker on
(`create update claim unclaim close drop`).

Three placements were available. The choice was forced by one question: is
there a moment when the ball exists and has not been published?

1. **`<op>.pre`** — rejected on fact, not preference. A `pre` plugin runs
   BEFORE `bl` writes the task file, so it scans the previous state and waves
   through the very body being added.
2. **A git hook inside the store clone** — rejected. Hooks are untracked and
   per-clone; the clone is disposable state `bl prime` re-founds, so the gate
   would be absent on every other checkout and silently absent after the next
   re-clone. Nothing in yog source can install it there, and yog must never
   write into another agent's live clone.
3. **`<op>.post`, before the tracker** — taken. The store commit is sealed and
   nothing has left the box: the tracker is the only plugin that talks to a
   remote and it runs later in the same ordered list, and a non-zero exit is
   the protocol's abort — the op is refused and prior plugins roll back in
   reverse, un-sealing the commit. That is the one window between written and
   published, so that is where prevention has to live.

It reuses the rule table rather than restating it. `scripts/leak-scan.sh` now
resolves `leak-rules.sh` from its OWN directory instead of the git root, so the
same script and the same table judge yog's index and the store's; the plugin is
dispatch around it, and there is no second definition of what counts as a leak.

## What it catches

Every mechanical rule, applied to `tasks/*.md`: home paths under any account on
any platform, addresses outside the reserved documentation space (the
maintainer's own excepted, per the ruling on bl-dd1d), speaker-labelled
transcript, vendor session and resource ids, credential assignments, tokens,
private keys, routable addresses, and content no rule can read. It reads INDEX
BLOBS, so a body edited on disk after staging is judged by what would publish.

## What it provably cannot catch

- **A determined author.** `bl conf remove <op>.post yog-leak-gate`, or a hand
  `git commit`/`git push` in the store clone, and it is gone — exactly as
  `--no-verify` defeats the source hook. There is no unbypassable PREVENTIVE
  placement to move it to. GitHub cannot interpose a check on a direct push to
  a branch: there is no pull request to require a status check on, and a
  server-side hook is not a repo artifact — the same boundary bl-167d drew for
  protected refs.
- **Prose.** An unlabelled paragraph of somebody's conversation, or a third
  party named in ordinary writing, reads as writing. No regex reaches it. That
  is the half AGENTS.md now states as a rule, and it is the half that actually
  leaked: the audit recovered no credential of any kind, only private context.
- **History.** The gate and the workflow both see only the tip.

So the remote half is `.github/workflows/store-scan.yml` — the only check the
agent writing the ball cannot switch off. It cannot be a push trigger on the
task branch: for a push event GitHub resolves workflows from the pushed ref's
OWN tree, and that ref holds task files and nothing else, because `bl` writes
nothing else. It therefore runs daily, on dispatch, and whenever the rule table
changes, and it DETECTS rather than prevents — by then the material is on the
remote and the remedy is a rewrite. Prevention local and bypassable,
enforcement remote and late: stating that is worth more than a gate that
implies otherwise.

## Wiring is not this ball's act

The plugin schedule lives in the balls landing, not in yog's tree, so the
delivery ships the gate and AGENTS.md ships the two-line wiring. **It must not
be wired until the scrub lands:** the store tip trips the home-path rule on
nine live task files today, bl-dd1d among them (it cites the paths as
evidence), so wiring first would refuse every `bl` op on the box — the scrub's
own edits included.

Tested in `tests/leak_store_gate.rs`: seven tests driving the real plugin over
throwaway stores, with the scanner's own fixtures as the probe material.
