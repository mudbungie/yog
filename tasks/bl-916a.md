Discovered by bl-2f30's agent (landed `b5c27fb`) with a **demonstrated, reproduced failure** — this is not theoretical.

## What happened

The agent ran a plain `git commit` inside its `work/bl-2f30` worktree. That fired `.githooks/pre-commit` → tarpaulin → the test suite. Git exports `GIT_DIR`/`GIT_INDEX_FILE` into every hook it runs, and **something in the suite forked git without the scrub**, committing `config: init [config/default]` **onto `work/bl-2f30` itself** — replacing the whole tree. Every source file went untracked; a stray `providers.yaml` appeared.

Recovered with `git reset --mixed 67903fa` (working files survived untracked) and re-committed with `--no-verify`. Nothing was lost, but a work branch was genuinely corrupted by running the repo's own gate.

## Why bl-0dff did not already fix this

bl-0dff (`83db523`) fixed the scrub for yog's **own** git forks: it created `src/git_env.rs` (`INHERITED` + `command()`), made it the crate's only `git` constructor, and deleted six copy-pasted scrub lists. That work is sound and holds — verified 2026-07-29: `grep -rn 'Command::new("git")' src tests` returns **exactly one hit**, `src/git_env.rs:37`. There is no stray direct git fork left.

So the leak is elsewhere. The prime suspect, unconfirmed: **the environment handed to spawned child binaries.** Tests drive `bl`, `lernie`, the `$EDITOR` shim and fake binaries as subprocesses; those children run git internally, and they inherit the ambient `GIT_DIR`/`GIT_INDEX_FILE` unless the spawn site scrubs the env it passes down. `src/git_env::command()` scrubs the env of a `git` process yog forks directly — it does nothing for a `bl` child that forks git of its own accord.

Note `tests/multiplex_bl.rs` and `tests/multiplex_lernie.rs` already recognized this class: they scrub their **own process env** by importing `yog::git_env::INHERITED`, precisely because they drive balls/lernie in-process. That is the same hazard, solved for two files by hand. If the fix belongs anywhere general, it is at the spawn boundary, not in each test.

## Scope

1. **Find the actual culprit.** Reproduce it: from a work worktree, `GIT_DIR=$(git rev-parse --git-dir) GIT_INDEX_FILE=$(git rev-parse --git-dir)/index cargo test`, and identify which test writes to the outer repo. bl-0dff's own repro idiom and its non-vacuity technique (temporarily delete the scrub, confirm the test fails) are the model.
2. **Fix it at the boundary, not per-site.** Six copies of the scrub list is exactly the drift bl-0dff just deleted; do not reintroduce it as six spawn sites each remembering to scrub. If child spawns need a scrubbed env, that belongs in the one place children are spawned (see `src/cli_outbound`, `src/start`, and the test spawn helpers) — one invariant, per AGENTS.md.
3. **Regression test it**, non-vacuously.

## Operating note for agents until this is fixed

`git commit` inside a `work/<id>` worktree is UNSAFE — it runs the hook, which runs the suite, which can write to the outer repo. Commit with `--no-verify` and let `bl close` run the gate. **`bl close` itself is unaffected**: it invokes the hook directly rather than through `git commit`, so no `GIT_DIR` is exported. This is worth stating in AGENTS.md as part of the fix.
