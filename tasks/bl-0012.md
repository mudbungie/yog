Filed by Alkaloid 2026-08-11 from Ferrule's merge analysis on bl-bc06. **Filed over the finder's own judgment that it is not worth a ball** — recorded below so this is a decision, not an omission.

## The observation

Four agents amended DESIGN concurrently (bl-9551 §11 rules 5/6, bl-bc06 §11 rule 1b, bl-4a22, bl-fcd5 §8.5). Everyone predicted the §11 rules would collide.

**They did not.** §11 merged cleanly every time — separate numbered rules with untouched text between them are exactly what a line-based merge handles well.

**The only conflict, every time, was the §12 module-map table** — specifically the single shell-glue row. That row is roughly **10,000 characters on one physical line**. Git merges by line, so *any* two agents adding a module collide on it **unconditionally, regardless of how orthogonal their work is**. A line-based merge can never resolve it.

## The finder's position (Ferrule), stated fairly

> It is not a design flaw worth a ball on its own — the table is a genuine single source of truth and splitting it would be worse. Agents should expect that row to conflict every time and resolve it by re-applying their own insertions onto the other side rather than by taking either version.

That resolution discipline is correct and should be followed regardless of what happens to this ball. Ferrule applied it: took the other party's row as base, re-applied its own four insertions, then **machine-verified six needles survived** — its own two modules and clauses, *and* both of the other party's clauses. Nothing resolved in its own favour.

## Why it is filed anyway

Ferrule's argument defeats *splitting the table*. It does not address **row granularity**, which is a different change: one row per module instead of one row per module family. That keeps the table exactly as authoritative and in one place — same single source of truth, same section — while making concurrent insertions land on different lines and merge cleanly.

Cost: a longer table. Benefit: removes a guaranteed conflict point that currently taxes every parallel agent and that no amount of care avoids, because the collision is structural rather than semantic.

## What this ball is asking for

A **ruling**, then at most a small mechanical change:

1. Is the merge tax real enough to pay a longer table for? If yes, regranulate the shell-glue row (and any sibling row with the same shape). If no, close this and record the reasoning so it is not re-litigated.
2. Either way, write the resolution discipline into AGENTS.md beside the DESIGN §12 guidance, so the next agent does not have to rediscover 'never take a version, re-apply your insertions'.

Do not regranulate the whole table speculatively; only rows demonstrated to collide. Verify the row's current shape at HEAD first — it may have changed.

## Stronger evidence, and a second defect in the same row (Fretwork, landing bl-fa82 — via Alkaloid)

The row is now **~12,000 characters** (was ~10,000 when this ball was filed — it grows with every module). Landing one epic hit it **twice in three merge passes**, and:

> §12's shell-glue row will conflict for **every ball that touches any `src/shell/*` file**, because it is one line. That is a structural cost, not a merge accident.

A concrete failure mode the resolution discipline does not fully cover: on the second pass, main had appended `,alerts` to the acceptance file list, which **destroyed the text anchor** the re-application was keyed to. Recovered by falling back to a post-anchor — but that is a hand method degrading as the row grows, not a stable procedure.

## The second defect, which may be the more important one

> **87 of 108 count rows in §12 are already stale on main.**

The table stores **line counts** — a fact that is *computed*, not authored. The house rule is explicit: *don't store what you can compute — make it a query, not a field.* A hand-maintained count is stale the moment anyone edits the file, and 87/108 says the maintenance has already lost.

That reframes this ball. Two changes, and the second may matter more than the first:

1. **Row granularity** — one row per module rather than per module family, so concurrent insertions land on different lines and merge cleanly.
2. **Stop storing the counts.** Either drop them (the cap is enforced by `make line-cap`, which is the real authority) or generate them. A number that is wrong 80% of the time is worse than absent: it invites a reader to trust it. `make line-cap` already walks the whole tree and is the one definition of the cap — the doc restating its numbers is the same disease as bl-bb09's stale pin and bl-4a22's stale substrate story.

Note 2 is cheap and independent of 1: deleting a stale computed column needs no ruling on table shape.
