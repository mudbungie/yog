Operator report 2026-08-03, verbatim: 'the current binary that I'm getting out of make run doesn't use the latest logo, the 45 degree one' (the latest mark: tangent circles on pinned arcs, bl-f60e commit 030fcfc).

Anchors from a quick read (VERIFY all of this against the tree — do not trust it):
- Makefile comments: the freedesktop seats are the launcher entry + hicolor theme PNGs (INSTALL_THEME); 'Icon=yog' matches the window's app_id (src/main.rs) 'or a running window gets a generic icon'. So on the desktop, the window/launcher icon can come from the INSTALLED icon set, not the binary — 'make run' rebuilds the binary but installs nothing, so a stale installed hicolor set keeps showing an old mark forever.
- The runtime path claims single-source: src/main.rs:132 sets the window icon 'from the same orb table assets/yog.svg is emitted from' (src/theme/icon). Diagnose which surface the operator is actually seeing (window decoration? taskbar/dock? launcher?) and why it is stale: uninstalled new PNGs, icon-cache staleness, Wayland app_id path ignoring the set_window_icon, or the orb table itself not carrying the 45-degree change.
- make icon re-emits the install set; close.post auto-install (scripts/bl-install-main) runs make install on ball closes — check whether that installs icons and whether it ran since 030cfc/030fcfc.

Fix per the severability/single-source instinct: whatever surface is stale, the mark must have one home (the orb table) and every seat (embedded window icon, installed PNGs, SVG) must derive from it, with staleness impossible or loudly detected — e.g. install refreshes the icon theme cache, or a check that the checked-in/install set matches the generator output. Do not add a second icon home. Record the resolution in DESIGN where the icon pipeline is documented.
