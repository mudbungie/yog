A real run through the offered Ollama provider reached local inference and could not produce one useful agent turn: `{"type":"usage","input_tokens":4095,"output_tokens":1}` then `{"type":"finish","reason":"length"}`, one thinking delta generated, no text and no tool call, on a model whose own context is 262144 and which supports tools.

## Where the 4K comes from — verified

The request declares no context size at all. brazen's `ollama_chat` encoder maps `max_tokens` onto `options.num_predict` and emits no `options.num_ctx`, so the Ollama server's own runtime default governs every turn — not the model's capacity, and not the `context_window` the picker declares in `models.yaml` (which reaches no request; it is only yog's own fullness denominator).

Measured, not read: `tests/brazen_ollama_context.rs` drives the LINKED brazen through `brazen::run` with a capturing `Transport` — no network, no server — against the built-in `ollama` row, with one canonical request carrying a tool and `max_tokens: 4096` (lernie's own per-call cap). The captured body is `{"model":…,"messages":…,"tools":…,"options":{"num_predict":4096},"stream":true}`.

The escape hatch does not compose, and that is the sharper half. `encode` inserts the typed `options` object FIRST and folds config passthrough with a shallow `or_insert` on the top-level key, so a row carrying `body_defaults = { options = { num_ctx = N } }` has that object dropped WHOLE and silently whenever any typed generation scalar is set — and lernie always sets `max_tokens`. Test leg two asserts exactly that.

One config-only route does work at the pin (test leg three): `unsupported_body_keys = ["max_tokens"]` plus `body_defaults = { options = { num_ctx = …, num_predict = … } }` yields `"options":{"num_ctx":32768,"num_predict":2048}`. It is lossy (the output cap must be restated inside the object) and fragile (`stop` cannot be cleared the same way — `strip_unsupported` never touches the typed `stop`), which is why it is offered as an operator remedy and not written by yog.

## What landed

No guessed default, and no provider row authored by yog. yog cannot see what the server was started with, so a refusal would refuse a correctly-raised server on the strength of an unanswered question — the same discipline `is_unknown_row` applies to an unanswerable table. So:

- `ProviderRow::context_caveat` beside `tools_blocked` in the new `src/config_edit/brazen/providers/capability.rs` — the same total match over brazen's public `ProtocolId`, answering for `ollama_chat` only, and `CONTEXT_REMEDY` carrying the two config lines.
- The picker states it and does NOT gate on it: `plan` writes the pick (asserted), and the row stays selectable with the caveat above it and the remedy on its hover (`src/shell/model_pick/select/notes.rs`, split off `select.rs` at the cap on the says-versus-chooses seam).
- `tests/brazen_ollama_context.rs` — the three legs above, so the caveat is true because a test says so and reddens the day brazen changes, naming what to delete.
- DESIGN §9.4 amended (the caveat is stated, not gated, and why), §12 rows for both new files.

## Upstream

The seam is brazen bl-f19d: either a first-class context declaration each dialect projects where it has a slot, or a config passthrough that merges one level into a same-named object the encoder already built. Filed with the three measurements and with a second finding beside it — `unsupported_body_keys = ["stop"]` is inert for the typed `stop`, which the built-in `claude-code` row already declares.

Not closed by this ball, and not yog's to close: until bl-f19d lands, a yog turn on an ollama row runs at whatever the server was started with. The acceptance line "the wire request contains the intended context size" is reachable today only through the operator's own config, which is what the remedy hands them.

Follow-up filed as bl-d9cb: lernie 0.0.10 retired the `models:` table (its bl-35e2), so the `models.yaml` half yog writes is inert at the pin and its `context_window` can only ever be yog's own denominator.
