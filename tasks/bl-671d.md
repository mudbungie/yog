A real run through the offered Ollama provider reached local inference but could not produce one useful agent turn.

The selected model reports `context length 262144` and supports tools. The persisted response was:

`{"type":"usage","input_tokens":4095,"output_tokens":1}`

followed by:

`{"type":"finish","reason":"length"}`

The only generated token was a thinking delta; no text, tool call, or project change followed. The canonical request carried nine yog/lernie tools and `max_tokens:4096`.

Source inspection explains the exact 4K boundary. Brazen maps `max_tokens` to Ollama `options.num_predict`, but never supplies `options.num_ctx`. Ollama therefore runs at its smaller runtime context despite the model capacity. The declared `models.yaml context_window` is currently only the UI denominator; it does not shape this request. Closed bl-848f corrected how that declaration is seeded and is not a runtime fix.

Impact: the built-in local-provider route can be selected, contacted, and shown as healthy, yet the platform tool and instruction payload itself consumes the whole runtime context before the model can act.

Required outcome: carry one authoritative context declaration into the actual Ollama request, including room for both prompt and output, or make a provider-level nested `options.num_ctx` compose with the typed `options` fields. Do not add a second guessed default. The required upstream brazen seam must be tracked rather than hard-coding a parallel protocol table in yog.

Acceptance: a real Ollama drive asserts a non-length terminal turn with the standard injected toolset; the wire request contains the intended context size; output-token and context limits remain distinct; an explicit smaller operator value still wins; unsupported or unavailable size discovery is stated rather than fabricated.
