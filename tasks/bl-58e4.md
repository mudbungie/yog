**The clarification is the specification.** This is one band moving, not a
stack inversion.

## The four named elements are exactly one band

Work directory, budget, context, model selection = `src/shell/settings.rs`,
whose own doc names its contents:

    //! The conversation's **settings rows** (§11 bottom accessories, bl-2e18):
    //! the config-shaped rows of altitude 1, docked at the bottom of the
    //! conversation pane beside the composer.
    …
    //! what the conversation *runs on* — the §9.4 model line and the §3.5
    //! budget-spent figures — reads where the operator talks to it

plus the §11 birth-config block it seats on an empty selection, which carries
the work directory.

## The stack today

`src/shell/pane.rs` builds the conversation-scoped bottom stack. egui's inner
panels stack **outermost-first**, so code order is the reverse of screen order.
Top to bottom today:

    transcript text
    flight strip          (innermost — bl-905f)
    settings rows         ← the four elements, on the wrong side
    start-composer        (the §3.4 goal box, when a start is pending)
    outbox + composer     (outermost — the pane's bottom edge)

## Wanted

    transcript text
    flight strip          (UNCHANGED)
    [start-composer]      (see below)
    outbox + composer
    settings rows         ← moved below the input box

## What must NOT move

- **The flight strip.** It is not among the four named elements, and its seat
  is itself an operator ruling, recorded verbatim in
  `src/shell/flight_strip.rs`:

      //! the inference status at the top is good, but I want to see in-flight
      //! call characteristics at the bottom of the screen while it's going.
      //! something so that if I'm looking down at the chat, I'll see that it's
      //! working.

  Moving it below the input is exactly what that ruling forbids. **bl-905f
  survives untouched.**

- **The outbox.** It is the §11 inbox-composer queue
  (`src/shell/inbox_queue.rs`): *"the pending deposits above the typed draft,
  under the derived fold line"* — already inside the composer panel, above the
  draft box, not a sibling band. The operator named it as the exception so it
  would not be swept below with the chrome. On this reading it needs no change
  at all.

- **bl-c038** — *"the chat line belongs in the conversation box, not across the
  entire bottom"*. The stack stays inside the pane.

## What this supersedes

**bl-2e18's ordering clause only**: *"between the goal box and the in-flight
strip, so what the conversation runs on reads beside where the operator talks
to it."* That rationale is what the new order overrides, and it must be amended
where it lives (the `settings.rs` module doc and DESIGN §11) rather than
silently reordered around — per AGENTS.md, "don't implement a deviation: fix the
doc".

bl-2e18's *other* recorded ruling — 2026-08-11, *"Move all the settings for a
conversation to the bottom, instead of the top"* — **still stands**. These rows
stay at the bottom of the pane; they move only to the far side of the input box.

## The one open judgement

`start-composer` (the §3.4 goal box) is not among the four named elements, and
it is a second **text input**, not chrome. Default: it stays adjacent to the
composer rather than going below with the settings. Rule on it explicitly and
say why; do not leave it implicit in a panel order nobody can read back.

## Constraints

- The budget discipline stays: each band asks `crate::layout::share` for its
  share first and paints nothing when the answer is `None`, *"the composer
  included, with no special case: a pane that cannot seat a row of it has
  nothing to type into either."* Reordering must not turn that into a special
  case — check what a starved pane now drops first and whether that is still
  the right thing to drop.
- The settings seat is bounded at half the pane (the fold line's own ceiling,
  §11 inbox-composer) because the §9.4 picker expands inline and an
  over-subscribed bottom stack is the QUALITY G4 defect bl-9551 filed. Two
  half-pane-capped bands now sit on the same side of the input; verify the
  stack still cannot eat the transcript.

## Acceptance

Assert the geometry on the composed frame, at more than one window size — this
surface has a history of being correct at one size and broken at another
(bl-7414 on narrow-tall, bl-5410 at 420x320 and 800x500). The load-bearing
assertion is that the settings band's `top()` is below the composer's
`bottom()`, and that the flight strip is still above the composer.

Note the existing assertion at `src/shell/acceptance/inbox_composer.rs:292`:

    assert!(
        strip.bottom() <= composer.top() + 1.0,
        "the strip sits above the fold line: strip {} !≤ composer {}",

It stays TRUE under the corrected order, so it is not the test that changes —
which means it would not have caught this defect either. Add one that would
have.
