Operator ruling, 2026-08-12, verbatim:

> chat prompt input should be closest to the text, everything else below it,
> except the outbox we just talked about

## The stack today, and why it is backwards

`src/shell/pane.rs` builds the conversation-scoped bottom stack. egui's inner
panels stack **outermost-first**, so the code order is the reverse of the
reading order. Top to bottom on screen today:

    transcript text
    flight strip          (innermost — "hard against the chat tail", bl-905f)
    settings rows         (bl-2e18)
    start-composer        (the §3.4 goal box, when a start is pending)
    composer + outbox     (outermost — the pane's bottom edge)

So the chat prompt input is the thing **furthest** from the text, with three
bands of chrome wedged between them. The ruling inverts that.

The code's own comment states the current intent, verbatim
(`src/shell/pane.rs`):

    // Inner panels stack outermost-first, exactly as the window-level ones do:
    // the goal box at the pane's bottom edge, then the settings rows (bl-2e18),
    // then the in-flight strip innermost, hard against the chat tail (bl-905f),
    // then the remainder is the conversation.

## What is wanted

    transcript text
    outbox + composer     ← innermost, hard against the text
    everything else       ← below it

## Reading the "except the outbox" clause

The outbox is the §11 inbox-composer queue (`src/shell/inbox_queue.rs`), whose
own doc already places it *"the pending deposits above the typed draft, under
the derived fold line"* — it is inside the composer panel, riding above the
draft box, not a sibling band.

**So the clause is read as: the outbox stays attached to the composer, above the
draft, exactly where it now is.** It is named as an exception because it is the
one thing that legitimately sits between the text and the input, and the
implementer must not "fix" it down below along with the other chrome. On this
reading the outbox needs no change at all — the whole edit is the panel order.

If the operator meant instead that the outbox should become its own band
*between* the transcript and the composer, that is a different (larger) change;
raise it rather than guessing, but do not block on it — the reading above is the
one to build.

## The rulings this supersedes

Three prior operator rulings are recorded in the code and are contradicted by
this one. Do not silently reorder around them — amend them where they live, per
AGENTS.md ("Nothing is set in stone. […] don't implement a deviation: fix the
doc").

- **bl-905f** — the flight strip sits *"innermost, hard against the chat tail"*.
  Under the new order the composer is what is hard against the tail. Decide
  where the strip goes and say why: it is a live-activity indicator, so "below
  the input with the rest of the chrome" may cost it its glanceability. State
  the call.
- **bl-2e18** — the settings rows sit *"between the goal box and the in-flight
  strip, so what the conversation runs on reads beside where the operator talks
  to it"*. That rationale is precisely what the new order overrides.
- **bl-c038** — *"the chat line belongs in the conversation box, not across the
  entire bottom"*. This one **survives** and must not be disturbed: the stack
  stays inside the pane.

DESIGN §11 carries the altitude-1 layout and must be amended to state the new
order and the reason, not just the code.

## The start-composer question

`start-composer` (the §3.4 goal box) is the one band the operator sizes, and it
is a *second* input. "Everything else below" reads as chrome, and a second text
box is not obviously chrome. Rule on whether the goal box goes below the chat
input with the rest, or pairs with it. Say which and why; do not leave it
implicit in a panel order nobody can read back.

## Constraints

- The budget discipline stays: each band asks `crate::layout::share` for its
  share first and paints nothing when the answer is `None`, *"the composer
  included, with no special case: a pane that cannot seat a row of it has
  nothing to type into either."* Reordering must not turn that into a special
  case — if the composer is now innermost, check what a starved pane drops
  first and whether that is still the right thing to drop.
- No stored heights and no draggable boundary for the fold line (§11 rule 3).
  The outbox's height IS its content.

## Acceptance

Assert the geometry on the composed frame, at more than one window size — this
surface has a history of being correct at one size and broken at another
(bl-7414 on narrow-tall, bl-5410 on 420x320 and 800x500). At minimum:
`composer.top()` is below `transcript.bottom()` with no other panel between
them, and every other band's `top()` is below `composer.bottom()`.

Note the existing assertion at `src/shell/acceptance/inbox_composer.rs:292`
encodes the OLD order and will invert:

    assert!(
        strip.bottom() <= composer.top() + 1.0,
        "the strip sits above the fold line: strip {} !≤ composer {}",

Change it deliberately, not incidentally, and make sure whatever replaces it
would have caught the old layout.
