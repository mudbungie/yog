Seen on the 0.0.6 release. `release-binaries` resolves which tag to build with `git describe --tags --abbrev=0` over its own checkout, and that checkout's fetch raced the tag the job it `needs:` had just pushed. The step logged `Note: switching to 'refs/tags/v0.0.5'` seconds after v0.0.6 was tagged, so the job built the PREVIOUS version and uploaded it — over the previous release's own asset. The new release got no binary at all until a `workflow_dispatch` with `binaries_tag` backfilled it.

Two failures, and the quiet one is worse:

- **The new release ships no binary.** Loud, and the workflow's own documented backfill (`workflow_dispatch` with `binaries_tag`) fixes it — which is how 0.0.6's archive got attached.
- **The previous release's asset is REPLACED.** Silent. Here it was replaced by a rebuild of its own tag, so the bytes are equivalent and nothing is lost; that is luck, not the mechanism. The upload action overwrites by name, and the job had every permission it needed to do it.

`git describe` is the wrong question. The tag is an OUTPUT of the job this one already `needs:` — `release-plz-action` reports what it released — so the binaries job should take the tag as data from that output and refuse to run when it is empty, rather than re-deriving it from a checkout whose freshness it does not control. The `binaries_tag` dispatch input stays exactly as it is: it is the backfill path, and it is already the shape the fix wants (the tag arrives as data, in the environment, never spliced).

A guard is worth having beside it: the resolved tag must match the version in the `Cargo.toml` it is about to build, or the job refuses. That is the check that turns this class from "uploaded the wrong thing" into "said no".

Do not treat the dispatch backfill as the fix. It is the remedy for a run that already went wrong, and it needs a human to notice — which on 0.0.6 happened only because someone was watching the release through.
