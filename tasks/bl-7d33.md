Round 2, lane comparator. yog main at 5cd95986 (`cargo build --release`, `yog 0.0.48`), litany pinned `=0.0.10`, brazen pinned `=0.0.14`, fresh isolated world, engine on 127.0.0.1:7776.

## The gesture

    yog wire-certs                      # fresh world
    yog                                 # engine up
    P=$(yog gesture --ws w '/prepare dir <a git dir>' | jq -c .prepared)
    yog gesture --ws w '/config brazen <a config with a credentialled row>'
    yog gesture --ws w '/model worker <provider> <model>'
    yog gesture --ws w --prepared "$P" '/prompt Implement …'

`/prompt` answers `{"conversation":"CoolAvocado","kind":"started","ok":true}` and the conversation is dead on arrival. `/ops` carries the reason, verbatim:

    litany prompt: role "worker" grants tool "clients", which its governing
    config commit does not describe — no descriptions/tools/clients.json
    (ARCH §3.3 descriptions-always); described tools: apply_patch, bash, cd,
    dispatch, load_skill, message, python, read_file, search_history

`/lineages` confirms it: the default lineage holds `descriptions/tools/*.json` for those nine names and no `clients.json`, while `providers.yaml` reads

    roles:
      worker:
        tools: [apply_patch, bash, cd, dispatch, load_skill, message, python, read_file, search_history, clients]

This reproduced on every workspace tried — three fresh ones, two providers.

## Why

bl-0460 (872ccf54) made birth assert `clients` into `roles.worker.tools` at every prepare. The `clients` tool is yog's, injected over litany's `ToolInjection` seam at prompt time — but the pinned litany (0.0.10) checks the GRANT against the governing config commit's `descriptions/` before any injection is consulted, and refuses a granted name it cannot describe. Nothing on the lineage describes `clients`, so litany refuses the run.

bl-0460's own close note records what was verified — "a brand-new workspace and an EXISTING one both carry clients in the worker grant after one prepare" — and that is exactly the assertion that holds. No `/prompt` was fired after it, so the refusal was never seen.

## Severity

p1, and it is the whole product: a `yog` built from main today cannot start a conversation at all. Every lane driving main is blocked behind it.

## Expected

`/prompt` starts. Either birth authors `descriptions/tools/clients.json` on the lineage in the same config pass that asserts the grant (the grant and its description are one fact and must move together), or the grant is not asserted until the description exists.

## Note on the pin

bl-ebef (pin litany `=0.0.11`, brazen `=0.0.17`) may or may not dissolve this — litany 0.0.11's `BUILTIN_TOOLS` gains `remember`, not `clients`, and `clients` is not litany's tool in either version, so the descriptions-always check has the same input. Whichever way it lands, it needs a live `/prompt` to say so, not a `/roles` read.

## Workaround used by this lane

Capture the prepared body, rewrite `providers.yaml` on the lineage with `clients` removed, then fire `/prompt --prepared` with the captured body — birth does not re-assert between the two acts. Conversations then start and run normally on both a claude row and a gpt row.
