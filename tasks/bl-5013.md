A standing design principle from the operator, 2026-07-27. Not a defect — the
rule future UI work is measured against. Its home is `docs/DESIGN.md` §11
(which already has a "Glyph coverage" paragraph from bl-24d3, so this sits
beside it); the deliverable is writing it there.

## The ruling, verbatim

> glyphs: I don't mind using them. I like glyphs, but use them like colors in
> accessible UI: they are visual organizing data for interface elements that are
> otherwise clear. You don't add a glyph so you don't have to say the state. you
> add a glyph so the state is glancewise-clear. please use as many glyphs as are
> appropriate, just don't assume they are clear unless they are _extremely_
> clear.

## What it means, concretely

**The colour analogy is the whole rule.** In accessible UI, colour is never the
only carrier of meaning — remove it and the interface still reads. Glyphs get
the same treatment: remove every glyph and the surface must still say what it
means. The glyph makes it *fast*, not *possible*.

So the test for any glyph is: **is the state still legible with the glyph
deleted?** If not, the glyph is carrying meaning it should not be carrying, and
the fix is to say the state — then add the glyph back on top for the glance.

**Volume is not the constraint.** "as many glyphs as are appropriate" — this is
not a call to strip them. yog's existing vocabulary (`● ◐ ○ ■ ⚑ ⚠ ▶ ★ ⚙ ✔ ✖`)
is wanted. It is the *load* on each one that is capped.

**"Extremely clear" is a high bar and it is not the author's judgement.** The
author of a glyph always finds it obvious; they chose it. `●` for Live and `◐`
for InFlight are legible **once you know**, which is not the same thing.
Assume a first-time reader with no legend.

## Where this bites today (audit, do not assume)

- `src/theme/mod.rs` `state_badge` — `●` Live, `◐` InFlight, `○`, `■` Stopped.
  These are the primary "is this running" signal on every §11 conversation row,
  and the row currently carries **no text** for the state. Under this rule the
  state should be sayable — a hover text at minimum, and consider whether the
  row has space to say it outright.
- `src/shell/conv_ball.rs` — `◈` ball badges and group headers.
- `⚑` attention counts, `⚠` failures, `?` uncertainty (§10), `⋯` overflow,
  `▶`/`▼` folds, `★` pin, `⚙` config, `✔`/`✖` good/error in the transcript and
  steps view.

For each: what does a reader who has never seen yog understand from the glyph
alone, and is the state recoverable without it?

## Related

bl-24d3 (landed, `cc4db2d`) fixed glyph *coverage* — the font question, which is
orthogonal. Its guard (`tests/glyph_coverage.rs`) asserts glyphs RENDER. This
ball is about whether they should be doing the work they are doing. A glyph can
render perfectly and still be a legibility bug.
