Split from bl-e492, which made the `linux` job green for the first time in this
repository's history. The `macos` job was red in the same run and in all 30 runs
before it, for causes bl-e492 does not touch.

**It is on the release path.** `.github/workflows/release-plz.yml:154-155` gates
the publish on the CI *workflow run*, not on a job:

    github.event_name == 'workflow_run' &&
    github.event.workflow_run.conclusion == 'success'

A workflow run concludes `success` only when every job does, so while `macos` is
red, no version of yog can be released by the pipeline — 0.0.2 included.

**It is a claim the README makes.** README.md:392-393:

    `make ci` on Linux (fmt-check, clippy `-D warnings`, tarpaulin 100% floor)
    and `cargo build` + `make test` on macOS (Apple silicon).

That sentence is false today and has never been true. Whatever is decided below,
it must end up saying what is so.

**Root cause 1 — six delete tests assume the Linux liveness probe.**
`app::tests::deletes::the_unmaking_removes_the_wall_moves_the_focus_and_leaves_the_trail`
(src/app/tests/deletes.rs:106) unwraps `Err("refused — live conversations: hi")`;
`app::tests::agent_deletes::a_declined_verb_rides_back_its_stderr_verbatim`
(src/app/tests/agent_deletes.rs:147) gets `"refused — live: c-1 — stop them
first"` where it expects the substrate's words. The other four are the same
shape. This is not a surprise — DESIGN.md:4221 already says it:

    - **The gap:** both probes scan `/proc/<pid>/fd` (Linux-only). The fix:

and DESIGN.md:4249 documents what yog does on macOS instead. The fixtures were
written against the Linux answer, so on macOS the gate refuses and the tests
read the refusal as the product misbehaving.

**Root cause 2 — six shell-acceptance tests lay text out differently.**
`src/shell/acceptance/unfold/drive.rs:95` fails three of them with

    the frame paints "20260803T04…", which reads as more than one row's title

so a column that seats a full title on Linux elides on macOS; and
`src/shell/acceptance/bands.rs:139` fails with `which bands each size seats has
changed`, at all four window sizes (420x320, 800x500, 1150x760, 2560x1700).
`inbox_composer.rs:285` is the sixth.

The obvious explanation is wrong and should not be chased: the harness builds
`egui::Context::default()` and never calls `theme::apply`, so both platforms get
egui's OWN embedded faces (theme::mod.rs:187 `fonts()` starts from
`FontDefinitions::default()`), which are identical bytes. The width difference
comes from somewhere else — a rounding difference on aarch64, a
`pixels_per_point` default, or a tessellation setting — and wants measuring, not
guessing. Print the galley widths on both runners before touching anything.

**The decision this ball carries.** Three ways, and it is an operator call
because two of them change a published support claim:

1. Make macOS green. Honest, keeps the claim, unknown cost — root cause 2 has
   no diagnosis yet and each CI round trip is ~15 minutes.
2. Move macOS to its own workflow (a name other than `CI`). The release then
   gates on the platform that is actually green, macOS stays visible and
   tracked, and README:392-393 is amended to say macOS is not gating. Small,
   severable, and honest.
3. Drop macOS entirely and say so in the README. Subtractive, and defensible if
   nobody runs yog there — but DESIGN already carries macOS-specific behaviour,
   so this throws away work that exists.

Recommended: 2, then 1 on its own clock.
