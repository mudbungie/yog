On this drive a conversation built a working two-file program in its bound
working directory — the files are there, the test passes, the CLI runs — and
NOTHING at the control boundary can see any of it.

    /files      → 22 rows: descriptions/skills/*, descriptions/tools/*,
                  goal.md, name, soul.md. Neither work product.
    /work-diff  → {"rows": []}

The operator's only way to the deliverable is to already know the host path and
look outside yog.

## Why /files answers that way

`/files` reads the **agent branch worktree**
(`<workspaces>/<ws>/agents/<agent-id>/`). The conversation's tool cwd is the
path rung's binding — a directory outside litany's agent branch — seeded as the
`--cwd` mark at creation (DESIGN §3.3). Two different directories; the read
looks at the one with no work in it.

The help page promises the other one:

> The agent's own worktree read-only: goal, soul, summaries, skills and
> **whatever work products it has written**, as a sorted listing with each
> entry's size.

For a path-rung conversation that clause is false of every conversation, always.
And absence is not named: the reply is a normal listing, not a statement that
this conversation's work products live somewhere this read does not reach —
which is QUALITY H2 ("a fact yog cannot derive is answered as absent and never
as a zero") applied to a listing rather than a field.

`/work-diff` is honest by its own page — it is per-BALL, over the project
repository's work branches — so it is not lying, but it is the only other read
an operator would try, and between the two of them the boundary has no answer to
"what did this conversation build".

DESIGN §3.3 already names the underlying limit and calls it verified:

> Edits at the target still land in balls' external project worktree, outside
> litany's agent branch, commit-per-side-effect history, child inheritance,
> bundle, and replay. That is the verified two-Git limit

…and rules that per-step observed project OIDs join project commits to agent
history by pointer (bl-2b8c, VISION §4.10). Nothing on the read side spends that
pointer yet, so the limit is invisible where the operator meets it.

## Shape of the repro

    yog gesture --ws <ws> '/prepare dir <dir>'      # <dir> a git checkout
    …fire a goal that writes a file there…
    ls <dir>                                        # the file is there
    yog gesture --ws <ws> --agent <name> '/files'   # it is not
    yog gesture --ws <ws> --agent <name> '/work-diff'  # rows: []

## What would settle it

Either the path-rung binding becomes a read at the boundary (a listing of the
bound directory, or the §4.10 project-OID pointer spent into a diff), or `/files`
says outright that this conversation's work target is elsewhere and names it.
The one answer that is not acceptable is the present one: a promise of work
products and a listing with none, with nothing said.
