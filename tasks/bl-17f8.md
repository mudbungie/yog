LANDED. The foot and the seat are installed on this laptop, enrolled against the box's own engine, and the whole loop was driven end to end on one machine.

INSTALLED, each from its own source tree with `cargo install --path <repo> --locked`:

- **thrall 0.0.1** — the foot.
- **lernie 0.1.0** — the seat, the 0.1.0 side of the version fence (REMOTE §12).
- **yog 0.0.5** — the UI-free server. `yog --help` lists no window and no `serve`, which is bl-7942 landed: one face, and the verb gone with the second one it named.

**One install trap, and it is the fence made physical.** A `lernie` **0.0.10** binary — the OLD engine, from the era that name has retired into `litany` — was seated in the user's bin directory, which precedes the cargo bin directory on this box's PATH. A freshly installed seat was therefore invisible: `lernie --version` kept answering `0.0.10`, from a program that is no longer called lernie at all. The stale binary was moved out of PATH. Every box that ran the old engine meets this on upgrade, and the version fence is the only thing that names it — a `lernie` answering `0.0.x` is not an old seat, it is a different program.

**Debris, not a defect, but it held the port.** Two orphaned engine processes from a deleted worktree of an already-closed ball were still bound to the wire's loopback port forty minutes after the tool call that started them had timed out. They were stopped by exact pid. The current binary's `--version` prints and exits, verified twice, so what those processes are is the residue of an intermediate build — worth knowing only because an abandoned engine keeps the port and goes on deriving the same world.

THE ENGINE. The local world had been scrapped with its walls kept, so the boot seeded fresh — state root re-derived, existing loopback material taken as it stood, nothing re-minted (the mint is idempotent by construction). A workspace was founded through the boundary by a bare `/prepare`, which is §4.1's raise founding a name that did not exist. No bootstrap verb was needed and none exists.

THE FOOT, enrolled as the two-sided act §4.2 and §8.2 describe.

- **Host half.** `WIRE_FOOT=1` beside `WIRE_LEAF=<name>` on `yog wire-certs` issued a leaf whose subject reads `OU=foot, CN=<name>`. The grade is written into the certificate by the operator's own CA, in one act, out of channel — presence-shaped, with no word to mistype into a demotion.
- **Client half.** That pair plus the anchors were carried by hand into the foot's own data root as one channel directory under `wire/workspaces/`, beside an `address` file naming the engine. thrall mints nothing; there is no bootstrap flow and there must never be one.
- **Registration.** One `mkdir -p` and one `touch` under the engine's state root. That is §4.1's entire management surface — no gesture manages registrations and none was added.

THE TOOL DOCUMENT, authored deliberately rather than copied. Two entries, each with an explicit `cwd`, and the `cwd` is a scratch directory belonging to the foot rather than any checkout:

- **`shell`** — one command line, run by `sh -c`.
- **`read_file`** — one file's bytes.

Each entry's `command` is an argv naming a small operator-written executable that takes the invocation's `tool_use.input` JSON on stdin and answers with stdout, stderr and an exit code — §5.2's contract exactly. The shell lives inside that script's own body, never between thrall and the argv: thrall interpolates nothing, which is what keeps a declared schema from becoming advisory. Nothing else is enabled, and a third capability is a third entry in a file on this box — the severability the arrangement rests on.

THE LOOP, PROVEN. The first exercise of all the parts at once: a gesture asks, the server routes, the foot executes, the seat reads what came back. Driven from the seat CLI, over an §8.2 entry, on real mTLS:

- `{"op":"clients"}` — the foot present, both tools with their schemas and descriptions.
- `{"op":"invoke", …, "tool":"shell", "input":{"command":"…"}}` — `{"invocation":"inv-3","kind":"routed","ok":true}`.
- `{"op":"capture","invocation":"inv-3"}` — `exit_code: 0`, `stderr` empty, and `stdout` carrying the three lines the command actually printed on this laptop, the last of them the working directory the entry declared.

The same pair ran for `read_file` and returned a file's bytes. A name the foot does not advertise refuses in band, at the ask: *client "…" advertises no tool "…" right now*. **Zero model spend** — the routing leg is fully exercised by the operator's own `invoke` and `capture`, with no agent, no driver and no provider anywhere in the path.

THE FOOT GRADE BITES. §4.2's raise, exercised on real material for the first time. The same foot leaf was placed as a **seat's** channel and made to ask and to act. Four gestures, four refusals, one sentence — in band, naming the grade, and not absent-shaped:

    this certificate is a foot: it may advertise its tools, take the invocations
    addressed to it and complete them, and nothing else. An operator-grade
    certificate is what the rest of the boundary needs.

`workspaces` and `clients` are the asks; `nudge` is an act; `invoke` is the fourth of §5.3's verbs, the asking side — the one a foot is invoked *by* and may never send. The raise sits ahead of the dispatch and ahead of the create's auto-registration, so none of the four founded or seated anything.

THE SEAT. An operator-grade leaf was minted and registered the same way, and placed as an §8.2 entry naming the workspace. `lernie entries` lists it with its address without dialling it; a `workspaces` ask over that entry answers with the workspace's row; and the window opens against it — launched, observed holding an established connection to the engine on that entry's own material, then closed with SIGTERM, exiting 143. A bounded run; nothing graphical was left up.

TWO DEFECTS FILED, both in the seat's own store, neither blocking anything above:
