## Operator complaint (2026-08-01, verbatim)

'I need a way to clear the log. Or at least make the failed notification go away.'

## Verified code facts (verify again before editing)

- Banner: `AppModel::last_failure(origin)` (src/app/balls.rs:65) = newest ops row of that origin, iff failed. Painted per-frame by `failure_banner` (src/shell/mod.rs) on the originating surface (bl-48f8). It clears ONLY when a newer successful op of the same origin lands — an operator who doesn't retry stares at it forever. No dismiss exists.
- Chip: `activity · N ops · M failed ⚠` (src/shell/activity.rs), ichor whenever failed>0. Counts derive from the whole `ops.jsonl` tail; the file is append-only and never rewritten (src/opslog/mod.rs §4.2), so a failed count never goes to zero. No clear exists.

## Design (the log stays the single source of truth — no second state home)

**1. Dismiss = an acknowledgment that is itself an ops line.** The operator dismissing failures is an action with an outcome, so it belongs in the action log like every other action: append an ack line (a synthetic op — reuse the existing synthetic-line machinery/exit-sentinel vocabulary in src/opslog/mod.rs; it needs a distinct, documented shape). Semantics: **a global seen-watermark** — every failure-derived alarm (each surface banner, the chip's ichor + failed count) considers only rows AFTER the newest ack line. One line shape, no per-origin variants: dismissing from anywhere means 'I have seen what's on screen now.' Derivation change is small and pure: `last_failure` ignores rows at-or-before the ack; the chip's error count likewise (decide + document whether the drift count is also ack-quieted — drift is an alarm about the watch layer, likely YES quieted the same way, but check §7.2's intent). The expanded trail still shows ALL rows including acked failures and the ack row itself — ack quiets alarms, never hides history.

**2. Clear trail = an explicit verb in the expanded ops pane.** Starts a fresh trail: truncate `ops.jsonl` and immediately append an op line recording the clear itself (the new trail's first row is 'trail cleared' — the action is logged like any action). Truncation is safe against the other instance's O_APPEND appends (writes land at the new EOF) and against the reader (stateless re-read). Check DESIGN §4.2's durability language first: if it forbids destruction outright, amend it to carve out this deliberate operator action — the durability promise is about yog never *losing* outcomes, not about forbidding the operator from discarding their own history.

**UI affordance:** a dismiss control on the failure banner and/or the ops-pane header, and the clear verb inside the expanded pane (destructive-ish: keep it out of one-misclick reach; follow §11 conventions and bl-68ac's hover-explanation ruling — every control explains itself on hover). Pin semantics in tests, not pixels.

## Discipline

Both derivations are tested view-models — test both directions (failure alarms before ack, quiet after ack, re-alarm on a NEW failure after the ack; clear leaves a one-row trail whose row is the clear op). Amend DESIGN §4.2 (log shape: ack line, clear carve-out) and §7.3 (banner lifetime now ends at ack). Ops-line cap/atomicity rules (CAP=4096, PIPE_BUF) apply to the new line shapes.
