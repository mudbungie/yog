Found by Larkspur while sweeping bl-36c3. A **new size class**, not a new symptom: a window that is narrow and tall — a tiled left third of a portrait monitor — is a shape nothing in the suite has ever rendered. Every paint property in the tree is asserted at four sizes (`src/shell/acceptance/mod.rs::SIZES`: 420x320, 800x500, 1150x760, 2560x1700), and all four are landscape.

Measured at **480x1400** with `paint_probe::seen_of`, which reports each galley's laid rect beside the part its clip let through.

## Witness 1 — rows are laid to the LEFT of the pane's own left edge

The conversation pane's clip begins at x=268 (a 260 pt roster column plus the frame margin). These runs are laid *before* it and hard-cut there:

```
x  240..296 / shown 268..296   "Transcript"     56 pt laid,  8 pt shown
x  240..270 / shown 268..270   "Work"           30 pt laid,  2 pt shown
x  236..278 / shown 268..278   "google"
x  236..278 / shown 268..278   "ollama"
x  236..313 / shown 268..313   "claude-code"
x  244..512 / shown 268..512   "bearer-token provider — set the token in Config"
x  254..372 / shown 268..372   "Raw (verbatim bytes)"
x  262..289 / shown 268..289   "user:"          27 pt laid,  1 pt shown
```

`Transcript` is a **tab control** showing eight of its fifty-six points. `Work` shows two of thirty. At 480x1400 `Work` is not painted at all — clipped away entirely, which is the omission shape §11 rule 8 exists to stop (no seat to hover, no rect to click, no ellipsis to warn you).

## Why nothing caught it

§11 rule 1 — *"nothing in this panel extends past it"* — is asserted on **one edge of two**. `src/shell/acceptance/elision.rs::assert_inside_the_panel` is, verbatim:

    for (text, rect) in painted {
        assert!(
            rect.right() <= PANEL + 1.0,
            "`{text}` is laid past the panel edge at {}", rect.right()
        );
    }

There is no `rect.left()`. That is bl-36c3's vacuity **shape 3** (wrong axis) in its narrowest form: the axis is right, the direction is not.

The likely mechanism, stated as a lead rather than a finding: `row::control_last` lays its row in `egui::Layout::right_to_left`, and a right-to-left child that needs more width than it was given grows **leftwards** from its right edge. Under a rule that only ever measured the right edge, growing left is free.

## Witness 2 — the same size reddens the G4 disjointness walk

Adding 480x1400 to `SIZES` also fails `acceptance::overlap::no_two_runs_of_text_share_pixels_at_any_window_size`. Two independent properties fail at one untested size, which is the argument for the size rather than for either bug.

## The ask

1. Fix the left-edge overflow, and **state rule 1 on both edges** — `assert_inside_the_panel` should measure the panel, not one side of it.
2. Then add a narrow-tall size to `acceptance::mod::SIZES`, which is the one list `overlap` and `legible` share. It cannot be added before the fix: it is red today in both.

Reproduce with no new machinery — change `SIZES` to include `(480.0, 1400.0)` and run `cargo test --lib shell::acceptance`. Both failures print their own evidence.

Verify all cited paths against HEAD; ball bodies drift.
