From the 2026-07-27 UX-testing session (the operator).

## Why

UX testing is a loop: land a fix, reinstall, relaunch against the REAL world
(`$XDG_DATA_HOME/yog`), look at it. Today that loop is three remembered
commands and the easy mistake is skipping the reinstall — you then test a
stale binary and mis-attribute what you see. `~/AGENTS.md` puts build
instructions in the Makefile; this belongs there.

Compounding it: `make run` uses `cargo run`, which is the DEBUG build. The
installed binary is the release build. They are not the same artefact, so
"it worked under `make run`" does not prove the thing the operator launches
works.

## Ask

A target that kills any running instance, rebuilds + installs the release
binary, and launches it inheriting live state. Roughly:

    .PHONY: relaunch
    relaunch: install
    	@pkill -x yog 2>/dev/null || true
    	@"$(INSTALL_BIN)/yog" &

Decide the details with care rather than pasting the above:
- `pkill -x yog` must not fire before the build succeeds — a failed build
  should leave the running instance alone, not kill it and install nothing.
  (Ordering: `install` is a prerequisite, so it runs first. Verify that
  actually holds for the recipe you write.)
- Detaching (`&`) vs blocking the terminal: blocking gives the operator
  yog's stderr live, which is worth a lot during UX testing. Prefer it
  unless there is a reason not to, and say which you chose in the README.
- Naming: `relaunch` is a guess. Something that reads as "the UX loop".

README.md must gain the line — AGENTS.md: "Create a README.md, and keep it up
to date."

## Not this ball

Do not touch `make run`; the debug-build path stays for quick checks.
