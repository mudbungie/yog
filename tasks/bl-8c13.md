## Operator complaint (2026-08-01, verbatim)

'we're still starting at the top and going down. The anchor is working fine, but we should start at the bottom.'

This is the piece bl-5cdb explicitly skipped (its DESIGN §11 amendment and a test pin that underfull content is left alone — that pin is now overruled): when content is SHORTER than the viewport, it must sit at the BOTTOM of the view with empty space above, terminal-style. New text always appears at the bottom edge from the very first line; growth pushes upward into the empty space, then scrolls.

## Scope

Every surface bl-5cdb tail-anchored: transcript chat (src/transcript/render.rs), inbox deposits (src/inboxview/render.rs), activity ops trail (src/shell/activity.rs), steps table (src/steps_view/render.rs — respect its drill-in anchor-release rule from bl-5cdb; decide and document whether bottom-alignment also relaxes while a drill-in is open). ## Implementation sketch (verify against the tree — bl-1f21 lands in these files first, by design: this ball is claim-gated on it)

egui's stick_to_bottom does not bottom-align underfull content. The standard idiom: pad the top inside the scroll body — space = (viewport height − content height), clamped ≥0 — using the previous frame's measured content height (the paint_probe 'settled' two-frame pattern from bl-5cdb's tests already models the one-frame settle). Alternatives (bottom_up layout inside ScrollArea) are known-awkward in egui; pick what stays testable, but whatever the mechanism, it lives in ONE shared helper.
