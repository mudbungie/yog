The operator, at the §9.4 picker, hit the credential fault and reported it
verbatim: **"This isn't really fixable through the yog interface. It should
be."** Everything else on that pane routes; this one line strands them at a
shell.

## What the pane painted

    ⚠ no credential for this provider: set BRAZEN_API_KEY (or the provider
      API-key env var / --api-key) or run `bz --login --provider <id>`
    or run by hand:
    bz --list-models --provider anthropic --json

That is `shell/model_pick/mod.rs:189-195` (`roster_candidates`) — brazen's own
error text, forwarded raw, plus §8.3's run-by-hand fallback. No verb.

## Why it is a defect and not just terseness

**1. yog already knows the remedy, and it is not the one brazen printed.**
That sentence is brazen's `resolved_secret` `None` arm
(`brazen-0.0.5/src/auth/mod.rs:181`), reached from `StaticSecretAuth` — so it
fires for **`api_key`/`bearer` rows only**. For those rows yog's own derivation
says something different and more useful:
`ProviderRow::login_blocked` (`config_edit/brazen/providers.rs:64`) →

> `api-key provider — set the key in Config`

The Login rows (§8.3) and the §9.5 config rows both render that sentence from
that one derivation, "so the two surfaces cannot state different things about
one provider" (`providers.rs:20`). The picker is a third seat saying a fourth
thing — and the thing it says leads with an env var and offers `bz --login`
for a row yog's own capability read says login can only exit 78.

**2. The fact needed to fix it is already in hand, and thrown away.**
`marks::provider_rows` (`shell/model_pick/marks.rs:34`) calls
`picker.bz_runner.providers()` — the full `ProviderRow` set, `auth` column
included — then discards `auth` through `row_names`. No new read, no new
spawn, no new RAM: the picker holds the capability fact and drops it one line
before it needs it.

**3. Every other auth seat in yog ends in a control; this one doesn't.**
DESIGN §8.3 rule 5 (bl-8e34) gives a *failing step* a routed verb —
`⚠ auth: <row> — Login ↙` — and adds, verbatim: *"The Login pane still paints
beneath the banner in both cases — a wrong derivation must never become the
only way out."* That rule paid a git-join cost to derive the row. **The picker
needs no join at all**: it just asked that row, by name, one frame ago. The
seat where the routing is free is the only seat with no routing.

**4. The route already exists in this same file.** The provider dropdown's
`add a provider…` entry returns `true` out of `pane`, and `pane_routed`
(`shell/model_pick/mod.rs:86-91`) spends the one bl-1ca2 Config gesture to
focus the Config tab. The credential fault needs that same return, under a
different label.

## What is NOT in scope

The other two warnings the operator saw on the same pane already route, and
are not defects:

- `⚠ gpt-5.6-sol names provider row 'openai-chatgpt', which brazen's table
  does not have — repoint it in the Config editors, or pick a live model here`
  — the provider dropdown below it offers the live rows (bl-bd89 dissolved
  that dead end).
- the scope sentence and the frozen-at line — shipped and correct (bl-a0d4's
  verification stands).

Credentials stay constitutionally untouchable (DESIGN §8.3, line 2286). This
ball asks for **routing to the existing remedy surfaces**, never for yog
reading or writing a secret.

## Proposed shape — attack it before building it

Give the roster's auth failure the same treatment the step failure got, keyed
on the `auth` column already fetched:

- `oauth2` → the Login verb for **this row**, right there (the pane is already
  a seat that `login_section` renders in — §11's auth banner is the
  precedent), or the tab focus carrying the row.
- `api_key` / `bearer` → `login_blocked`'s own sentence plus the Config route
  the `add a provider…` entry already implements.
- anything else → today's wording.
- The run-by-hand command **stays** in every arm: §8.3's fallback grammar, and
  rule 5's "a wrong derivation must never become the only way out".

One judgement, in `model_pick` beside `grammar::fault` (testable, per the
picker's own coverage split); `shell/model_pick` renders it. Do **not** add a
second phrasing of "what this row needs" — take `ProviderRowView`'s.

Open question for the implementer to settle against the tree, not to assume:
whether the fault should distinguish *spawn/exit* failures from *auth*
failures at all, or whether `RosterView::error` needs the classification
`login::auth` already performs on step errors. `query.rs` currently carries
one flat `error: Option<String>`.
