From the 2026-07-27 UX-testing session (the operator): *"I'm talking to gpt-5.4. How do I change that?"*

He could not find the answer in the window. Neither could I, quickly — here it
is, which is itself the evidence.

## Where the model actually lives (two places, both YAML, neither a picker)

1. **Per workspace**, on the workspace's `config/default` **git branch** —
   `providers.yaml`, one entry per role:

        roles:
          worker:
            provider: codex
            model: gpt-5.4
            tools: [bash, read_file, load_skill]
          compactor:
            provider: codex
            model: gpt-5.4

   yog's §9.3 config-branch editor is the lawful writer, and it works by
   staging drafts and driving `lernie config` with `$EDITOR`
   (`src/config_edit/branch/edit.rs`, `src/shell/config_edit.rs:197`). So
   changing your model means: ⚙ Config → find the branch surface → open an
   external editor → know that `worker` is the role that talks to you → know
   the model id string → know that `compactor` exists and probably wants
   changing too.

2. **For future workspaces**, the seed at
   `$XDG_DATA_HOME/yog/world/lernie/template/providers.yaml`, edited only
   outside yog.

Nothing in the window ever displays which model you are talking to, let alone
offers the set you could switch to.

## Ask

A model picker. The facts it needs already exist and are already read by yog:

- the **available** models are the keys of the world `models.yaml`
  (`$XDG_DATA_HOME/yog/world/lernie/models.yaml`) — yog's §9.2 `lernie_global`
  editor already loads that file (`src/config_edit/lernie_global`);
- the **current** model is `roles.worker.model` in the focused workspace's
  `config/default:providers.yaml` — yog's §9.3 branch surface already reads
  that tree (`src/config_edit/branch.rs:48-49` enumerates `providers.yaml`
  among the governing commit's paths).

So this is a derivation over two things yog already has, not new plumbing.
Per AGENTS.md, prefer a query to a stored field: do not cache "the current
model" anywhere — read it.

## Design questions to settle before building

- **Where does it live?** The obvious spot is Config, but the operator asks
  this question *while looking at a conversation*, not while in a config mode.
  Showing the current model somewhere on the conversation surface may be most
  of the fix; a picker without a display still leaves you guessing.
- **What scope does a change have?** `providers.yaml` is per workspace, so
  switching the model switches it for **every conversation in that sphere**,
  retroactively for future turns. If the operator expects "change the model
  for this chat", the mechanism does not match the expectation and the UI must
  not pretend otherwise. Say what the scope is, in the UI, at the point of
  change.
- **`worker` vs `compactor`.** Two roles, two models. A one-model picker that
  silently writes only `worker` leaves them mismatched. Decide and document.
- Writing `config/*` goes through `lernie config` (§9.3) — the picker must use
  that path, not write the file. It is "the only lawful writer".

## Depends on

The set of *offerable* models is only correct once bl-53be is fixed — today
`models.yaml` lists two Claude entries pointing at a brazen provider row that
does not exist, so a naive picker would offer models that fail at fire.
