From the 2026-07-27 UX-testing session (the operator): *"I'm talking to gpt-5.4. How do I
change that?"* — then, on being told the list has three entries: *"[redacted: operator remark on a live account's model roster]"*

He is right, and the cause is not what I first wrote in this ball. Corrected below.

## Why you only see one usable model

Nothing is lazy-loaded. yog's model list is a **static, hand-maintained YAML
file** — `$XDG_DATA_HOME/yog/world/lernie/models.yaml` — with three entries, two
of which name a brazen provider row (`anthropic`) that does not exist on this
box (bl-53be). So the effective set is one: `gpt-5.4`.

Meanwhile brazen already does live discovery, and the codex row is already
configured for it (`~/.config/brazen/config.toml`):

    [provider.models]
    path      = "/models"
    query     = [["client_version", "0.0.0"]]
    array_key = "models"
    id_key    = "slug"

and `bz --help` documents the verb:

    --list-models        one GET: list the resolved provider's models

Run against a live credential it returns **seven**:

    $ bz --list-models --provider codex
    gpt-5.6-sol
    gpt-5.6-terra
    gpt-5.6-luna
    gpt-5.5
    gpt-5.4
    gpt-5.4-mini
    codex-auto-review

yog never calls it. That is the whole gap.

## What the operator asked for, verbatim

> we should be triggering that list every time the picker is triggered (and ui
> elements should indicate the list operation in flight)

So: no cached model list, no stored candidate set. The picker opens, it fires
`bz --list-models`, and the UI says it is doing so. This is the AGENTS.md rule
applied directly — "don't store what you can compute — make it a query, not a
field" — and it is also just correct, because the provider's roster changes
without yog's involvement.

## Where the model is written (unchanged from the original ball)

`providers.yaml` on the focused workspace's `config/default` **git branch**:

    roles:
      worker:                      # the role that talks to you
        provider: codex
        model: gpt-5.4
        tools: [bash, read_file, load_skill]
      compactor:                   # a second role with its own model
        provider: codex
        model: gpt-5.4

`config/*` is written **only** through `lernie config` (DESIGN §9.3 — "the only
lawful writer"); yog's §9.3 branch editor stages drafts and drives it. The
picker must use that path, never write the file.

## The design question you must settle

`models.yaml` is not merely a list of names — it carries the facts lernie needs
and brazen does not own. Its own header:

> Holds the facts lernie's behavior relies on and brazen does not own:
> per-model capabilities and context windows.

    gpt-5.4:
      provider: codex
      model_id: gpt-5.4
      capabilities: [tool_use_native, streaming]
      context_window: 400000

So if the operator picks `gpt-5.6-sol` from a live `bz` list, there is no
`models.yaml` entry for it — no capabilities, no context window. **Decide what
happens**, and write the answer into DESIGN:

- does the picker also write a `models.yaml` entry (and where do capabilities
  and context_window come from — does `bz --list-models --json` carry them?
  CHECK, do not assume);
- or does lernie have a defensible default for an unlisted model;
- or is the offerable set the intersection of "brazen can reach it" and
  "models.yaml describes it", in which case the picker must SAY why a model the
  provider offers is not selectable — a silently-shorter list is the bug we are
  already fixing.

Prefer the shape that does not require the operator to hand-edit a second file
to use a model their provider already offers. Attack it before committing, per
AGENTS.md.

## Other things to settle

- **Scope, shown at the point of change.** `providers.yaml` is per *workspace*,
  so switching the model switches it for every conversation in that sphere. If
  the operator reads the picker as "change the model for this chat", the UI is
  lying. Say the scope in the UI.
- **`worker` vs `compactor`.** Two roles, two models. A picker that silently
  writes only `worker` leaves them mismatched. Decide and document.
- **Where it lives.** The question is asked while looking at a conversation, not
  while in config mode. Displaying the *current* model on the conversation
  surface may be most of the fix; a picker with no display still leaves you
  guessing what you are talking to.
- **In-flight UI.** yog already runs `bz` async and renders it live — the §8.3
  login pane streams `bz --login` through `Streamed` / `RealBzRunner`
  (`src/login`, `src/cli_outbound/mod.rs`, `src/config_edit/brazen`). Reuse that
  machinery; do not invent a second async-command surface.
- **Failure.** A `--list-models` that errors, times out, or returns empty must
  render as itself — INV-2, no error printed and dropped. The §7.3 ichor-red
  banner already exists for this.
