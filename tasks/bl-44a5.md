Found by the §16.7 W14 clean-room drive (docs/drive-logs/2026-07-26-w14-cleanroom.md).

`world::overrides` puts `<yog-data-root>/world/tools` at the head of the child PATH (§16.2 W9/W11), and `yog env` prints that PATH verbatim — but nothing on the hatch path MATERIALIZES the three shims. They are written only by the Start flow (`Step::EnsureSeeded` -> `world::tools::ensure_shim`). So before the first Start:

- ambient machine: `yog exec bl …` falls through world/tools (absent) to the HOST `bl` on PATH — right nested paths by env inheritance, WRONG implementation. That is exactly §16.4's (b) failing silently, the thing W9 was written to make structural.
- clean room (only yog+git on PATH): it dies — `yog exec: failed to spawn bl: No such file or directory (os error 2)`.

Reproduce: scripts/drive/cleanroom.sh target/release/yog /tmp/w14 /tmp/w14-shots run-s3s4s6 (its fixture's first act is `yog exec bl prime`). After one Start has seeded the shims, the same `yog exec bl list --json` returns `[]` exit 0 in the same room — the gap is precisely 'before the first Start'.

Fix shape: the tools dir is a generated artifact of THE WORLD, not of the start flow, so converge it wherever the world is handed out — `yog env` and `yog exec` call the same `ensure_shim` for all three namespaces before printing/spawning. Single source, no new config. Needs the §8.4/§16.4 doc rows amended to say so (the hatch doc still says 'the ambient bl/lernie/bz then operate on yog's nested state' — the phase-1 sentence).

NOTE: fixing this alone does NOT unblock `yog exec bl prime` — see the sibling ball on the embedded bl's refusal of prime.
