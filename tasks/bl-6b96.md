DESIGN §10.1's registry ruling says where the image publishes and by what authority — `ghcr.io/mudbungie/yog`, one package per repo, "pushed only from that repo's own release workflow, at tag time. Not from a laptop, not from `make`, not from a second repo's workflow. The publishing identity is the repository's own `GITHUB_TOKEN`, which exists only inside that workflow run." That job does not exist. The ruling is stated in the doc, restated in the Makefile beside `image`, and restated again in README "The image", and nothing anywhere performs it: `ghcr.io/mudbungie/yog` has never been pushed, so `make deploy`'s `save | ssh … load` is the only way an image reaches a box.

Wire it into `.github/workflows/release-plz.yml`'s release path, where the tag is minted — not into `ci.yml`, and not a workflow of its own that would need its own trigger to keep in step with the tag.

What the job owes:

- **Trigger: a release that actually happened.** The tag and the GitHub Release are the release job's own outputs; the push hangs off those, so a CI run that concluded anything other than `success` publishes nothing. A version is published ONCE (§10.1) — a re-run over an existing tag must not re-push, because "re-push a corrected build under the same tag" is a moving `latest` wearing a version number.
- **Login with the workflow `GITHUB_TOKEN`.** `packages: write` on the job, `docker/login-action` (or a plain `podman login`) against `ghcr.io` with `${{ github.actor }}` and that token. No long-lived registry credential is created, stored or rotated anywhere — that is the property the ruling buys, and a PAT would spend it.
- **Two tags, both immutable, and no `latest`.** The version tag (`ghcr.io/mudbungie/yog:<version>`, the one `Cargo.toml` names and the tag was minted from) and the commit sha. `make image`'s local `:latest` stays local; a published one is a name whose bytes change under everyone who wrote it down.
- **`image-scan` is a PREREQUISITE, not a companion step.** `make image` already ends in `make image-scan` (§10.1's condition on the registry ruling), and the push must be gated on that same scan passing on the same image the push carries — build, scan, then push, in one job, or the gate is a different image's.

Open questions to settle in the ball, not by guessing:

- **Which engine on the runner.** `make image` autodetects podman-then-docker; a GitHub runner has docker. Either `make image` on the runner and push with the same engine, or `docker/build-push-action`, which would build a SECOND time from the same `Containerfile` and so would not be the scanned bytes. The first is the one that keeps the scan honest.
- **Whether the arch story is stated or shipped.** The build is a static musl binary and the runner is amd64; an arm64 box pulling this gets nothing it can run. Either the manifest is single-arch and the README says so, or the job builds a multi-arch manifest — which is a real cost and needs its own decision.

Do not push a byte from a laptop while wiring this. A push is not undoable, and the whole reason the authority lives in the workflow is that the workflow is the only place the answer to "who may publish" is already answered.
