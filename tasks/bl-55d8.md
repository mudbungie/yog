It did not fall out. bl-bf79 fixed the *cause* (the wall now rides every §8.2

## The shape, verbatim from the falsifying run

Driving the pre-fix binary (`scripts/drive/stories.sh run`) left this on disk:

    steps/<agent-id>/002/response.json   0 bytes
    steps/<agent-id>/002/stderr.log:
    bz: no workspace in this environment — providers, sign-ins and the model
    cache belong to a workspace, and there is nothing shared to fall back to.
    Run this inside a yog workspace, or focus one in yog.

and the transcript stopped at `002-user.md` with no reply after it, ever. The
operator's report of the same event was: *"it looks like the second message in a
conversation always fails."* That is the whole signal yog gave them — the
absence of a reply. The reason was sitting in a file yog already watches.

## Why this is a §7.3 rendered-fact matter

§7.3's rule is that a failure is a *rendered* fact, never a silence; `ops.jsonl`
already carries that discipline for spawns (§4.2's synthetic-failure line). A
step is the other half and has no such rule: a step whose latest
`response.json` is EMPTY while its `stderr.log` is NON-EMPTY is not "still
streaming" and not "quiescent" — it is a driver that died before its first
token, and the reason is bytes in a sibling file.

Note the distinction from the framing yog already parses (§4.4): an
`{"type":"error"}`-then-`{"type":"end"}` tail is a *reported* failure and
renders. This ball is about the case where there is no tail at all — zero
bytes — which today reads as nothing.

## Suggested shape (attack before building)

- The state is a query, not a field: `response.json` empty AND `stderr.log`
  non-empty. No new stored fact, no index.
- It probably belongs beside the existing `Doc::{Json,Absent,Unparsed}`
  taxonomy in `src/steps_view` (bl-307f added `Unparsed` for the same class of
  hole) — a fourth reading rather than a new surface.
- Check first whether the §6 attention model should carry it too, or whether
  the transcript/step view alone is honest. A new mark is a smell; the epitaph
  path (`lernie scan`'s died-epitaph deposit) may already be the general path
  with an empty input.
