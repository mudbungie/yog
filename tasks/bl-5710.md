bl-77be split the shipped worker grant by subject and gave the worktree names
(`bash`, `read_file`, `apply_patch`, and any granted pool name) a routing lane
to the one consenting tool host. The lane works — proved on this drive with a
foot enrolled and `subject_cwd: true` on its entries: a bare `bash` call ran in
the conversation's own bound directory and the program got built.

What no component ships is anything that ANSWERS those names. The install seeds
`<world>/litany/tools/{bash,read_file,apply_patch,…}.json` — schemas, offered to
the model verbatim as `input_schema` — and `src/install` holds the grant and the
pool "in step". Behind the schemas there is nothing: bl-77be's own words,
"Nothing resolves a binary behind it any more." thrall ships no corpus either;
its design document's only example of a `command` is a fictional path
(`/usr/local/libexec/thrall-tools/bash-tool`).

So the shipped worker grant is a set of eight names of which four are engine acts
that work, and the rest resolve only if the operator has separately written and
provisioned tool binaries that nothing documents beyond one docstring stating the
contract (JSON on stdin, bytes on stdout, exit code the verdict).

## What it costs, measured

Out of the box — a bare engine, no foot, which the thrall README calls "a valid,
and the default, installation" — a conversation is offered all eight names and
every worktree name refuses. On this drive that conversation spent eight model
steps discovering it and gave up, having written nothing. That is the exact shape
bl-1fd0 already ruled against for providers: *"the start pane invites a goal that
cannot possibly run … the first rung must be provider sign-in, not a text box."*
The tool-host half of that ruling has not been drawn.

With a foot enrolled, the worst offender is `apply_patch` specifically: it is the
tool a model reaches for FIRST to write a file, it is in the grant, it is in the
offered schema list, and it is the one name an operator provisioning a
co-located foot is least likely to have implemented (bash and read_file are ten
lines each; apply_patch is a patch-format parser). Every conversation on this
drive opened with an `apply_patch` call and paid a step for the refusal.

## Two separable questions

1. **Does the pool ship an implementation?** A co-located foot is called "the
   normal install" by REMOTE §5.4, and a normal install currently requires the
   operator to author the execution corpus from scratch. If thrall owns it
   (bl-1dd3: "the foot that owns the local execution corpus"), the balls belong
   upstream and this one is the record of the gap.
2. **Does yog offer a name nothing can answer?** The grant is config and the
   refusal is in band, so the posture is defensible — but a schema in the model's
   `tools:` array is an offer, and an offer that always refuses is a decoy the
   operator pays for once per conversation. The cheap end of this is the start
   gate's shape: at `/prepare`/`/prompt`, a workspace whose granted worktree
   names have no consenting advertiser is a workspace where typing a goal will
   write nothing, and saying so before the spend costs no model call.

## Shape of the repro

    # a fresh world, a workspace, a role pointed at any working provider
    yog gesture --ws <ws> '/clients'          # rows: []  — nothing advertises
    …fire any goal that must write a file…
    # every apply_patch / bash / read_file call refuses in band; nothing is written
