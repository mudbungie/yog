Carved out of bl-1015 under the operator's ruling of 2026-08-13 — "not worried about
osx atm. I'll fix it eventually." This ball does NOT make macOS pass. It stops
a platform nobody is fixing today from blocking every release, and it makes the
README say what is true. bl-1015 keeps the real fix.

**Why it blocks.** `.github/workflows/release-plz.yml:154-155` gates the publish
on the CI *workflow run*:

    github.event_name == 'workflow_run' &&
    github.event.workflow_run.conclusion == 'success'

A run concludes `success` only when every job does, and `.github/workflows/
ci.yml` carries a `macos:` job (`runs-on: macos-14`, `cargo build --locked`
then `make test`) that fails 14 tests and always has. So 0.0.2 cannot ship.

**The change.**

1. Move the `macos` job out of `ci.yml` into its own workflow file with a name
   that is NOT `CI` — release-plz.yml's `workflow_run` filter matches the name
   exactly, and ci.yml's own header already warns that "this workflow's name
   must stay `CI`". Same triggers, so macOS still runs on every push and PR and
   still reports red where it is red; it simply is not what the publish waits
   on.
2. Say so in ci.yml's header, beside the release-gate note that is already
   there, so the next reader learns why the platform split exists without
   having to find this ball.
3. Correct README.md:392-393. It reads today:

       `make ci` on Linux (fmt-check, clippy `-D warnings`, tarpaulin 100% floor)
       and `cargo build` + `make test` on macOS (Apple silicon).

   which states a macOS guarantee that has never held. It must say that Linux
   is the gate and that macOS builds and tests are reported but not gating, and
   point at bl-1015.

Done when a push to main produces a CI run that concludes `success` on the
linux job alone, and the macOS run reports separately.
