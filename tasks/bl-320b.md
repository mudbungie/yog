## The gap

REMOTE §1's canonical scene is "a home server runs the engine and keeps every
log; a phone seat talks to a conversation". The server half now exists and is
deployable (bl-bf35 seats `yog serve` as a service and keeps it current). The
seat half exists only for **argv**: `yog seat` sends one gesture over the wire
and prints the reply, and `yog tool-host` advertises tools. There is no
graphical seat for an engine in another process, let alone another machine.

That is not an omission, it is construction. `Engine::window_seat`
(`src/engine/window.rs`) builds its material as:

    crate::wire::client::Seat::open(&crate::wire::material::Material {
        address: crate::wire::loopback(&bound),
        ..material
    })

`bound` is the address this process's own listener actually bound, and
`loopback()` forces the host regardless of what `address` says. A window is
therefore a client of the engine *in its own process*, always — bare `yog`
boots an engine and dials itself. Nothing reads the operator's stated address
on the way in, and no flag names one.

The consequence is that a box running the engine and a box running the window
are the same box, so "run the engine on the server" and "keep using the window"
are today mutually exclusive. Every REMOTE property that made this look
reachable is already paid for — the framing, the strict `Reply` decode, the
per-workspace registry, presence, the mailbox, name-based addressing — and the
argv seat proves the transport end to end.

## What this is not

Not a request for a second face. VISION §8 and REMOTE §1.2 both refuse a second
implementation, and this needs none: the window already speaks *only* the wire
(`AppModel::dispatch` is deleted, bl-1747). What it lacks is the ability to be
pointed at a listener it did not start.

Not a new verb either, most likely. The engine boot and the window are one
argv today; separating "be a window" from "be an engine" is the actual
question, and it is a §8 question — the ruling there was *one world, one
engine, whichever face started it*, which was decided for a box that is both.

## The other half: material is per-box, not per-server

A second problem sits behind the first and should be settled in the same
breath. A client reads its certificate material from one place —
`<yog-data-root>/wire` — so a box can hold exactly one CA, one client leaf and
one address. A machine that already runs its own engine (and self-provisioned
a loopback root at boot, §8) therefore cannot also be a client of somebody
else's engine without its own window breaking, because both read the same
directory.

Today the only way to hold two is to hand a seat a different data root
entirely, which drags a whole world along with it for the sake of four files.
Whether the fix is a client-material lookup separate from the engine's own, or
a stated address selecting among registered servers, is the design question —
but a "primary" server the operator's laptop is a seat of is exactly the case
that trips it, so §1.5's per-workspace trust domain needs a per-server
material story beside it.

## Sequencing

Blocked on nothing. The transport is proven; this is a design ruling plus the
plumbing that follows it, and it is the difference between a server that runs
agents and a server that is the operator's primary seat.
