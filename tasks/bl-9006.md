## Why this should NOT be filed away as 'flaky'

The obvious reading is a flaky timing assertion to be loosened. Attack that reading first, because the alternative is a real bug:

yog holds a shared `Arc&lt;dyn Clock&gt;` and a **§7.2 sweep schedule**. Under load, far more wall-clock elapses between ticks than the beat's author ever saw. If a scheduled sweep fires inside what the beat calls the 'idle' window and mutates, then **idle is not pure once enough time passes** — and the beat is correct while the code is wrong. A green run on a fast machine would be luck, not proof.

So the first question is not 'how do we stabilise this beat' but: **what fired?** Capture the ops line the beat objects to under load; it names the mutation.

## Scope

1. Reproduce under artificial load (or by advancing time) and capture the actual ops line. Do not tune timeouts before that line is read.
2. If a sweep is mutating during idle: that is the defect. Fix the sweep or amend the invariant in DESIGN, per the standing rule that code and DESIGN disagreeing means one of them is a bug.
3. If it is genuinely a real-clock race in the beat: the repo already has the tool — inject a `FakeClock` (`Arc&lt;dyn Clock&gt;` is shared exactly so a test can advance it, AGENTS.md rule 9) so the beat drives time instead of racing it. **Do not** widen a tolerance; a load-sensitive assertion that passes by being generous is [[vacuous]] under the very conditions it should catch — see bl-f16e and bl-36c3 for the two sweeps of that same disease.

## Why this is urgent at fan-out

The close gate runs the full suite. A beat that reddens only under load will **fail an unrelated agent's `bl close` at random** and read as that agent's fault, costing a ~15-minute gate and inviting a wrong 'fix' to whatever they happened to be touching. It has already cost one.

Verify all cited paths against HEAD first; ball bodies drift.

## Timing evidence (Dowel, via Alkaloid) — supports the sweep hypothesis over the flake reading

Measured on the same beat, same tree:

- **Standalone: 68/68 pass in 1.15s.**
- **Under tarpaulin instrumentation at load ~14: FAILED at 188s.**

That is a ~160x stretch of the window the beat calls 'idle'. It is exactly the shape predicted in the body: enough wall-clock elapses for a §7.2 scheduled sweep to fire *inside* the idle window and mutate.

This is evidence the assertion is **correct and the invariant is false under real time**, not evidence of a racy test. A beat that only passes when the machine is fast is not proving purity; it is proving that nothing had time to happen.

**Therefore, still: capture the ops line before touching any timeout.** The mutation names itself. If a sweep is the cause, the fix is in the sweep or in the DESIGN invariant, not in the beat's tolerance.
