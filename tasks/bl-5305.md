Round 1, devadmin lane. STORIES S5 (Operator) and S15 (Warden): watching the work happen.

`lernie follow ops <conversation>` on a conversation that spent its whole life
running commands on two enrolled boxes. Every distinct frame it produced:

    {"kind":"follow","ok":true,"stream":{"delta":"thinking"}}
    {"kind":"follow","ok":true,"stream":{"delta":"text","text":"On box2:\n\n- **Kernel version:** ..."}}
    {"kind":"follow","ok":true,"stream":{"delta":"text","text":", excluding the header line; `ps aux | wc -l` returned 6 total lines)"}}

That is the whole live surface. Behind those three frames the conversation
loaded four tools off two machines and ran eight commands on them — `hostname
&& uptime`, a service sweep, a `find /`, an `apk add` pulling forty packages.
None of it appears. The follow lane carries the assistant`s prose and a
thinking marker, and nothing about the tool window at all: not the tool name,
not the client it is routed to, not the command, not the capture, not even
that a call is in flight.

For a conversation editing its own worktree that is defensible — the work is
on disk and the diff is a read away. For a conversation administering a
MACHINE it is the wrong omission, because the box is the thing the operator
cannot inspect afterwards and the tool call is the only record that it was
touched. The transcript does record every capture in full (`lernie transcript`
carries the stdout verbatim), so the fact exists; it is the LIVE view that
drops it, which is the view an operator has open precisely when a command they
did not expect is about to run on their server.

Compare the same task under `codex exec` in the same container: every command
is printed as it is dispatched —

    exec /bin/bash -lc "gzip --test -- /var/log/app/app.log...Z.gz ..." in /root
     succeeded in 0ms: live=/var/log/app/app.log size_bytes=0 ...

— so the operator reads what ran and what it answered, in order, as it
happens. That is the bar for a fleet seat and this is well under it.

ASKED FOR: the follow frame carries the tool window as it opens and closes —
at minimum `tool <name> on <client>` when a call is posted and its exit code
when the capture lands. The names are already on the wire (the transcript has
them); the question is only whether the follow fold is allowed to carry
anything but text.

SECOND, SMALLER, in the same place: `lernie help follow` states "Each frame is
the WHOLE accumulated fold rather than a delta, so a frame missed is nothing
missed." The frames above are keyed `delta` and do not overlap — the second
text frame is a continuation of the first, not a superset of it — so a
follower that reconnects loses whatever was written while it was away. Either
the claim or the frames are wrong.
