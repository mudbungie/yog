Under `cargo test --lib` at full parallelism the test binary is sometimes
killed outright — cargo reports `signal: 13, SIGPIPE` — part-way through the
run, so a few hundred tests never report and the gate fails on nothing that
failed.

## What is established

- **It is not caused by any one ball's tests.** Measured on two checkouts of
  the SAME tree, in the same filesystem, on the same box: a checkout at the
  base commit of an unrelated in-flight change crashed **2 runs in 8**, and the
  checkout carrying that change crashed **~3 in 8**. Adding socket-heavy tests
  raises the rate; it does not create the defect.
- **Serialized, it does not reproduce.** `--test-threads=1` ran the whole suite
  three times clean. It is a parallel-load defect.
- **It is not the multiplex arms resetting the disposition.** The obvious
  hypothesis — an embedded substrate CLI's `main`, run in-process by the
  multiplex tests, calling `signal(SIGPIPE, SIG_DFL)` for the whole process —
  was tested and is FALSE. `/proc/self/status` reports `SigIgn` with the
  SIGPIPE bit set before and after each of the three in-process arms, and a
  watchdog thread polling that field every 5 ms across a crashing run never saw
  it change.

That last point is the puzzle: a process whose SIGPIPE disposition is
`SIG_IGN` cannot be killed by SIGPIPE, and the disposition was measured as
`SIG_IGN` throughout. Either the window is narrower than a 5 ms poll (a forked
child briefly sharing the handler table would be one way), or the death is not
what the wait status says it is.

## What was not done

An `strace -f` of the signal syscalls was started and abandoned: it produced
157 MB in one run of the suite and the box's temp filesystem is the same one
the gate builds in. A targeted run — the signal syscalls only, output to a
non-temp filesystem, looping until the crash — is the next step, and it should
name the caller outright.

## Why it matters

`bl close` runs the suite as its gate, and so does CI. A one-in-four death is a
gate that fails for no reason a quarter of the time, and the failure looks like
nothing: no test is reported failing, only the process is gone. A re-run passes,
which is exactly the shape that teaches an agent to re-run rather than read.

## Where to start

- Bound the strace to `rt_sigaction`, `kill`, `tgkill` and `write` on the
  crashing run, with the log outside the temp filesystem.
- Alternatively install a real SIGPIPE handler for the duration of a run (a
  test-only shim) so the death carries a backtrace instead of a wait status.
- Check whether the crash correlates with the tests that open real loopback
  listeners; the suite's socket count is what recent balls have grown.
