Under `cargo test --lib` at full parallelism the test binary is sometimes
killed outright — cargo reports `signal: 13, SIGPIPE` — part-way through the
run, so a few hundred tests never report and the gate fails on nothing that
failed.

## Cause — found, and it is one line of test-reachable production code

`perform`'s `Outcome::Exec` arm (`src/multiplex/lernie.rs`) spent the execve
baton with `std::os::unix::process::CommandExt::exec`. **`exec` does not
fork.** std's `do_exec` runs in THIS process, and on its way to `execvp` it
does `signal(SIGPIPE, SIG_DFL)`. A successful `execvp` never returns, so in
production the reset is invisible — it belongs to the image being replaced. An
`execvp` that FAILS returns, and hands back a live process with the reset
standing.

`src/multiplex/lernie/tests.rs` drives exactly that failure — it is the arm's
only reachable proof (`/nonexistent/yog-successor`) — so **every lib run reset
its own SIGPIPE disposition to `SIG_DFL` and left it there**. From that moment
any write to a reader that went away is a death instead of a `BrokenPipe`
error, and the suite is full of pipes and loopback sockets on fifteen other
threads. The death therefore lands nowhere near the exec, names no test, and
looks like nothing.

Every earlier observation fits without amendment:

- **Not any one ball's tests, and socket-heavy tests raise the rate.** The
  clobber is constant; what varies is how many closable readers the rest of the
  run has.
- **Serialized it does not reproduce.** One test at a time is one writer at a
  time, and the arm that clobbers runs late enough in most orderings that
  nothing follows it down a closed pipe.
- **The `SigIgn` watchdog was reading a true thing about a false subject.** The
  bit is set for the whole run *until this arm executes*, and the suspicion it
  cleared — a substrate CLI's `main` resetting the disposition — was correct to
  clear. The reset is std's own, on a path no substrate crate is on. That is
  the one line of the original write-up to strike: the multiplex ARMS are
  innocent; a multiplex TEST was not.

Direct evidence rather than inference: a `bpftrace` on
`syscalls:sys_enter_rt_sigaction` filtered to `sig == 13` and to threads of a
live process (`pid != tid`, which excludes every forked child doing its own
lawful reset) caught exactly one in-process call per run, every run, with the
stack `__libc_sigaction < signal < std…Command::do_exec <
std…CommandExt::exec < yog::multiplex::lernie::perform < test::run_test`.
`strace` never saw it: bounded to the signal syscalls it perturbed the timing
enough that eight runs stayed clean.

## The fix

`crate::git_env::exec` — the crate's one `exec`, beside its one fork. It
returns only on failure, carrying the failure, and restores the disposition
before returning; `sys::ignore_sigpipe` is the third confined `unsafe`. The
repair belongs at the boundary and not at the call site for the same reason
the git-env scrub does: a contract a caller has to remember is a defect nobody
sees until it fires. `rules/no-bare-fork.yml` gained `exec` as a fourth verb
with its own fixture, so a second bare exec cannot be added silently.

`a_failed_exec_leaves_sigpipe_ignored` pins the property rather than the
mechanism: after the arm returns, a write to a `UnixStream` whose peer is
dropped must be a `BrokenPipe` error. A regression does not redden that test,
it deletes the run — which is the shape being fixed, and the honest failure
mode for an invariant whose violation is a death.

**Residual, stated rather than hidden:** the window between std's reset and the
repair is one failed `execvp`. In production it is single-threaded and above
eframe, so nothing can write into it. Under test it is ~10 µs against a ~30 s
run, twice — the flake is reduced by orders of magnitude, not proven to zero,
and only `CommandExt::exec` not clobbering in the first place could do that.

Independent reproduction from another ball (bl-269a), filed as duplicate bl-8b0f
and folded here rather than worked twice. Two things it adds:

**A named prime suspect.** Nothing in `src/` calls `libc::signal(SIGPIPE, …)` —
`rules/unsafe-outside-sys.yml` holds the whole crate's `unsafe` inventory to one
file and that file never touches SIGPIPE — so the restorer is not yog's own
source. The candidate to check first is the embedded substrate: brazen's `bz`
binary restores SIGPIPE in its own `main` (brazen arch §5.8), and yog links
brazen with the `native-host` feature. The question is whether any in-process
path yog links reaches that restore. After that: a linked C dependency's
initializer, or a test that forks without exec'ing.

`src/bz_host.rs` states the reliance being violated, verbatim: *"yog never
resets SIGPIPE — the disposition is `SIG_IGN`, so a closed stdout surfaces as a
`BrokenPipe` write error that brazen's own `ExitClass::from_io` maps to the same
141, and restoring it would need an `unsafe libc::signal` outside the one
sanctioned site"*.

**Where it dies.** Both captured runs died in the `wire::*` block — the socket
and spawn-heavy region — at 2427 and 2504 of ~2622 tests: after
`wire::server::tests::an_unbindable_address_refuses` / `wire::seat::tests::*`,
and after `wire::host::exec::tests::a_tools_own_failure_is_its_verdict`. A write
to a closed TCP socket raises SIGPIPE on the same terms a closed pipe does, so
the wire's own sockets are as good a candidate as any child's stdin. Note the
test names locate the REGION, not the culprit: libtest prints on completion, so
the test that actually died prints nothing.

Rate on a second box: 2 of 3 on `--lib`, 2 of 4 on a full `cargo test` —
load-sensitive, not deterministic. Confirmed independent of bl-269a's signal
work by re-measuring with `--skip engine::serve --skip engine::stop --skip
world::tools::tests::seed` (no line of that ball's production code executing):
still 2 failures in 3 runs.
