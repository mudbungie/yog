`src/wire/provision/openssl.rs`'s `san` takes ONE host and derives the whole
subject alternative name from it:

    pub(super) fn san(role: Role, host: &str) -> String {
        let loopback = format!("IP:{LOOPBACK}");
        match role {
            Role::Server if host.parse::<IpAddr>().is_ok() => {
                let named = format!("IP:{host}");
                if named == loopback { named } else { format!("{named},{loopback}") }
            }
            Role::Server => format!("DNS:{host},{loopback}"),
            _ => format!("DNS:{}", role.common_name()),
        }
    }

So a server certificate covers **either** a name **or** an address, never
both, plus `127.0.0.1`. `WIRE_HOST` is one string and there is no second
reading that could add to the list.

**The client makes that binding load-bearing.** The seat derives its
`ServerName` from whatever the address file says — an address that parses as
an IP becomes `ServerName::IpAddress`, anything else a `DnsName` — and rustls
then checks that name against the SAN. The address an operator provisions is
therefore not a free choice of route: it must be spelled the one way the
certificate was minted for.

**Where that bites, and it is the ordinary case.** A box on an overlay network
has a resolvable name, an overlay address and a LAN address, and different
clients reach it different ways. A client that cannot use the name's resolver
— a virtual device whose DNS is its emulator's, a container with its own
`resolv.conf`, anything off the overlay's DNS — has no lawful spelling left:
the name will not resolve for it, and the address is not in the certificate.
The connection fails verification rather than failing to route, so the error
names trust where the fact is reachability.

**The remedy today is destructive, which is the actual defect.** `mint`
refuses to overwrite:

    if dir.join(ANCHORS).is_file() && !force {

and `FORCE=1` re-founds the **CA**, not just the server leaf — every client
leaf already issued and carried to another box stops verifying. The module
says so itself: *"A rotation distrusts every certificate already issued, so it
stays the operator's deliberate `FORCE=1`."* Adding one address to a running
engine's certificate should not cost every enrolled client, and today it does.

The `WIRE_LEAF` act is the precedent for the shape the fix wants: an act over
a trust root that already exists, founding no CA and touching no other leaf.
A server leaf re-issued under the same CA is the same kind of act, and it is
the one artifact whose replacement strands nobody — clients verify the CA.

Two things are wanted and the second is the cheaper half:

- **`WIRE_HOST` should carry more than one entry** — a list, each parsed as
  address-or-name exactly as the single one is now, so a box reachable three
  ways says so once. `127.0.0.1` stays appended, unchanged.
- **Re-issuing the server leaf should not be a rotation.** Whatever the
  spelling, the guard in front of it should be the one in front of
  `WIRE_LEAF`, not the one in front of the mint.

Not asked for here: SAN editing after the fact, a certificate library, or any
in-channel act. REMOTE §1.4 is untouched — this is entirely about what the
operator's own out-of-channel mint can be asked to write.

Found while driving a virtual device against a deployed engine: the device's
DNS could not resolve the engine's name, and its address was not in the
certificate, so the material could not be authored at all without touching
the CA.
