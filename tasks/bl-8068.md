CLOSED DIAGNOSIS (message-medic, 2026-08-02, verified against real bytes).

The failing call: agent **energize** (dev workspace, id `<agent-id>`, `~/.local/share/yog/workspaces/dev`) ran its `message` tool with `{"agent": "marbling-lake", ...}` (messages/004) after the operator asked "send a message, any message, to marbling-lake" (messages/003). The recorded is_error result (messages/005-tool.json):

    lernie message: no agent "marbling-lake" in this workspace — a message is
    addressed to an existing agent, by id or unique name (ARCH §2.11)

Root cause — **operational, not a lernie bug**: the dispatching yog binary predated bl-08f2 (316fef8), so `--name` was never passed at fire. The world ops log (`~/.local/share/yog/world/state/yog/ops.jsonl`) shows both fires with NO `--name`:

- 21:59:37Z `lernie prompt <dev-ws> "You are marbling-lake.\n\n…"` → agent `<agent-id>`, **no `name` file at all** on its ref (pre-0.0.4-embedded build).
- 22:34:26Z `lernie prompt <dev-ws> "You are energize.\n\n…"` → agent `<agent-id>`, `name` blob present but **empty** (e69de29 — the 0.0.4-embedded lernie writes an empty blob for an unnamed dispatch).

So "marbling-lake"/"energize" existed only as `You are <x>.` prose in goal.md — yog's display ladder rendered them (legacy rung), but lernie resolution (id, else unique *stored* name) correctly found no such agent. Messaging "energize" by name would fail identically. bl-08f2 landed 2026-08-03T04:32:54Z, hours AFTER these dispatches; ~/.local/bin/yog (mtime 2026-08-02 22:35Z) also predates it. lernie 0.0.4's resolution behaved exactly per contract — **no lernie ball filed, no upstream half owed**, no release ordering to record, yog's pin untouched. bl-aca4 (name is an exposed dispatch parameter; omission auto-mints inside lernie) removes the *creatable* unnamed agent entirely, so the class dies upstream on its own; only pre-aca4 agents still on disk can reach this rung.

Operational remedy: rebuild/reinstall yog from ≥316fef8 and relaunch (mind the `make reload` pidfile gap — a hand-launched yog never reloads); pre-fact agents can only be addressed by id, or re-dispatched to gain a name fact.

**The recurrence stopper delivered by this ball** — an unaddressable name never leaves yog as if it were addressable, on either face:

- `Agent::name_display_only()` — the `name` blob is absent *or* empty (`git_tree::cmd::ref_name` folds emptiness into absence, so the energize case is covered) while the goal-stamp parse is present. `ConvRow.name_display_only` carries it to the view models.
- **Human face:** `theme::NAME_DISPLAY_ONLY` hovers the §11 conversation-row title and the centre header — it says the name is display-only and names the agent id as the address that works.
- **Machine face (CORRECTION, 2026-08-11):** the earlier draft of this diagnosis claimed "Boundary JSON needed no change: it already emits only the stored fact as `name`". **That was wrong against the tree** — `ConvRow.name` is `Agent::name_fact()`, which folds the legacy goal-stamp parse in, and `boundary::reply::rows::conv_row` emitted it verbatim under `name`. So a *peer agent* reading `conversations` over the control boundary — the exact reader that failed here — was still handed "marbling-lake" under the key it feeds to `message`. Fixed: `conv_row` withholds `name` when the row is display-only; `display` still carries the §3.3 ladder's answer and `root_id` is the address that works.
- yog's own composer was never at fault: it targets `message` by `agent_id` (`shell::input_bar` → `shell::dispatch::message`), and only the *label* uses the display ladder (bl-2f30).

DESIGN §3.3 amended alongside, stating both faces.
