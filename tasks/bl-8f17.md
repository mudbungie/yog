## Status: OPERATOR DECISION. Reported, not acted on.

## The fact

`providers.yaml` is authored into a workspace's **first config commit** at
`lernie new` and frozen there (lernie ARCH §2.2 — control is read from the governing
config commit, never from a worktree file). Nothing in a pin bump rewrites it. So the
grant a workspace was born with is the grant it keeps.

All five existing workspaces under `~/.local/share/yog/workspaces/` were created
under lernie ≤0.0.2, whose shipped template granted the `worker` role only:

    tools: [bash, read_file, load_skill]

lernie 0.0.3's `[bl-38c2]` widens the shipped template's worker grant to five tools
(adding `message` and `dispatch`) — *"shipped template grants the worker role only
[bash, read_file, load_skill] — no root agent can message a sibling or dispatch a
child out of the box"*. That change reaches **new** workspaces only.

Affected: `<workspace>`, `<workspace>`, `<workspace>`, `native-album`,
`<workspace>`.

## Why it matters

This is the root cause behind the two reproduced conversations in bl-55b1
(`<agent-id>`, `<agent-id>`), where agents asked to
message a sibling burned 5+ steps discovering they had no `message` tool. The
descriptor-visibility half of that confusion is fixed in 0.0.3 (the dispatch commit
now prunes `descriptions/**` to the role's grant, so an `ls descriptions/tools/`
answers "what can I call"). The *capability* half is not: on these five workspaces
that `ls` will now correctly show three tools, and the agent still cannot message.

## The two options

1. **Hand-edit** each workspace's `config/default:providers.yaml` to the five-tool
   grant. Authoring a new config commit is what `lernie config` does; the new commit
   governs conversations forked after it, not ones already running.
2. **Recreate** the workspaces. The operator declared the current world state
   disposable play-state on 2026-07-28 (recorded in bl-56bd), which makes this
   acceptable — but that declaration is two days old and predates whatever is
   currently in them, so it should be re-confirmed rather than assumed.

## Not decided here

Which option, and whether all five or only the ones still in use. Both touch live
operator state; neither is reversible by re-running it.

## Resolution (2026-08-01): option 2, executed as a full wipe

Operator re-confirmed disposability mid-session ("you're in fact allowed to wipe really everything out here. I don't have any useful work in yog"). All five workspaces (`<workspace>`, `<workspace>`, `<workspace>`, `native-album`, `<workspace>`) deleted, following yog's own `src/delete/mod.rs` plan by hand (the verb is GUI-only): no bound-ball claims to release, `ui.json` `seen` keys pruned to empty, workspace directories removed. The <workspace> storm evidence was bundled first under bl-4fb1 (`~/<workspace>-storm-20260728.bundle`).

No hand-editing of frozen grants was needed or done: any future workspace is born from the installed lernie template and inherits the current worker grant (five-tool as of 0.0.3).
