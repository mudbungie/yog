## Reproduction

Create two ready balls in an isolated project: `<high>` at priority 1 and `<low>` at priority 5. Arm `/fleet 1`. Arrange for the first drone to settle stopped before closing `<high>`.

With the arm-created default, which omits `lease_min`, the board remains full forever: `<high>` is claimed by the stopped drone and `<low>` remains ready.

Then set a valid zero-minute lease to compress the same state machine. Two sweep cycles produce:

```text
bl claim <high> --as <workspace>
yog-fleet spawn <high> <conversation-a>
bl unclaim <high> --as <workspace>
yog-fleet reap <high> <workspace>
bl claim <high> --as <workspace>
yog-fleet spawn <high> <conversation-b>
```

The lower-priority ball never runs. Any positive lease repeats this more slowly: reaping returns the same top-priority ball to ready, and the next tick selects it again.

## Contradiction

`docs/STORIES.md` says:

> “One move per tick, and no memory between ticks. A tick reaps or spawns, once, and stops. It keeps nothing: the next tick reads the world the last one left, so a missed tick, a crashed yog and a second instance all converge, and no board state can make the loop storm.”

`src/fleet/pilot/plan.rs` plans `reap(...).or_else(|| spawn(...))`; spawn always takes the board's first ready ball. There is no failed-attempt, retry-count, cooldown, or quarantine fact.

## Impact and required invariant

The default wedges capacity; enabling recovery turns the wedge into unbounded sequential retries, conversations, ops rows and possible spend while starving other work. Fleet policy needs a durable, derived answer for a failed attempt that bounds retries and allows later ready work to progress.
