The provider catalog offers `claude-code`, and `/model worker claude-code sonnet` succeeds and advances the model configuration. The next worker start fails before any network call.

`/steps` reports `framing:"failed"`. The encoder error is:

`claude_code carries no tool declarations; use the anthropic row for tools`

The architecture promises: `Nothing offered is unroutable.` It also reasons that a custom model may be unserved `but never an unroutable one, because the row beside it is still brazen's.` That premise is false: row existence does not establish request-shape compatibility.

The picker validates only provider-row existence and model-ID grammar. Yog always injects at least its clients tool, and lernie carries injected tools into every canonical request. The authoritative brazen `claude_code` encoder intentionally rejects every request with nonempty tools. The accepted provider-role mapping is therefore structurally unable to produce a yog worker turn.

Acceptance: before either configuration file changes, the terminal and GUI pickers refuse any row whose authoritative protocol cannot carry the yog/lernie request shape and explain the incompatible capability. Capability must come from the provider protocol, not a hard-coded row name. Cover an otherwise empty role tool list, custom model IDs, terminal and GUI paths, and a compatible provider control. Amend the false row-exists-implies-routable design claim. If brazen exposes no authoritative capability projection, track that upstream seam rather than create a second protocol table in yog.
