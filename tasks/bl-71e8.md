Diagnosed from the operator's conversation with agent **energize** (dev workspace,
`<agent-id>`), 2026-08-02.

## The defect

A child agent's **result deposit** is rendered by the transcript as an ordinary
peer message, and when the deposit carries an epitaph and no body it renders as
a blank line:

    <agent-id>-<agent-id>: (no message body)

Two such rows landed in energize's transcript (`messages/027`, `messages/040`),
both `epitaph: stopped` with an empty body. The operator sees nothing; the
agent's next utterance ("That notification confirms the first inspection
subagent is now **stopped**") has no visible cause on screen.

The epitaph IS the message of a body-less result deposit (lernie ARCH §2.6 — a
`stopped`/`died`/`budget-exhausted` deposit is defined as an assertion with no
body; `terminal.rs`: "it reads the branch tip as the terminal ref and deposits a
`stopped`-epitaph result with no body"). Yog already parses it —
`inboxview::parse_deposit` returns `Deposit.epitaph: Option<Epitaph>` and
`inboxview` renders it in the Inbox tab — but `transcript::classify` keeps only
`sender` + `body` and throws the epitaph away, so the one fact the row exists to
carry never reaches the screen.

DESIGN §11 currently ratifies the drop, verbatim:

> The envelope's asserted fields are dropped from the parsed view exactly as the
> model-id line and the `tool_use_id`s are; the Raw toggle still shows them
> verbatim.

and

> A delivered message whose body is empty once the envelope is off — a result
> message that asserts an epitaph and nothing else (§2.6) — previews `(no
> message body)`, the same arm the no-content-blocks model message already
> takes.

That reasoning holds for `from:`/`deposited_at:` (re-asserted by the filename
and the file order) but not for `epitaph:`, which nothing else carries. Fix the
doc with the code (AGENTS.md: "never implement a deviation: fix the doc").

## Deliverable

1. `EntryKind::Delivered` carries the parsed `epitaph` (already available from
   the one envelope reader — no second parse).
2. §11 row: an epitaph-bearing delivered message reads as the *result deposit*
   it is, naming how the child ended, in both the body-less case (replacing
   `(no message body)`) and the body-bearing case (a final-response deposit
   keeps its body and gains the label). A peer/user message — no `epitaph:` in
   the envelope — renders exactly as today.
3. Amend DESIGN §11 at both quoted passages: `epitaph:` is the one envelope
   field the parsed view keeps, and why (it is asserted nowhere else).

## Why it matters beyond the blank row

The same conversation shows the operator asking, at the end:

> are you responding to me with info intended for a subagent?

Inter-agent result traffic and the operator's own exchange are one undifferentiated
row sequence. Labelling result deposits is the display-side half of that; the
routing half is lernie's (filed separately: a child's terminal response deposits
to its dispatcher even when the turn was prompted by someone else).

Burden check: no dispatches → no epitaph-bearing deposits → the transcript reads
exactly as it does today.
