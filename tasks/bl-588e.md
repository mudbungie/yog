The fact: confinement's writable set (bl-bca4 + bl-34b1) is {workspace, world root, bound project, /tmp}, and ops.jsonl lives under the world root — writable. Both the §4.11 writable root and bl-34b1's bound-project member derive from 'the last bl claim row on yog's own ops.jsonl', so a drone that can write the trail can name any directory as its project and own its own adjudication. Not new with bl-34b1 — the writable root has read the same rows out of the same writable place since bl-fec8 — and VISION §4.11 item 8 scopes adversarial evasion out by construction: this layer bounds the write-ACCIDENT class.

The question for the operator: accept the stated scope (close this with the ruling recorded — the doc already states it), or close the hole by siting ops.jsonl outside the writable set. The latter is a real design change: the trail is written by yog's own executors AND read at spawn time, so moving it means either a read-only bind of a trail dir that yog's unconfined side writes, or splitting trail-write from trail-read homes — each touches §4.2's 'everything that mutates a substrate writes a row' and needs its own consistency argument. If ruled 'close it', file the implementation ball off this one with the chosen shape.
