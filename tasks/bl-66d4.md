**Follow-on to bl-1462**, filed from the foot's side after thrall landed its
half (thrall bl-2d78).

## Where bl-1462 left it

bl-1462 closed the two shapes the engine can see: a second concurrent
follow-class read under one identity is refused, and an advertisement that
would CHANGE the set in force is refused while that client holds a parked read.
That covers the whole of an idle foot's life, because an idle foot is parked.

The window it cannot cover is the one the foot opens itself. A foot is
**absent** while it executes — one connection per ask, held only while waiting
— so during a tool's runtime it holds no parked read, `serving()` is false, and
a second connection bearing the certificate may replace the set with no
refusal.

thrall's half (bl-2d78) is to re-assert its set at the end of every hand-off,
which bounds that window to one tool's runtime instead of forever. It costs an
idle foot nothing: no hand-off, no gesture.

## What is still missing

The foot **heals silently**. `advertise` is answered `{"kind":"advertised",
"ok":true}` whether the engine wrote the document or found it identical and
compared. `registry::tools::store` already computes exactly the fact that is
missing — it returns `bool`, "did it write" — and `dispatch::advertise` throws
it away.

So a foot re-presenting an unchanged set and a foot restoring a set some other
connection blanked receive the identical answer, and the second event — which
is two processes claiming one machine's name — reaches no log on either side.

## The ask

Carry the bool the store already returns. A `stored` (or `wrote`) field on the
`advertised` reply, false on the ordinary re-presentation and true when the
document changed. A foot that presents once per channel sees `true` on the
first and never again; a `true` on any later re-assertion is the machine
learning it was disarmed, and the sentence it prints is the whole remedy.

It is one field on one reply and no new verb, but it IS wire surface, so it is
REMOTE §5.1's call and a PROTOCOL bump if the field is required rather than
optional-absent-reads-false.

## Interaction with bl-0a74

bl-0a74 asks for a redial loop around each tool-host channel. Two notes for
whoever takes it, both consequences of bl-1462's reader slot:

- A redial re-presents the set on the new connection, so a redial loop is a
  second, coarser instance of the same self-heal.
- The reader slot is released "however the read leaves", and a read parked on a
  TCP connection that has died does not leave until the engine tries to answer
  it. A redial inside that window is refused by the one-reader guard, naming
  the client. A redial loop must therefore treat that refusal as **retryable**
  — it is the stale predecessor, not a rival — or the first network blip
  becomes a permanent stop, which is the very defect bl-0a74 exists to fix.
