## §11 amendment (docs/DESIGN.md, 'Keyboard bindings' replacing 'Keyboard navigation')
Two rules decide what gets a key, so the table never grows by taste:
1. **A key fires a verb on the current target.** The target is the one the selection already names — the focused conversation (up/down), its bound ball, the focused workspace. Nothing needs a second cursor.
2. **Choosing among several targets stays a pointer gesture.** A pick is what a pointer is for: Move's destination workspace, the overflow menu's entries, which descent-tree member or ops row to open, which step record to drill into. These are *picks*, not a bindings gap.

The table (arrows/digits unchanged, twelve keys added):

    i  composer focus (whichever composer is painted, target unchanged)
    n  + conversation (clear the selection, then i)
    w  + workspace (the deliberate sphere-wall mint, §3.4)
    s  > Start the balls section's FIRST ready row (rule 2 keeps the pick a click)
    x  Stop the selected conversation (+children per its checkbox)
    f  Flush the inbox — lernie scan on the focused workspace
    c  Close the focused conversation's bound ball
    r  Release (unclaim) that same ball — Move stays a click (its destination is a pick)
    b  fold/unfold the balls section (the persisted §4.1 collapse)
    g  organizing view: recent <-> by ball
    a  activity accessory: collapsed <-> expanded
    Enter  fire the pending start goal (Send, detached prompt)
    Esc    drop the pending start goal (Cancel)

Recorded verbatim in §11: bindings are suppressed while a text box holds the keyboard (egui wants_keyboard_input), so a bare letter is lawful and **Escape then i** is the one deterministic 'put the cursor in the composer' idiom from any state. §12's module map gained src/shell/keys.rs and a src/keymap row.
