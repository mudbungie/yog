Found while closing bl-848f under a bl-b7dc monitor run. The close was refused,
and so was every other `bl` op — create, update, claim, close — because
`scripts/yog-leak-gate` scans the WHOLE store checkout at `<op>.post`, not the
one task file the op touched. One polluted body is a repo-wide stop, exactly the
way a red pre-commit on main is.

The refusal, verbatim except for the finding itself, which is folded to the
house synthetic root because quoting it as printed re-publishes it (that fold is
worth noticing: the gate refuses a body that quotes the gate):

    error: leak-scan found material that must not be committed:
      tasks/bl-3aa1.md:71  [home-path]   /home/u/
           an absolute path under a home directory — it names an account, and it is a portability bug besides. Use a synthetic root (/home/u).
    bl-leak-gate: the close is REFUSED and the store commit rolled back — the
      ball body above would have published that material to <repo>'s task ref.
      Rewrite the text (cite the shape, not the instance: /home/u, not a real
      account path) and run the same command again.
    plugin bl-leak-gate aborted the op (exit status: 1)

The line was a CORRECTION appended to bl-3aa1's body naming the local bundle
that holds the pre-publication history. **Already fixed in passing** — the home
root is folded to `~`, which is how the code block two lines below it in the
same comment had always written it, so the sentence keeps its whole meaning. The
store took the update and ops flow again. What is filed here is the class, not
that one line.

Also seen once and then gone: a second finding on `tasks/bl-89f5.md`, a task id
`bl show` does not resolve and that no store commit ever carried. That is a
concurrent op's in-flight body being scanned and rolled back — evidence the gate
reads a shared checkout rather than a per-op snapshot, which is worth
confirming: one agent's refused create should not be able to appear in another
agent's scan.

Three things to decide, none of them assumed here:

1. **Is the blast radius the design?** Scanning the whole store is why no op can
   publish a polluted ref, which is right. The cost is that the author who
   writes a bad body is never the one who discovers it — every other builder
   rediscovers it, mid-close, after their own gate has already run. A `<op>.pre`
   scan of the op's OWN text would fail the author at the moment of writing;
   AGENTS.md's reason for `post` ("a `pre` plugin runs before `bl` writes the
   task file, so it would scan the previous state") argues against scanning the
   STORE early, not against scanning the AUTHOR'S OWN INPUT early. Two scans
   with different jobs may beat one scan with two.
2. **How did it get in?** AGENTS.md is explicit: "Wire it only once the store
   scrub (bl-dd1d) has landed." A live body still carrying a home path means
   either the scrub missed a body edited after it ran, or the body was written
   through a path where the gate is not in the schedule.
3. **The refusal names the file but not the remedy's owner.** The blocked op
   belongs to one agent and the polluted body to another, who may hold it
   claimed. Editing someone else's ball to unwedge your own close is what the
   situation forces; the foreign-edit refusal ("close refuses a task file you
   haven't seen") makes that recoverable, but nothing says so at the point of
   refusal.
