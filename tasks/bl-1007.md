Found while closing bl-848f under a bl-b7dc monitor run. The close was refused,
and so was every other `bl` op — create, update, claim, close — because
`scripts/yog-leak-gate` scans the WHOLE store checkout at `<op>.post`, not the
one task file the op touched. One polluted body is a repo-wide stop, exactly the
way a red pre-commit on main is.

The refusal, verbatim except for the finding itself, which is folded to the
house synthetic root because quoting it as printed re-publishes it (that fold is
worth noticing: the gate refuses a body that quotes the gate):

    error: leak-scan found material that must not be committed:
      tasks/bl-3aa1.md:71  [home-path]   /home/u/
           an absolute path under a home directory — it names an account, and it is a portability bug besides. Use a synthetic root (/home/u).
    bl-leak-gate: the close is REFUSED and the store commit rolled back — the
      ball body above would have published that material to <repo>'s task ref.
      Rewrite the text (cite the shape, not the instance: /home/u, not a real
      account path) and run the same command again.
    plugin bl-leak-gate aborted the op (exit status: 1)

The line was a CORRECTION appended to bl-3aa1's body naming the local bundle
that holds the pre-publication history. **Already fixed in passing** — the home
root is folded to `~`, which is how the code block two lines below it in the
same comment had always written it, so the sentence keeps its whole meaning. The
store took the update and ops flow again. What is filed here is the class, not
that one line.

Also seen once and then gone: a second finding on `tasks/bl-89f5.md`, a task id
`bl show` does not resolve and that no store commit ever carried. That is a
concurrent op's in-flight body being scanned and rolled back — evidence the gate
reads a shared checkout rather than a per-op snapshot, which is worth
confirming: one agent's refused create should not be able to appear in another
agent's scan.

Three things to decide, none of them assumed here:

1. **Is the blast radius the design?** Scanning the whole store is why no op can
   publish a polluted ref, which is right. The cost is that the author who
   writes a bad body is never the one who discovers it — every other builder
   rediscovers it, mid-close, after their own gate has already run. A `<op>.pre`
   scan of the op's OWN text would fail the author at the moment of writing;
   AGENTS.md's reason for `post` ("a `pre` plugin runs before `bl` writes the
   task file, so it would scan the previous state") argues against scanning the
   STORE early, not against scanning the AUTHOR'S OWN INPUT early. Two scans
   with different jobs may beat one scan with two.
2. **How did it get in?** AGENTS.md is explicit: "Wire it only once the store
   scrub (bl-dd1d) has landed." A live body still carrying a home path means
   either the scrub missed a body edited after it ran, or the body was written
   through a path where the gate is not in the schedule.
3. **The refusal names the file but not the remedy's owner.** The blocked op
   belongs to one agent and the polluted body to another, who may hold it
   claimed. Editing someone else's ball to unwedge your own close is what the
   situation forces; the foreign-edit refusal ("close refuses a task file you
   haven't seen") makes that recoverable, but nothing says so at the point of
   refusal.

**Landed (Quoin).** The three questions, answered against the tree.

**1. Is the blast radius the design? No — the scope was.** The gate now scans
what the OP publishes, not what the store carries: `scripts/leak-scan.sh` grows
a `--commit REV` mode (the blobs REV adds or rewrites, read out of REV, plus
REV's message) and `scripts/yog-leak-gate` hands it the `commit` field of the §7
post payload. A tree scan is the right question for a commit hook — the tree IS
your change — and the wrong one for a shared, long-lived checkout many agents
write, where it judges every agent for every other agent's text. Fail-closed on
a payload naming no store OR no commit, each refusal naming the unwire.

Two scans with different jobs, as the ball proposed, but the split is not
pre/post: it is local-prevention vs remote-enforcement, which AGENTS.md already
drew. The author's own text is refused at the moment of writing; the
standing-state question — what the ref carries in total, including whatever
predates the gate — stays with the daily `.github/workflows/store-scan.yml` over
the whole published ref, where a hit's remedy (a history rewrite) lives anyway.
A `pre` scan of the op's own input was not needed to get that: `post` already
has the op's text, and only `post` has it in a form (a commit) that cannot be
confused with a neighbour's in-flight edit.

Considered and rejected: keeping the whole-store scan as a non-fatal nag on
every op. It reintroduces the noise that gets a gate unwired, and it duplicates
a question CI already owns.

**2. How did it get in?** Not resolved here, and it does not need to be: the
scoped gate makes the answer local. The second symptom the ball recorded — a
finding on a ball id no store commit ever carried — is explained and dissolved
by the same change: the old scan read a checkout other ops write concurrently
(worktree/index), so one agent's in-flight or rolled-back body appeared in
another agent's scan. The commit is the only text that is unambiguously yours.

**3. The refusal names the file but not the remedy's owner.** Moot for the
common case: the file it names is now always your own commit. The refusal says
so ("the text above is THIS op's own").

**Gained in passing:** the message is scanned. A `-m` note lands in NO file — it
is the whole of what a close writes to the journal — so no file-based scan,
whole-store or not, had ever read it, though AGENTS.md governs it like a body.

**What is NOT in yog, and cannot be.** `bl-leak-gate`, the machine-layer plugin
in the operator's `~/.config/balls/plugins.toml` (balls bl-053a), runs
`<project>/scripts/leak-scan.sh` over the store of every opted-in project on the
box, and it runs FIRST — prepended at the xdg layer, ahead of the landing's
`yog-leak-gate`. Bare, that invocation is still the whole-tree scan, so the
wedge persists until it passes the same scope. The change it needs is one line:
read `commit` off the payload (its `field` helper already does jq/python3/sed)
and call `"$scan" --commit "$commit"`, keeping its own fail-open posture for a
missing field, since it runs on every store on the box. Recorded in AGENTS.md,
"The task store gate"; the file is not a yog artifact and was not touched.

**Also seen, not fixed:** both plugins are wired on the same six ops in this
checkout (`bl conf`: `bl-leak-gate, yog-leak-gate, ...`), so every op scans the
store twice. Now that the machine layer runs the project's own scanner, the
landing-level `yog-leak-gate` is arguably redundant wiring — a config question
for the operator, not a code one.
