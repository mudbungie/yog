`engine::tests::a_booted_engine_hands_its_window_a_seat_on_its_own_wire`,
`engine::tests::a_window_takes_both_halves_of_the_wire_once` and
`wire::tests::an_unprovisioned_box_founds_its_own_loopback_wire` boot a real
engine, which binds the one fixed port `wire::provision::PORT` on loopback.
A yog window already running on the same box holds that port, so all three fail
with `bind 127.0.0.1:<PORT>: Address already in use` — every run, not
occasionally. The suite is therefore red for exactly as long as the app under
development is up, which means the local pre-commit gate cannot pass and a close
has to lean on an imported remote verdict.

Found while diagnosing bl-3a88 (a different flake, in tool_host::remote). Not
the same class: this one is deterministic and environmental, not a race.

Direction, not a decision: the port is a constant because an operator dials a
known address (REMOTE §8, `wire/provision.rs`), but a *test* engine has no
dialler but itself. Either the test world founds its own address on an ephemeral
port (bind port 0, read the bound port back, write it to the world's address file
the client already reads) or the boot takes the address from the world rather
than the constant. The constant stays the default for a real box; the test stops
asserting on a shared machine resource. Same family as bl-e492 — a test
asserting on the host rather than on yog — with a fix one seam away from it.
