While chasing bl-3792 the lib suite failed twice in ~30 full-parallel runs with
a test that no fixture can explain:

    thread 'multiplex::landing::tests::the_repair_spends_no_scalar_config'
    panicked at src/multiplex/landing/tests/world.rs:93:
    found landing: Error { kind: InvalidInput,
                           message: "nul byte found in provided data" }

## What that message is

It is std's, raised by `CString::new` on the way into a spawn: an argument or
an environment entry it is about to hand `execvp` contains an interior NUL.
Nothing the fixture writes holds one. The bytes are TORN, not wrong.

## The tearing party

`set_env` (`src/cli_outbound/sys.rs`) — and its own SAFETY note names the
hazard verbatim:

> `setenv(3)` is not thread-safe — a concurrent `getenv` in another thread may
> read a table this call frees — and that is the whole of why std marks it
> unsafe. Every caller stands at the process edge, single-threaded:
> `world::inhabit` is reached only from `multiplex::dispatch`, which `main.rs`
> calls above clap, above the hatches and above eframe, before this process has
> spawned a thread.

**That argument does not hold under `cargo test --lib`.** The lib binary runs
one test per thread; a test that reaches `world::inhabit` (or `inhabit_space`)
calls `setenv` while fifteen peers are reading the same table — and std's own
spawn path reads it, which is why the corpse surfaces inside somebody else's
`Command`. The note's second paragraph anticipates exactly this and claims the
src-side unit tests reach no folding arm; the evidence says at least one does.

## Why it matters

It is the same class as bl-3792 — a process-global effect performed inside the
shared test binary — and the same cost: a gate that reddens on a test that is
not broken, in a module the failing assertion does not name. It is rarer
(2 in ~30) and louder (a named failing test, not a silent death), so it is the
lesser of the two, but it is undiagnosable from the message alone.

## Where to start

- Enumerate what actually reaches `world::inhabit`/`inhabit_space` from
  `src/**/tests.rs`. The SAFETY note asserts the set is empty; measure it.
- Two shapes for the fix, and they are the two the tree already uses:
  either every reacher moves into an integration binary that owns its process
  env and runs one `#[test]` (the precedent `src/multiplex/tests.rs` states in
  prose for the `bl` and `lernie` arms), or the fold takes `test_support`'s
  `ENV_LOCK` — which only helps against readers that also take it, and std's
  spawn is not one, so the first shape is likely the only honest one.
- The soundness paragraph in `sys.rs` is part of the deliverable either way:
  as written it is a claim about the test tree, and a claim that is false is
  worse than no claim.
