## Operator complaint (2026-08-01, verbatim)

'The way that the conversation should unfold from the agent should be essentially live-populating at every step: thinking, tool exec, etc, but the moment each step is done, it collapses down, until all you get is a single line showing "3150 thinking tokens, 9 inference calls, 14 tool calls" or whatever, which can be expanded to see each step in flight. Each thing gets a fold, and the whole thing rolls up. The experience should show a lot happening while it is happening (stream thinking directly visible, eg), but when it's done and the agent is responding, just one line before the response.'

## Verified code facts (verify again before editing)

- `src/transcript/rows.rs`: one line per block; expansion is DERIVED — `expanded = auto XOR overridden`, auto from two `AutoExpand` knobs (Response expands, Other = thinking/tools contracts). No arrival events; the whole transcript re-reads statelessly each frame (§3.5). Keys are `tx/<entry filename>#<block index>`.
- Live tail is a virtual trailing entry (`src/transcript/mod.rs`, STREAMING_NAME); 'tool in progress' is already a QUERY (committed tool_use with no committed tool_result), never a flag.
- `src/transcript/render.rs` just gained stick_to_bottom (bl-5cdb) — rollup shrinking content composes fine with the tail anchor.

## The design (stay inside the existing invariants — expansion stays a pure function, nothing stored per row)

Two changes, one principle: **in-flight is the operator's show; finished is one line.**

1. **Live steps expand.** A row that IS in flight — the live streaming tail (thinking or text as it streams) and an unresolved tool call — auto-expands regardless of class knobs. Completion (the result/next entry committed) returns it to its class auto-state. No event needed: in-flightness is already derivable per row, so this is one more input to `expanded_for`. Explicit operator override still wins (XOR discipline unchanged).
2. **Turn rollup.** Group the machinery run of a completed turn — thinking blocks, tool calls, tool results, intermediate model text between the turn's start and its final response — under ONE parent row whose line is the aggregate: e.g. `⚙ 9 inference calls · 14 tool calls · 3150 thinking tokens`. Expanding it reveals the per-step rows, each still individually foldable (folds all the way down). The IN-FLIGHT turn is never rolled up — its steps are live-visible per (1). A turn = the maximal run of machinery entries preceding a Response row; derive it in the rows projection, store nothing. Group-row keys must be stable across stateless re-reads (e.g. keyed on the turn's first entry filename).
3. **Aggregate honesty:** state only what the committed bytes carry. Count inference calls (model-output files) and tool calls directly; thinking tokens ONLY if lernie commits usage in the model json — check the canonical blocks; if absent, use an honest measure (e.g. 'N thinking blocks') — never fabricate token counts. (Recall bl-8433: a badge claiming more than the data knows is a filed bug class.)
