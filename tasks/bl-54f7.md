Operator complaint, 2026-08-12, verbatim:

> text doesn't stream back in directly while the model is thinking/writing. yog
> should be reading directly from the stream-in file in the lernie workspace;
> it should be showing the user every character as it lands.

## Operator ruling, 2026-08-12 — the in-memory carve-out, verbatim

> I'm okay with this as a violation of the no-state-in-memory rule explicitly.
> It is purely display: a dead-end.

This **supersedes** the "one fact, one home" constraint an earlier draft of this
ball placed on the implementer. The live tail may hold accumulated stream text
in memory. It does not have to be re-derivable, and it does not have to agree
with a snapshot that has not caught up yet — because nothing downstream reads
it. That is what *dead-end* means here, and it is the whole licence:

- **Nothing may consume the in-memory tail but the painter.** No derivation, no
  query, no `Doing`/`Flight` computation, no ball verb, no boundary reply may
  read it. The moment a second consumer appears, this is no longer a dead end
  and the carve-out is void — the fact would then need a home. Enforce the
  dead-endedness structurally (make it unreachable from the derivation path),
  not by comment.
- **It is superseded by the committed bytes, never merged with them.** When the
  step commits and `NNN-<model>.json` lands, the in-memory tail is dropped
  whole. Do not reconcile the two texts character-by-character; the committed
  entry is the truth and the tail was a preview of it.

## What the carve-out does NOT waive

Precision matters here, because the two rules are easy to conflate:

- Waived: **no state in memory** (the derivation-is-the-only-truth rule).
- **Still absolute: the frame does no IO, and the UI never freezes.** Do not
  read `response.json` inside the render pass. The waiver lets you *hold* the
  text; it does not let you *fetch* it on the UI thread. The shape stays a
  cheap follower running off-thread, publishing into memory the frame paints
  from.

## Where this stands today

The mechanism exists; its **cadence** is the defect. `src/transcript/mod.rs`
already appends the live tail as a virtual trailing entry:

    /// Build the transcript for `agent_id` in `workspace`. When `in_flight`
    /// (the caller's `AgentState::InFlight` — the latest step's `response.json`
    /// fd is still open, §3.5), the folded live tail is appended as a virtual
    /// trailing entry.
    pub fn build(workspace: &Path, agent_id: &str, in_flight: bool) -> Transcript {
        let dir = workspace.join(AGENTS_DIR).join(agent_id).join(MESSAGES_DIR);
        let mut entries = read_messages(&dir);
        if in_flight && let Some(text) = crate::git_tree::streaming_text_from_disk(workspace, agent_id)

and `src/git_tree/streaming.rs::fold_stream` reads the open JSONL with the right
tolerance:

    /// Lines that fail to parse, and events outside the delta seam, are
    /// skipped — partial-write tolerance is structural (the harness may be
    /// mid-line on disk).

So the file *is* the stream-in file the operator means, and yog *does* fold it.
What the operator is watching is the rate: that fold only happens as a byproduct
of a **whole-workspace derivation**, gated behind the §7.2 chain — `Bridge`'s
poll interval, the `DirtySet` announcement, the 100 ms debounce
(`src/app/dirty.rs`), the worker's full re-derive, then `AppModel::refresh`
taking the published snapshot. Characters therefore arrive in clumps at the
watcher's rhythm, and during the *thinking* phase — where no text delta exists
yet — there is nothing at all.

## The ask

The focused conversation's live tail updates at frame cadence and paints every
character as it lands. Nothing else changes rhythm.

## Remaining constraints

- **Re-use `fold_stream`.** The follower supplies fresher bytes to the existing
  parser; it does not grow a second one. The carve-out is about where the
  *result* may live, not a licence to fork the parsing.
- **Scope it to the focus.** Tailing every agent in every workspace at frame
  rate is the version of this that burns the machine. One conversation is open;
  that is the one that streams. Say what happens to the tail when focus moves.
- **Incremental read, not re-read.** "Every character as it lands" at frame
  cadence means an append-only follower holding its offset — re-reading and
  re-folding the whole file every frame is the naive shape and it degrades as
  the response grows. The in-memory carve-out is what makes the incremental
  shape legal; use it.
- **Thinking must be visible too.** The complaint says *"thinking/writing"*.
  `Delta::Thinking` is already folded (`last_delta` tracks it) but the tail
  entry carries `text` only. Decide whether reasoning text streams into the
  tail as its own toned row, or whether the existing thinking indicator is the
  answer — and say which in DESIGN. "Nothing is happening on screen" is
  precisely the complaint, and a `Doing::Thinking` badge that never grows is
  not obviously enough.

## Acceptance

The assertion has to be about **freshness**, not content: bytes appended to the
open step file are on the composed frame within one repaint, with no sweep
having run. A beat that asserts the tail is merely non-empty passes today, with
the bug shipped — see bl-70b8's catalogue of tests that prove nothing, and
bl-f16e on vacuous assertions.

Also assert the dead-end: a test that the in-memory tail is not observable from
any derived surface. That is the guard on the carve-out, and it is the one thing
that stops this becoming a real single-source-of-truth violation later.
