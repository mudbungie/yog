Round-2 install lane, second-box scenario. Engine yog 0.0.46 (PROTOCOL 13) on one container, foot thrall 0.0.10 on another, enrolled foot-grade through `lernie enroll home box2foot foot --into <dir>` and serving.

STEPS, all verbatim:

1. Foot up, tool advertised, routed call answered — the whole leg works:

       clients
         box2foot  present  1 tool
           Whoami  "say which box this is"
       {"invocation":"inv-2","kind":"routed","ok":true}
       {"capture":{"exit_code":0,"stderr":"","stdout":"box=<box2 hostname> kernel=Linux …"},
        "invocation":"inv-2","kind":"routed","ok":true}

2. Kill the foot's process on the far box. Immediately after, the engine still says:

       clients
         box2foot  present  1 tool
           Whoami  "say which box this is"

3. Route another call at the dead foot:

       yog gesture --ws home "/invoke box2foot Whoami {}"
       {"invocation":"inv-3","kind":"routed","ok":true}

4. Read the capture, repeatedly, for two minutes:

       yog gesture --ws home "/capture inv-3"
       {"invocation":"inv-3","kind":"routed","ok":true}

TWO FACTS, and the second is the ball.

Presence DOES clear on its own — within the two-minute watch the row lost `present`, so the connection drop is noticed and this is not a stale-presence leak. Accepting the invocation while the row still said `present` is therefore defensible: absence answers at invocation (bl-bc7c), and a foot that dropped between the read and the post is a race no design removes.

What does not work is the READ AFTERWARDS. `/capture inv-3` answers `ok:true` with no `capture` key and no sentence, and it answers that identically at one second and at two minutes, on an invocation whose foot is gone and whose answer is never coming. The operator has nothing to distinguish "running, wait" from "the box died holding it". Compare the sibling refusal on the same surface, which is excellent and names three causes and the next act:

    {"error":"no invocation \"inv-2\" is in flight; it was answered already, it expired, or
     this engine restarted since it was posted — the box may have run it; read the world
     before acting again","ok":false}

EXPECTED: an in-flight invocation whose client is no longer present should say so — the client name, that it is not connected, and whether the invocation is still held for it or has been abandoned. The engine already derives presence (it cleared the row); the capture read does not consult it.

SEVERITY p3: no data is lost and no wrong act is taken; the cost is that a devadmin operator watching a routed command on a box that just rebooted has no read that says what happened, which is exactly the moment they most need one.
