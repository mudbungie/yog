bl-ae05 built the read path and migrated one surface (clients). bl-adcb migrated two more (the ops trail and the V4 board), wrote the shell's one spelling of a wire read, and gave the acceptance suite a wire it answers itself. What is left is not more of the same work: every read still in process is blocked on one of three named things, and each wants a decision before a build.

1. A read whose subject is a VIEWPORT FOLD the boundary deliberately does not carry.

- The conversation list. `Query::Conversations` answers the all-collapsed list by ruling — folds are filed under views — while the frame paints `visible_conversations(now, expanded)`, and the expanded set is per-instance viewport state. Migrating as-is would delete the unfold.
- The inspector family (transcript, steps, files, step detail, rail, inbox). Each has an exact 1:1 reply, but the frame folds all of them through the rail PIN, and the pin is the same class of fact: `Query::Rail` answers unpinned by ruling, `Query::Files` has a path parameter and no pin, and a pinned Files listing is a git read of the pinned commit that no query spells. The tab build is one function that needs them together, so this is one decision, not six.

The decision: either the boundary gains the fold as a parameter (which is a read naming a seat's own viewport, and the reason it was refused), or the seat keeps folding a wire-fed unfolded answer locally (which asks whether the answer is even the right altitude), or the fold becomes a durable pane fact. Attack it before building it.

2. A read the window addresses BY PATH while the boundary addresses BY NAME.

The workspace tab bar. `Reply::Workspaces` carries name, kind, attention, agents, running — no path — and the tab bar is built from the snapshot's workspace values plus the pin order, with focus itself held as a path. The name/path resolution is the engine's one table; a seat that only ever had names would have to hold focus by name too. That is a coherent change and a wide one.

3. A read with nowhere to paint a refusal, or whose consumer reads it synchronously.

- The decision queue behind the desktop escalation. Exactly 1:1 with `Query::Attention`, but its consumer folds a baseline every frame to decide what is NEW; a frame with no answer would read as everything having departed, and there is no surface on which to paint a refusal. It needs a rule for what an unanswered frame means to the baseline.
- The config family (read config, lineages, models, marks, providers). These are already answered through the boundary, but at CLICK time on the frame thread rather than as standing questions. Their shape is the acts ball's shape — a declaration whose receipt lands later — so they belong with it, not here.
- `focused_conversation` / `Query::Agent` is the one exact 1:1 with no obstacle but blast radius: it is the centre pane's whole input at six call sites, several inside act glue, and a cadence of emptiness on startup blanks the pane. Worth doing, worth doing alone.

Two candidates that are neither blocked nor large, for whoever takes this next:

- The Work tab. `Query::WorkDiff` and `Reply::WorkDiff { attempts, patch }` are exact, the surface is a whole-pane read with a picked file, and it retires two per-snapshot memos that fork git against a project repo.
- Search. It is already off-frame through the model's own searcher, and `Query::Search` answers it; riding the asker instead would retire a whole second asynchronous mechanism.

Not in scope here: the acts (bl-4841), and `Prepared::binding`.
