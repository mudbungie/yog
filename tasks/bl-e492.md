Found while driving the publication sequence (bl-4f96). The repository is now
public and Actions run on free runners, but `make ci` fails there and has
ALWAYS failed there: 30 of 30 CI runs in the archive repository concluded
`failure`, so this is not a regression — it is a gate that was never green
where it counts.

It blocks the release. `.github/workflows/ci.yml` says so in its own header:

    # Gate pull requests too — notably release-plz's own release PR, which must go
    # green before it is merged (release-plz.yml's release job keys off a CI run
    # concluding `success`, and its `workflow_run` filter matches `name:` above
    # exactly, so this workflow's name must stay `CI`).

So no 0.0.2 ships until this is green.

Locally: `1969 passed; 0 failed`. On the runner: `1964 passed; 5 failed`. Every
one of the five asserts something about the machine rather than about yog.

**1. Two confinement tests depend on the host having a git identity.**
`src/boundary/control/tests/mod.rs::World::policy` commits `capability.yaml`
onto `config/default` with a bare `git commit-tree`, and a GitHub runner has no
`user.name`/`user.email` configured, so `commit-tree` writes nothing, the
`update-ref` that follows gets an empty oid, the policy never lands, and
`Policy::read(...).confinement_required` is false. The gate then correctly
answers `Ok(())` and

    let err = confinement_gate(&world.workspace()).expect_err("no layer exists");

panics with `no layer exists: ()`. Failing tests:
`confinement::confinement_required_refuses_every_birth_and_absence_gates_nothing`
(src/boundary/control/tests/confinement.rs:13) and
`confinement::an_attempt_is_refused_by_the_same_gate_a_start_is`. The remedy is
an identity on the harness's own git, the way every other fixture in the tree
already does it (src/test_support/workspace.rs:40 passes `user.email=t@t.local`
and `user.name=T`; src/control/tests/mod.rs:70 sets the GIT_AUTHOR_* env).

**2. Two watcher tests assume a re-created directory gets a new inode.**
Both remove a directory and create it again at the same path, then assert the
inode changed — `src/watch/tests.rs:118` (`assert_ne!(armed.ok(),
replaced.ok(), \"the inode really changed\")`, which fails with
`left: Some(9211169)  right: Some(9211169)`) and
`src/fs_watcher/tests/drift/loss.rs:121` (`\"and re-creating the path does not
re-arm the old inode\"`). The runner's filesystem hands the freed inode
straight back, so the precondition the test needs is not established and the
watcher under test never had a replaced inode to notice. Both tests are RIGHT
about the behaviour they want to prove; they are wrong to hope for it. Replace
the remove-then-create with a **rename over the path**: create a sibling
directory WHILE the root still exists (so its inode necessarily differs), then
remove the root and rename the sibling onto it. That yields "same path,
different inode" on every filesystem, deterministically — and it is the more
faithful reproduction anyway, since a re-primed clone is materialized beside
its target and moved into place.

**3. The icon artifact test asserts exact pixel equality against a rasterizer
that dispatches on CPU.** `theme::icon::tests::artifacts::
every_checked_in_png_decodes_to_the_pixels_the_generator_makes`
(src/theme/icon/tests/artifacts.rs:37) compares the checked-in PNG's decoded
pixels to `rgba(size)` generated at test time. On the runner exactly one
channel of one pixel of yog-16.png differs by one: the file holds
`12, 99, 42, 25` where the runner's generator makes `12, 99, 41, 25` — a blue
channel off by one at alpha 25. tiny-skia selects its SIMD kernels at runtime,
so two CPUs round one nearly-transparent pixel differently; Cargo.lock cannot
pin that away. The test's own docstring already states the contract it means to
hold — "only the picture is the contract" — so the fix is a per-channel
tolerance of 1, which still catches every geometry or palette change while not
claiming a bit-exactness the rasterizer does not offer.

Done when a CI run on `main` concludes `success` on both the linux and macos
jobs, with the local suite still green.
