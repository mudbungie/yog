Split out of bl-e47b's broken-board investigation (see that ball's journal for
the full reproduction).

bl-e47b fixes the CAUSE: yog's world left `XDG_CONFIG_HOME` ambient, so balls'
seed template resolved to the operator's `~/.config/balls/default-config/`,
which on this box is a stale copy naming the retired plugin `tracker` (renamed
`bl-tracker`, balls bl-27bf). Every entry pruned at seed, so every landing yog
founded wired ONLY `bl-delivery` — no `bl-tracker` at any phase and no `show`
hook. Consequence: yog's balls stores never fetch and never push (create /
claim / close / unclaim / update / prime / sync all lost their tracker phase),
and `bl show <id>` prints no worktree line.

What bl-e47b does NOT fix: the landings already founded in the live world.
A landing's committed `config/plugins.toml` is seeded ONCE. `bl prime` rebinds
the schedule's names to sibling binaries but never prunes or rewrites it
("capabilities change only by `bl install`, never a re-prime", balls seed.rs),
and balls' own rename convergence is LANDING-only by an explicit boundary
decision — "an old name in the XDG layer is the user's file (the dispatch
notice stays its cover)", balls converge.rs. Neither reaches a landing that was
seeded EMPTY: there is no retired name left to converge, just an absent one.

So after bl-e47b every new clone is correct and every existing one stays
silently local. Decide and implement the repair path. Candidates, in the order
they look least bad:

1. Nothing in yog — document that a broken world is repaired by deleting the
   affected clone bundle under `<world>/state/balls/clones/<pct-enc-path>/` and
   re-priming. Cheapest; loses nothing durable (the store is a checkout of a
   branch, the landing is config), but it is an operator instruction, which is
   the thing yog exists to not need.
2. An upstream balls ask: make `bl prime` converge a schedule that is missing
   first-party entries the current seed default wires, the same way it converges
   a retired NAME. Correct home for it (single source of truth is balls' seed
   default), and it repairs every box, not just yog's.
3. yog drives `bl conf set <op>.<phase>` for the missing entries at prime — a
   second implementation of balls' seed default living in yog, which is the
   duplication bl-e47b was told not to commit. Named here only to be rejected.

VERIFY BEFORE ACTING: check whether the live world's landings are in fact
tracker-less (`bl conf` inside the world names the schedule and its layers)
rather than trusting this description. Do it against a copy or a scratch world,
never by mutating the live one.

Also, not yog's file and not this ball's to edit: this box's
`~/.config/balls/default-config/plugins.toml` is stale for the operator's OWN
`bl prime`s too (it names `tracker`, and it predates the `show` hook). Every
project the operator founds fresh on this box gets the same tracker-less
landing. Worth telling the operator; it is their file.

PREMISE CHECK against the live world (read-only — inspected `<yog-data>/world/state/balls/clones/…/config`, never mutated it) and against balls 0.5.9's own source. The ball holds, and the damage is WIDER than it says.

CONFIRMED — the live landing for /home/u/dev/yog is tracker-less. Its committed `config/plugins.toml` wires ONLY `bl-delivery`, and its git log is a single `balls: found` commit with no remotes, so nothing was ever fetched or pushed:

    [hooks]
    "claim.post" = ["bl-delivery"]      "claim.pre"  = ["bl-delivery"]
    "close.post" = ["bl-delivery"]      "close.pre"  = ["bl-delivery"]
    "drop.post"  = ["bl-delivery"]      "prime.post" = ["bl-delivery"]
    "unclaim.post" = ["bl-delivery"]    "unclaim.pre" = ["bl-delivery"]

WIDER THAN THE BALL STATES — this is not "bl-tracker was pruned out of the current default". Three of those phase keys (`drop.post`, `claim.pre`, `unclaim.pre`) do not exist in balls 0.5.9's default schedule at all, and `show` — which 0.5.9 wires as `"show" = ["bl-delivery"]` — is absent. The operator's stale `~/.config/balls/default-config/plugins.toml` was an OLDER balls SCHEMA, so the landing is stale in its phase vocabulary too, not just short two plugin names. Consequence beyond the ball's list: a repair that only re-adds `bl-tracker` entries would leave `bl show <id>` still printing no worktree line. The repair has to restore the whole schedule, not patch names into it.

CONFIRMED — bl-e47b's fix is in at HEAD and is new-clones-only, exactly as the ball says. `src/multiplex/bl.rs::edge()` hands balls `space.config` as its config home, so `Xdg::default_config()` resolves `<world>/config/balls/default-config/` — which does not exist, so balls falls through to its EMBEDDED default (`seed.rs`: "the default-config is EMBEDDED in the binary and used DIRECTLY as the seed"). New landings are correct. Already-founded ones are untouched, because `seed_landing` runs only when the landing is absent (`checkout::prime` branches on `substrate::is_landing`) and `seed::rebind` "never prunes or rewrites the committed plugins.toml".

CANDIDATE 2 (the upstream balls ask) IS the right long-term home and I am NOT implementing it here — balls is a crates.io pin (`=0.5.9`) and yog cannot land it. CANDIDATE 3 (yog restating balls' seed default via `bl conf set`) stays rejected. Taking a fourth path that is neither: yog asks BALLS for its own default rather than restating it — `balls::seed::seed_landing` is `pub`, so the repair re-runs balls' own seed over the damaged landing and yog never names a phase, a plugin or an order.
