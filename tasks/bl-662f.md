## convo-sleuth findings (2026-08-01)

**Root cause: brazen's provider row for the gpt-5.x family is named
`openai-chatgpt` in `~/.config/brazen/config.toml`, but lernie's
`$LERNIE_HOME/models.yaml` (config root `~/.local/share/yog/world/lernie/`)
declares `gpt-5.4: provider: codex` — a name that does not exist in brazen's
config. When the operator's model-selector pick (bl-bd89) wrote that mapping
into the <workspace> workspace's `providers.yaml` (`lernie config
<workspace> default`), every subsequent `lernie prompt` in that workspace now
resolves `provider: codex` and brazen refuses it before any model call is
made.**

Direct, live-caught repro (not reconstructed — this fired while I was reading
the world, ts 1785622482, "today"): the operator's running yog attempted a new
conversation in the <workspace> workspace. yog's own op log shows the
exact sequence:

```
{"argv":["lernie","new","/home/u/.local/share/yog/workspaces/<workspace>"],"exit":0,...}
{"argv":["lernie","config","/home/u/.local/share/yog/workspaces/<workspace>","default"],"exit":0,...}
{"argv":["lernie","prompt",".../<workspace>","You are limb-skirt.\n\nthis working?"],"exit":-2,...}
```
(`~/.local/share/yog/world/state/yog/ops.jsonl`, last 3 lines)

The detached stderr capture for that `lernie prompt` spells out the failure
verbatim:

```
lernie prompt: provider error (Config): unknown provider `codex`
```
(`~/.local/share/yog/world/state/yog/detached/1785622482-<workspace>.err`)

That error is brazen's own `ConfigError::UnknownProvider` (brazen 0.0.5,
`src/config/errors.rs:46`, `"unknown provider \`{name}\`"`), raised at
`lernie prompt` runtime when it resolves the workspace's `providers.yaml`
worker-role provider against brazen's config — confirmed by direct repro
against the ambient brazen install:

```
$ bz --list-models --provider codex --json
unknown provider `codex`          # exit 78

$ bz --list-models --provider openai-chatgpt --json
{"models":[{"id":"gpt-5.4",...}, ...]}   # exit 0 — same models, right name
```

`~/.config/brazen/config.toml` only ever names this row `openai-chatgpt`
(`[[provider]] name = "openai-chatgpt"`, `base_url =
"https://chatgpt.com/backend-api/codex"`); there is no `codex` row and never
was one in this config. So "codex" is not a stale rename — it is simply the
wrong provider name for gpt-5.4 on this machine.

**Where "codex" comes from:** not yog's own code. `models.yaml` at
`$LERNIE_HOME/models.yaml` is written by lernie's own `prime` bootstrap verb
(yog invokes lernie's upstream `LERNIE_HOME=<home> lernie prime` contract
verbatim, by design — DESIGN §14 explicitly rejects "yog aping lernie's
seeding" as a drift risk; see `src/world/seed.rs`). yog's source has zero
references to `openai-chatgpt` anywhere (grepped) — it never hardcodes a real
provider name, by design; provider names are supposed to come from brazen's
own config at pick time. `codex` appears only in yog's test fixtures/doc
comments (`src/test_support.rs`, `src/model_pick/**/tests*`,
`src/config_edit/**/tests.rs`) as an illustrative example name — those are
fixtures, not the live default.

**Confirmed code gap (bl-bd89's actual territory):** `model_pick::plan()`
(`src/model_pick/mod.rs:53`) composes and returns both file writes
(`models.yaml` declaration + `providers.yaml` role assignment) with no check
against brazen's live provider roster — it only refuses on `GrammarError`
(malformed file shape). The UI-time "⚠ unknown provider `codex`" warning
(bl-bd89's reported text) comes from a separate roster comparison
(`model_pick::query`) that is advisory only: it does not gate `plan()`. So
today, picking a model whose provider brazen lacks still writes a config that
looks valid and only fails later, opaquely, inside a detached subprocess whose
stderr the operator never sees in the yog UI — which is exactly why this bug
report says "it failed" with no further detail: the real diagnostic
(`unknown provider \`codex\``) is sitting in a `.err` file under
`world/state/yog/detached/`, not surfaced anywhere in the running window.

**Relationship to bl-bd89:** this ball (bl-662f) is the downstream symptom of
bl-bd89's root condition. The fix belongs in bl-bd89's scope (make
`model_pick` refuse-or-hide a model whose provider brazen doesn't list,
per bl-bd89 question (b)) — that is a design decision already posed and not
yet made there, not something to improvise here. Not fixing bl-662f
independently: it has no separate code path to correct, and closing it without
bl-bd89's decision would just let the same write recur for the next unlisted
provider.
