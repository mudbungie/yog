Round 1, devadmin lane.

Two commands, back to back, the second using the exact name the first printed:

    $ lernie start ops "On box2, list the top 3 largest files under /var/log."
    {"kind":"prepared","ok":true,...}
    {"conversation":"WeekendEmerald","kind":"started","ok":true}
    $ lernie follow ops WeekendEmerald
    {"error":"unknown conversation \"WeekendEmerald\"","ok":false}

In the same second, the roster read of the same name succeeds:

    $ lernie agent ops WeekendEmerald
    {"agent":"20260906T040745Z-014100ec","display":"WeekendEmerald",...,
     "flight":"inference","ok":true,"present":true,...}

So the conversation exists, `agent` resolves it, and `follow` does not. It is
reproducible: it happened on every attempt to follow a conversation
immediately after starting it, and a `follow` a few seconds later resolves the
same name fine. So the two reads resolve a name off different state and the
follow lane`s copy lands later.

WHY IT MATTERS more than the seconds it costs: `start` then `follow` is the
obvious two-command shape for watching a task you just launched, and it is the
shape a script would use. The sentence it fails with — "unknown conversation"
— is the same one a typo earns, so an operator reads it as having got the name
wrong and goes looking, rather than as "wait a moment".

EXPECTED: a name `start` returned resolves everywhere the moment it is
returned. Failing that, the follow lane`s refusal distinguishes "no such
conversation" from "not yet followable" so the operator knows to retry.
