## Deterministic reproduction

1. Copy the release binary to `/tmp/yog-repro/yog` and start `yog serve` from it in an isolated world.
2. Atomically replace that pathname, matching the install shape: copy a new binary to `yog.next`, then `mv -f yog.next yog`.
3. While the old engine is still alive, drive a fresh start path such as `/prepare`.
4. Inspect the generated world shim.

Actual:

```sh
exec '/tmp/yog-repro/yog (deleted)' 'tool-control' "$@"
```

The next agent tool call fails closed because that literal executable does not exist. Other roster shims can still name the live pathname; `ensure_control` alone rewrote this one from a fresh `std::env::current_exe()`.

## Impact

An install, update, or release rebuild can leave a live GUI/server accepting work while every subsequent tool invocation fails at the adjudicator boundary. The generated script also persists the failure until another convergence pass rewrites it.

## Required invariant

A live engine must retain a stable executable target captured before its inode can be replaced, or otherwise refuse to write a non-executable procfs spelling. Cover a real copied executable whose pathname is atomically replaced, followed by Start and an actual tool-control consult.
