the operator has OL9 (X11) and macOS as prospective users, so the window-icon channel
is load bearing after all and the rasterizer stays.

**Correcting my own recommendation.** I proposed baking the embedded raster
into the binary. That is wrong on this repo's own principle: the binary can
compute those pixels, so storing a copy is storing what you can compute, and the
computation is microseconds at start-up. `icon_data()` keeps computing. What
genuinely needs baking is the set of files *external consumers* read, and there
the gap is real: `make install` lays down only `hicolor/scalable/apps/yog.svg`.
GNOME is happy with that; plenty of X11 shells and panels still want sized
PNGs, and OL9 is exactly that audience.

**What lands:**
- `icon/png.rs` — a dependency-free PNG encoder over `rgba()`. PNG's deflate
  permits *stored* blocks, so this is chunk framing, CRC-32 and an Adler-32
  zlib wrapper and nothing else. No decoder enters the binary; the repo's
  no-image-codec property survives intact.
- `make icon` emits `assets/yog.svg` and `assets/yog-{16,24,32,48,64}.png`,
  each held to the same derivation test the SVG already has.
- `make install` lays each PNG into `hicolor/<n>x<n>/apps/` beside the
  scalable SVG.
- DESIGN §11 documents the **three icon channels** — desktop entry + icon
  theme, window icon, and Wayland's app_id — because which one is load bearing
  depends on the display server and that is not obvious.

Sizes stop at 64: the scalable SVG covers everything larger, and stored-deflate
PNGs are uncompressed, so a 256 would be a quarter-megabyte of generated asset
for no reader.
