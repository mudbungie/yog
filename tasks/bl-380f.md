## Verified

- `src/start/mod.rs` `BallSpec::Existing { id, title, body, join }` carries no tags, and `src/projects/balls.rs` `Ball` does (`pub tags: Vec<String>`). `fleet::pilot::birth` reads the whole `Ball` off the snapshot and copies exactly those four fields into the payload, so tags stop there.
- Grepping `tags` across `src/start/` and `src/boundary/dispatch/` finds one unrelated hit (a doc comment about ops-row attribution). There is no skill selection anywhere in the start flow at all — not a discarded one, an absent one.
- The doc contradiction is real and both halves are current text. VISION §4.2: "Skills are seeded at spawn, keyed on ball tags... yog selects skills and model from the ball's tags at fire." VISION §3 ledger G6: "Model by complexity heuristic, not tag map | yog has a per-role picker; no policy layer, no dataset | yog (§4.6)".

## Why it parks rather than lands

The ball's own required result is "either land the promised tag-derived model/skill policy or amend the product promise". Those are mutually exclusive product outcomes and no ruling picks one.

The build horn is a new config surface with no ruling behind it. VISION §4.6 names the shape — "Policy table, yog config, severable" — but names it as the target, and the ledger row is an open gap owned by yog. The design questions the ball itself lists are unanswered: what a tag maps to when two tags both match, what an untagged ball gets, whether skills and model share one table or two, and where the table lives such that deleting it deletes policy rather than editing core code. Answering those is authoring the policy, not implementing a decided one.

The amend horn is equally the operator's: §4.2's present tense is a product promise, and softening it to intent is a decision about what the suite claims, not a code defect.

Worth noting the third fact, since it is what makes this a standing gap rather than an oversight: closed bl-3381 excluded the policy table deliberately and called for separate work, and no live task has owned it since. So the contradiction between §4.2 and G6 is not drift — it is a gap the ledger is already tracking, stated in the present tense one section earlier.

## What a ruling would need to fix

Pick the horn. If build: the conflict rule for multiple matching tags, the untagged default, one table or two, and the file it lives in (severability test — removing a default must delete config, not edit code). If amend: whether §4.2 restates as intent pointing at G6, or G6 is re-scoped.
