**Found driving bl-0a74, filed rather than folded into it**: the redial that ball
asks for is the foot's, and this is the engine's mirror of the same blip. It is a
different subject (every connection, not the tool lane), a different mechanism and
a different fix, and it affects a seat exactly as much as a foot.

## What happens

`src/wire/server.rs::serve` is one thread per accepted connection, looping
`while let Ok(Some(request)) = frame::read_value(&mut tls)`. Nothing sets
`set_read_timeout`, `set_write_timeout` or a keepalive on the accepted
`TcpStream` — grep for all three across `src/wire/` in production code returns
nothing; the only hits are test clients setting one on their own side.

So a peer that goes away **without a FIN or an RST** — the laptop that sleeps,
the network that changes, the relay switch REMOTE §1 calls canonical — leaves
that thread blocked in `read_exact` forever. The socket stays ESTABLISHED, no
kernel timer runs against it, and the thread never returns.

Two things are pinned to that thread's return and therefore never released:

- **The presence guard.** `let mut live = None; ... live.get_or_insert_with(...)`
  is a `Live` whose `Drop` decrements the refcount, and it drops when `serve`
  returns. The doc above it says the guard is released "however it ends: a clean
  close, a refused frame, a peer that vanished, a panicking thread" — the fourth
  case in that list is the one that does not hold. `Query::Clients` then reports
  `present: true` for a box that has been off the network for hours, which is
  precisely the fact presence is RAM in order to be honest about.
- **The thread itself.** One leaked OS thread per vanished peer, unbounded.

## Why bl-0a74 raises it from cosmetic to load-bearing

Today a roaming box's blip costs one leak, because the foot never comes back
(that was bl-0a74's whole complaint). Once the foot redials, every blip costs a
leak *and* leaves a stale presence row beside the live one — the refcount makes
the roster still say `true`, so the lie is invisible rather than merely stale, and
a box that flaps for a day accumulates a thread per flap.

**The reader slot is NOT among the casualties, and that distinction is the point.**
`Mailbox::take` drops its claim on the way out, before the answer is written, so
the one-reader claim is bounded by the hold (30 s) whatever the socket does. That
is now stated in REMOTE §5.1 and is what makes a redial's refusal retryable. Presence
and the thread have no such bound because their scope IS the connection.

## What the fix is not

Not the §13.4 idle-ping design: that is the punched wire's, it is unimplemented,
and it needs both ends. Not a sweeper thread over presence — presence has no
timestamp and adding one makes it stored state that can disagree with the map.

## The shape that looks right

A read timeout on the accepted stream, sitting comfortably above the two 30-second
holds the engine can legitimately be quiet for (`registry::mailbox::slots`'s
240x125 ms and `boundary::follow`'s 1875x16 ms), with a timeout treated as **the
connection is gone** and never as a retry — a timeout mid-record leaves rustls
with a half-read frame and there is no clean resume from it.

The far end already does exactly this and its reasoning is worth reading before
picking a number: thrall's channel sets a two-minute read timeout and says it is
"a bound on the transport, not on the wait", because the engine parks a
follow-class read for its hold and then answers, so a foot waiting for hours is a
sequence of answered reads and never one read held for hours. The engine's side of
that symmetry is the same argument with the direction reversed.

**The question that needs answering before it lands, and why this is its own ball:**
whether any client legitimately holds an open connection idle for longer than the
bound. A foot does not (it re-asks immediately). A seat dials per gesture. A third
client that did would start seeing its connection closed under it, so this is a
protocol-visible behaviour change across three components and wants an eye on it,
not a quiet import into a ball about redialling.
