Round-1 swdev lane. Engine: yog 0.0.38, main tip, isolated root, wire on 127.0.0.1:7742.

Reproduction, from a world with no workspaces:

    yog gesture --ws swdev '/prepare'                       # {"kind":"prepared","ok":true,…}
    yog gesture --ws swdev '/config brazen timeout = 120'

Verbatim reply:

    {"error":"No such file or directory (os error 2)","ok":false}

Nothing names the file. `yog env --ws swdev` prints `YOG_WALL=<yog-data-root>/world/walls/swdev`, and that path does not exist — `world/walls/` itself does not exist. One `mkdir -p <wall>/brazen` and the identical gesture answers `{"kind":"applied","ok":true}`.

Expected: the write creates the wall (README: 'A wall is born empty', which reads as a promise that it exists), or the refusal names the directory and says how to make it.

Severity p1 rather than p2. The README says a newborn workspace 'answers brazen's shipped provider rows and nothing else; custom rows and sign-ins are per-workspace acts you perform after birth' — and `/config brazen` is the act that adds a row. On a remote engine the only surfaces are gestures, and no gesture makes a directory, so a workspace born there can never be given a provider row the shipped table does not carry. That reaches REMOTE §1's whole premise: everything crosses the boundary. On a local box it is recoverable only by knowing the wall's path and reaching around the boundary with `mkdir`.

Second, smaller defect on the same line: the error is a bare `io::Error` Display with no path and no act. Every other refusal in this surface names its subject.

Measured cost in this lane: the workspace could not be pointed at a provider row at all until the directory was made by hand, so no agent could run — the shipped rows are api-key rows with no credential, plus `claude-code` and `ollama`.
