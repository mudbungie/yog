Round-1 daily lane. yog 0.0.38 (main c7916da1).

`Agent::failure` is capped by `src/git_tree/failure.rs::clause`:

    const CLAUSE_CAP: usize = 120;
    ...
        .chars()
        .take(CLAUSE_CAP)
        .collect()

There is no elision mark. Every other preview in the same reply vocabulary carries one — `conversations`'s own `preview` field in the same reply reads

    "What changed in the last 20 commits of this repository? Write a concise changel…"

so the operator has been taught that `…` means "there is more". A failure clause therefore reads as a whole sentence when it is not.

Seen: the worker's role was pointed at a model id the provider does not offer. `lernie agent` and `lernie attention` both answered

    failure: "model: not-a-real-model-xyz; `not-a-real-model-xyz` is not in the model cache; run `bz --list-models` to refresh or enab"

The provider's actual sentence, read out of the step's own driver record one query deeper, is

    ... run `bz --list-models` to refresh or enable partial matching

The cut lands inside the word that completes the remedy. The clause's own doc comment says "a row is a glance ... the whole of it is the steps surface", which is a fair rule; what it does not buy is a glance that hides the fact that it is one. Here the half sentence that survives ends in a verb, so it reads as an instruction that has been given in full.

Reproduction:

    lernie model <ws> worker <provider> not-a-real-model-xyz
    lernie message <ws> <agent> "anything"
    lernie agent <ws> <agent>       # failure ends "or enab"

Expected: the clause ends in the same `…` the sibling previews use, so a reader knows to open the step. A cap on a word boundary would be better still, and cheaper than the reader's second query.

Severity p3: cosmetic in mechanism, but it lands on the one string whose job is to say what to do next.
