## What the face actually does

`yog serve` is, in full:

    fn serve(ambient: &Env, overrides: &[(String, String)]) -> ! {
        seed_world_tools(ambient);
        let _engine = Engine::boot(…, Arc::new(NoRepaint));
        loop {
            std::thread::park();
        }
    }

There is **no signal handler**. A SIGTERM takes the default action, so the
process dies immediately: no `Drop` runs, the `Engine` is never dropped, its
worker/bridge/consumer/sentry/pilot threads are never stopped or joined, and
`Stream`'s drop — the one thing that would SIGTERM a child politely and wait
for it — never executes at all. The children survive their parent for as long
as it takes whatever killed the engine to reach them. Under systemd the cgroup
kill does that; outside it, they are orphaned.

The GUI has the same shape and it is fine there, because a window closing is a
human act and §4.1 makes the engine's own state write-through — there is
nothing to flush, which is exactly why there is no `on_exit` (bl-b54e). That
argument covers the ENGINE. It does not cover the WORK: an agent turn is a
child process holding a provider call in flight, and killing it discards the
work and the spend regardless of how clean the engine's own exit is.

## Why this is worth closing

Every restart is currently destructive, and everything downstream is a
workaround for that:

- the deployment (bl-bf35) defers a restart until the service cgroup holds one
  process, because it cannot ask the engine to stop cleanly;
- consequently a box that is never quiescent never updates, and the journal says
  so every hour;
- `yog.service` already carries `TimeoutStopSec=30s` and **nothing uses the
  grace** — systemd offers a window the process does not know exists.

A drain dissolves all three. Nothing else has to change: with a stop that
finishes or settles what is in flight, the reconciler's idle predicate becomes
an optimisation rather than a safety requirement.

## The shape to work out before building

- **What a stop means.** Refuse new turns and let running ones finish? Bound
  that by the systemd grace and settle the remainder? The pinned lernie already
  settles its own unanswered window on a graceful SIGTERM, so the engine's job
  may be no more than *pass the signal down and wait* — check that before
  designing anything larger.
- **Where it binds.** Signal handling belongs at the process edge, which in this
  tree is `main.rs` above eframe, beside the existing edge-bound arms. Note
  rule 3 in `CLAUDE.md`: `unsafe` is pinned to `src/cli_outbound/sys.rs` by an
  ast-grep rule and that file's `ignores` list is the one location authority —
  if a handler needs raw signal work it goes THERE, and adding a dependency for
  it needs explicit approval (rule 6, zero new deps).
- **Both faces or one.** The GUI and `yog serve` are one `Engine::boot` with
  different repaint hooks, and VISION V5.4 is that neither is a second
  implementation. A drain that exists on only one face would be exactly that.
- **What it must not become.** No new verb, no new flag, no config key — the
  signal IS the existing explicit signal. And it must stay testable: a stop
  that cannot be driven from a test is one that will rot.
