Operator complaint, 2026-08-12, verbatim:

> when you start a conversation, the ux is nonresponsive for a second. you send
> the message, but before it goes into the inbox, it's just missing for a
> minute, then it responds. The UI should be pretty much immediate: you write a
> message, it goes into inbox, pushing the inbox line up; right now, it looks
> like it's waiting for the send.

## What is actually happening

Nothing is blocked — the frame is fine. The message is *missing* because
**there is nothing on disk to render yet**, and yog renders only what a
completed derivation read off disk.

The chain, in order:

1. `start::execute_prompt` (`src/start/prompt.rs`) mints the name and
   `spawn_detached`s `lernie prompt --name <minted> <ws> <goal>`. It returns
   immediately. Nothing is written by yog.
2. The **detached lernie driver** is what first writes `agents/<id>/goal.md`
   and `agents/<id>/messages/001-user.md`. That is a separate process cold-
   starting: git worktree/branch setup, then the file.
3. Only once those files land does the fs watch mark the root dirty; then
   §7.2's debounce (`src/app/dirty.rs`: `DEBOUNCE = 100 ms`) plus the
   derivation pass, then `AppModel::refresh` takes the new snapshot.

So the operator's typed text has **no representation anywhere in yog's model**
between Enter and step 3. Read the model doc's own promise, `src/app/mod.rs:7`:

    //! latest *completed* derivation. Rendering reads that snapshot and nothing

That is the right architecture (see the standing principle: the UI never
freezes, the frame renders snapshots only). The defect is that the snapshot is
the *only* source — there is no place for a fact yog itself just caused and
knows to be true.

## What to build

An **optimistic pending echo**, reconciled by the snapshot — not a synchronous
write, and not a spinner.

The moment the send is accepted, the composer's text must be in the rendered
model as a pending row: the conversation row in the nav list, and the user
message at the tail of the transcript, pushing the surface up exactly as a
landed one does. When a later snapshot contains the real message, the pending
one is dropped and the real one takes its seat.

There is already a half of this to build on, not to duplicate:
`AppModel::await_conversation` holds the minted name as the focus claim before
any agent id exists (`src/start/prompt.rs` docs it: *"the started root has no
agent id until the detached driver writes its branch, so the name is what
identifies the conversation until then"*). That claim is a **focus** handle
only — it paints no row and carries no message text. Extend that one mechanism;
do not mint a second pending-state concept beside it.

Design questions the implementer must answer in DESIGN before coding:

- **Where the pending fact lives.** It is not derived from disk, so it cannot
  live in `Snapshot`. It belongs beside the focus claim in `AppModel`, and the
  render seats must compose snapshot + pending in one place, not per-seat.
- **Reconciliation key.** Matching on message text is fragile. Prefer the
  conversation name (already minted and unique) plus the fact that the pending
  echo is the *last* user message — a pending echo is superseded the moment the
  workspace shows a user message yog has not already got a landed row for.
- **Expiry.** A spawn that never lands (the fork failed, the driver died) must
  not leave a phantom row forever. The `-2`/synthetic-failure line already
  distinguishes those (§4.2, `src/start/prompt.rs` docs); a failed launch drops
  the echo, and a launched-but-silent one ages out on a stated bound and says
  so rather than vanishing.
- **The second and later messages too.** The same gap exists on
  `actions::verbs::message` — the deposit is piped and the flushed
  `NNN-user.md` only appears on the next derivation. One mechanism covers both
  or it will be built twice.

## Acceptance

A real-substrate drive beat, not an in-crate unit test alone: fire a start, and
assert the composed frame carries the operator's text **in the frame
immediately following the send**, with no derivation having run. Then let the
snapshot land and assert the row is not duplicated. Beware the vacuous-assertion
shapes already catalogued in bl-70b8 and bl-f16e.
