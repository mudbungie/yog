On this drive a conversation whose goal was "write these two files in this
working directory, run them, prove they work" reported success — test passing,
CLI output quoted, `ls -la` of both files shown — and its bound working
directory was untouched. The whole deliverable had been written into the tool
host's own process working directory: the directory whatever supervisor started
`thrall run` happened to be standing in. `/files` and `/work-diff` both answered
empty. Nothing anywhere said the work had gone somewhere else.

## The path it took, step by step

1. The model's first call is `apply_patch` — in the grant, offered in the
   schema list, answerable by nothing (sibling ball on the missing corpus).
2. The worktree lane's refusal names two remedies, and the model takes the
   first one it can act on itself:

   > use the clients tool to see this workspace's machines and **load what one
   > advertises** — or the operator enrols a thrall …

   The second refusal shape spells the consequence out loud —

   > load it with the clients tool to run it in **that machine's own
   > directory**

3. `clients op=load` binds `<client>_bash`, and the loaded lane carries **no
   cwd** on the invocation (that is its definition: locality rides in the name,
   REMOTE §5). The foot has no `cwd` on the entry, so it runs the argv in its
   own inherited process cwd.
4. `cat > tally.py`, `python3 test_tally.py`, `python3 tally.py sample.txt` — all
   exit 0, all in the foot's cwd. Every observation the model makes to check
   itself is made in the same wrong place, so the check cannot fail.

## Why the design's own reasoning condemns the destination

thrall's DESIGN §3.4 refuses a *relative* `cwd` in the operator's document, and
the reason it gives is exactly this directory:

> A relative one resolves against whatever directory the supervisor happened to
> start this process in — a place nobody wrote down, which changes when the unit
> file does, and which nothing in the running system reports.

An entry with **no** `cwd`, invoked with no cwd, lands in that same
nobody-wrote-it-down directory — the refused case reached through a different
door. A foot with no `cwd` on an entry has an implicit one, and it is the one
value the design says may not be used.

## Why it is worse than a misplaced file

Nothing at the boundary can tell the two runs apart. A conversation that built
the program in the right place and one that built it in the foot's scratch both
answer: quiescent, `stopped` ("came to rest — your turn"), `/work-diff` empty,
`/files` showing goal and soul. The transcript is a wall of exit-code-0. The
only witness that the workflow failed is a human running `ls` on the host.

## Shape of the repro

    # engine + one foot advertising a shell tool with subject_cwd: true, no cwd key
    yog gesture --ws <ws> '/prepare dir <dir>'
    …fire a goal that writes a file, phrased with no absolute path…
    # the model hits an unanswerable grant name, loads the foot's tool, and works
    ls <dir>                     # empty
    ls <the foot's process cwd>  # the deliverable

## Candidate answers, none chosen here

- The loaded lane refuses an entry that declares `subject_cwd` but is invoked
  with no directory — consent to run at a named place is not consent to run at
  an unnamed one. (thrall-side; yog would need to say why in the refusal.)
- A foot with no `cwd` on an entry refuses the entry at the read, exactly as a
  relative one is refused. (thrall-side, and the same argument.)
- The worktree lane's refusal stops advertising the loaded lane as a remedy for
  a workspace-subject name: the subject already chose the machine, so "run it
  somewhere else instead" is not a remedy for it. (yog-side,
  `src/tool_host/subject.rs::unconsented`.)
