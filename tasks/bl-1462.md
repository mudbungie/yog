**yog twin of thrall's bl-2d78**, filed here under the fix-where-it-lives
doctrine: the advertised set is engine-side state and the remedy is in this
crate.

## The defect

REMOTE §5.1 stores one advertised set per client identity, and the write is
last-writer-wins. Any connection presenting that identity's certificate may
replace it, and a foot that is running never finds out.

Observed: a running foot serving normally; a second connection using the same
leaf sent `{"op":"advertise","tools":[]}` and was answered
`{"kind":"advertised","ok":true}`. From then on every invoke for that client was
refused engine-side with

    client "<name>" advertises no tool "<tool>" right now

while the foot sat there healthy and holding a full set. Restarting the foot
restored it, because presenting happens on connect.

## Why the far end cannot notice

By design, and the design is stated: the advertisement is presented once per
channel, not once per dial, because the engine writes the set only when it
differs from what is stored. That reasoning is sound for traffic and assumes
nothing else writes the set. Nothing in the protocol makes that true: there is
no version, no generation and no receipt on the read that would let a foot
detect that the set it presented is not the set in force.

## How real it is

It takes a leaf the operator minted, so this is not a stranger's reach. The
realistic shapes are a copied entry directory, a box provisioned twice, or a
foot restarted while the old process is still up. In each the failure is silent
on both ends: the engine believes the box offers nothing, the box believes it
is serving, and the only symptom is invocations refused for a tool that plainly
exists.

## What is being asked for

A visible seam, decided under REMOTE §5's two-rates doctrine. A tool set changes
when the operator reconfigures a machine; two connections under one identity
disagreeing about it, while one of them is parked on a follow-class read, is not
a rate-of-change event — it is two processes claiming one machine's name, and it
should be said out loud to whichever party can act on it.

The candidate rulings, from cheapest:

1. Refuse a **second concurrent follow-class read** for a client that already
   has one parked. Two parked readers under one identity is the pathology
   itself, and refusing the newcomer in band names it to the party that just
   arrived.
2. Refuse an advertisement that would **change** a stored set while that client
   holds a parked read. A foot re-presenting an unchanged set writes nothing
   and is untouched, so the ordinary reconnect path does not notice this at all.

Both are in-band refusals over existing shapes: no new verb, no new field, no
protocol movement. The ruling belongs in REMOTE §5.1's neighborhood.

The reader rule is also what makes the sibling ball's redelivery predicate
exact — a redelivery keyed on "the client asked for work again" is only sound
when one reader at a time may ask.
