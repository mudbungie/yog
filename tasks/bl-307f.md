Found by drive (docs/drive-logs/2026-07-27-s5-s7-s8-wire-green.md, S7-T2 beat).

Drive fixture: overwrite a real step's `steps/<agent>/001/request.json` with `{ this is not json`, open Steps → the step → the `request` drill-in. What renders is the bytes verbatim, monospace, with no framing at all (src/steps_view/mod.rs `Doc::of_bytes` → `Doc::Raw` on a parse error; src/steps_view/render.rs prints `ui.monospace(from_utf8_lossy)`). Nothing crashes and no byte is lost — the substance holds.

But two authorities say more than that:
- DESIGN §11 (Altitude 2): 'a file yog cannot parse renders as an error row rather than vanishing'.
- STORIES.md S7-T2: 'a malformed step file renders an error row and the sibling tabs still build'.

Rendered plain, an unparseable file is indistinguishable from a file whose content happens to be that text — the reader cannot tell 'this is malformed' from 'this is prose'. So one of the two is wrong and it is a one-line decision either way:
(a) code: mark the Raw arm of a *parse failure* (as against an absent file, already '(absent)') with an ichor row — e.g. 'unparseable JSON — bytes verbatim below' — and keep the bytes; the view-model already distinguishes the cases, so the framing is a render concern only. `Doc::Raw` would need to carry WHY it is raw (absent / unparsed) for the renderer to say so.
(b) DESIGN + STORIES: restate the promise as 'renders its bytes verbatim rather than vanishing', which is what the code does and is defensible ('every byte inspectable').

Recommend (a): the promise is about the reader knowing, and 'nothing is summarized away' is not the same claim as 'you are told it is broken'. Either way the drive beat then asserts the marker rather than only 'no crash'.
